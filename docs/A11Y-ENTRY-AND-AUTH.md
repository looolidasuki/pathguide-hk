# 盲用 UX：啓動入口與登錄註冊

適用範圍、設計判讀、以及一套可驗收的規範。

## 0. 設計判讀

**讀作：** 面向全盲與低視力用户的**原生 Android/iOS 應用**（不是網頁），
信任優先、無障礙為硬約束，風格延續既有的 M3 深色 + 綠色種子 `#2E7D32`。

**三檔刻度**（`design-taste-frontend` §1.A 的「trust-first / accessibility-critical」一行）：
`DESIGN_VARIANCE 3` / `MOTION_INTENSITY 2` / `VISUAL_DENSITY 4`。

**本 skill 的適用範圍聲明（§13）：** 原生移動端被明確劃在範圍外（"Native mobile:
use Apple HIG / Material directly"）。所以這裏**只借用它的推斷紀律**
（先判讀、再定刻度、無障礙約束壓倒審美偏好），實現規範走
**Material 3 + Apple HIG + WCAG 2.2 + TalkBack/VoiceOver 指南**，
不用它的落地頁條款（hero、bento、marquee、eyebrow 計數等在這裏無意義）。

**對照現實：** 現有 `app/lib/ui/demo_page.dart` 裏 **`Semantics` 出現 0 次**，
`app/lib/main.dart` 只有 `home: DemoPage()`，沒有路由、沒有帳號、沒有持久化。
所以本文是從「有」開始設計，不是改。

## 1. 首要原則：**登錄不得擋路**

這一條優先於本文其他所有內容。

領路通是**行動輔具**。如果未登錄就不能用引導功能，那麼忘密碼、斷網、
服務器故障、帳號被鎖，都會把一個盲人**丟在街上**。所以：

| 功能 | 未登錄 | 已登錄 |
|---|---|---|
| 實時識別 + 粵語播報 | ✅ 完整可用 | ✅ |
| 演示路線引導 | ✅ 完整可用 | ✅ |
| 上傳未識別障礙物 | ❌ | ✅ |
| 跨裝置同步設置 | ❌ | ✅ |

**登錄是雲功能的門，不是應用的門。** 登錄頁必須有一個
**「稍後再説」**（不是小小的「跳過」，而是與登錄按鈕同級的次按鈕），
觸發後直接進入引導，且**不再重複彈窗**（只在用户主動點「上傳」時再問一次）。

> 這與「離線優先」一致：模型在 APK 裏，推理在端上，
> 登錄唯一增加的是上傳通道。

## 2. 第一部分：盲人怎麼打開這個應用

### 2.1 六條真實路徑

按「對全盲用户的實際可靠性」排序，不是按實現難度。

| # | 路徑 | 全盲可用性 | 代價 |
|---|---|---|---|
| 1 | **桌面圖標 + TalkBack 雙擊** | ★★★★★ 永遠可用，零配置 | 已具備，只要 label 正確 |
| 2 | **語音「Ok Google，開啟領路通」** | ★★★★★ 最自然 | 只要 label 本地化正確；進階要 App Actions |
| 3 | **藍芽耳機 / 自拍遙控的按鍵** | ★★★★☆ 很多視障用户本來就戴着 | 需處理按鍵事件 |
| 4 | **快速設定磁貼（Quick Settings）** | ★★★★☆ 雙指下拉後可聚焦 | 需 `TileService` |
| 5 | **系統無障礙快捷方式（音量鍵/三指）** | ★★★☆☆ 各家 ROM 名目不同 | 多半隻能指向服務，指向 App 不穩 |
| 6 | **長按圖標出 App Shortcuts** | ★☆☆☆☆ **不適合當主路徑** | 需要視覺瞄準；TalkBack 下要走「動作」菜單，不是長按 |

**結論：** 把資源花在 1、2、3 上。第 6 條不要當賣點（它是給視力正常的人設計的），
如果做了，必須同時在 TalkBack 的「動作」菜單裏可達。

### 2.2 語音啓動（路徑 2）為什麼現在不行

Android 的語音啓動靠 **應用 label 匹配**。現在 `AndroidManifest.xml` 寫的是
硬編碼 `android:label="領路通"`，有兩個問題：

1. **不隨系統語言變**。手機設成英文的視障用户必須用中文念「領路通」才能啓動，
   或者根本匹配不上（他不會知道要念中文）。
2. **助理只認一個名字**。用户可能説「領路通」「PathGuide」「路通」，
   只能匹配到 label 字面。

**改法：** label 走 `@string/app_name`，分語言提供：

| 資源目錄 | `app_name` | 誰會命中 |
|---|---|---|
| `values/`（默認） | `PathGuide` | 英文系統 |
| `values-zh-rHK/` | `領路通` | 香港中文系統（粵語用户） |
| `values-zh-rTW/` | `領路通` | 台灣 |
| `values-zh-rCN/` | `領路通` | 簡體 |

讀音可辨識度要點：「領路通」三個字在粵語和普通話裏都不與其他常見 App 撞車，
是個好名字，**不要**改成「導航」「地圖」這類會與系統應用搶匹配的詞。

### 2.3 語音啓動（進階）：App Actions

`res/xml/shortcuts.xml` 裏聲明 capability，可以做到
**「Ok Google，同領路通開始引導」直接開啓相機並播報**，不必先開 App 再找按鈕。

```xml
<shortcuts xmlns:android="http://schemas.android.com/apk/res/android">
  <capability android:name="actions.intent.OPEN_APP_FEATURE">
    <intent
        android:action="android.intent.action.VIEW"
        android:targetPackage="hk.pathguide.pathguide"
        android:targetClass="hk.pathguide.pathguide.MainActivity">
      <parameter android:name="feature" android:key="feature" />
    </intent>
  </capability>
</shortcuts>
```

Manifest 裏掛上：

```xml
<meta-data android:name="android.app.shortcuts" android:resource="@xml/shortcuts" />
```

⚠️ **實話：** App Actions 需要應用已上架 Play 才生效，且 Google 正在把它
遷到 Android 16 的 **AppFunctions**（Gemini 側）。所以：
- 現階段**先做 2.2 的 label 本地化**（立刻見效，零依賴）；
- App Actions 等上架後再補，別在畢設階段花時間。

### 2.4 硬件按鍵（路徑 3）

用藍芽快門/耳機按鍵啓動，對視障用户價值很高（手機在口袋/掛繩上，
不用掏出來找圖標）。做法：在 `MainActivity` 覆寫 `dispatchKeyEvent`，
對**特定長按組合**響應，而不是裸搶音量鍵。

**為什麼不能裸搶音量鍵：** 音量鍵是系統級的，搶過來會讓用户無法調音量
（視障用户依賴耳機音量），而且會與 TalkBack 自己的快捷鍵衝突。

建議：只響應**媒體按鍵的長按**（`KEYCODE_MEDIA_PLAY` 長按 800ms），
並在設置裏可關。這是有代價的設計，要留給用户選。

### 2.5 快速設定磁貼（路徑 4）

`TileService` 在 Android 7+，雙指下拉通知欄即可看到一排磁貼，
TalkBack 可逐個聚焦並雙擊。相比桌面圖標，它的優勢是**不必回主屏**。

這是我認為**性價比最高的第二條路徑**：一個約 40 行的 `TileService`，
一個 `Tile` 圖標，無第三方依賴。

### 2.6 啓動後必須立刻出聲

全盲用户啓動後**唯一的確認信號是聲音**。所以首幀就要播報，文案要短、可打斷。

**不要**在每次啓動都念完整介紹。分兩種：

| 情形 | 播報 |
|---|---|
| 首次安裝後第一次啓動 | 「領路通。第一次使用，會問你相機權限，我來帶你過。要聽操作説明請説『説明』。」 |
| 之後每次啓動 | 「領路通，正在啟動鏡頭。」→（相機就緒後）「鏡頭就緒，可以開始。」 |
| 從口袋誤觸啟動 | 「領路通已開啟。若你不是要使用，請説『關閉』或按兩次電源鍵。」 |

**誤觸啓動是個真問題**：手機在口袋/包裏被喚醒很常見，而相機一開就是耗電 +
隱私。設計上：啓動後**先給 3 秒的「取消窗口」**，此窗口內不打開相機、
不上傳任何東西，只播報那句詢問。

### 2.7 iOS（對應 teammate 倉庫裏的 `VisionPlugin.swift`）

| 路徑 | 做法 |
|---|---|
| Siri | 「喂 Siri，開啟領路通」。靠 `CFBundleDisplayName`（同樣要本地化：`InfoPlist.strings`） |
| App Intents | iOS 16+ 的 `AppShortcutsProvider`，可定義短語直接跑動作，是 SiriKit 的現代替代 |
| 輕點背面 | 設定 → 輔助使用 → 觸控 → 輕點背面 → 選一個會啓動本 App 的捷徑。視障用户可穩定觸發 |
| 藍芽遙控 | 同 Android |

## 3. 第二部分：首次啓動與權限（真正的第一道坎）

比登錄更早、也更容易失敗的一步是**相機權限**。現在的代碼在啓動時直接觸發系統
權限對話框，對視障用户是這樣一幅景象：正在聽播報，突然被一個沒預期的系統
彈窗打斷，TalkBack 讀到幾句按鈕名，但他不知道這是什麼、為什麼問、該按哪個。

**規範：**

1. **先説，再問。** 觸發系統對話框**之前**播報：
   > 「接下來會問你相機權限。這個 App 靠相機認路，不開就沒辦法引導。
   > 我會把焦點移到『允許』，你聽到『允許』就雙擊。」

2. **教互動，不教位置。** 絕不説「按右下角的按鈕」。
   説「用 TalkBack 找到『允許』，然後雙擊」。位置描述對全盲用户是噪音。

3. **給退路，別把人堵死。** 權限頁要有三個選項，且同級：
   - 「允許相機」（主）
   - 「先聽語音示範」（不開相機，只播一段樣本，讓用户確認聲音正常）
   - 「稍後再説」

4. **永久拒絕後**必須給出可執行的路，並**念出來**：
   > 「相機權限被關掉了。要開啟：設定，應用程式，領路通，權限，相機，允許。
   >  要我把這段再念一次請説『重複』。」
   並提供一個「開啟設定」按鈕（`Semantics(button: true)`）。

5. **同一頁面內不重複請求。** 被拒後不再自動彈。這是 Android 的硬限制
   （第二次拒絕後系統不再顯示對話框），也符合「不騷擾」。

## 4. 第三部分：登錄 / 註冊

### 4.1 認證方式排序（這就是設計決策本身）

按「打字量」和 WCAG 2.2 合規性排序，**不是**按實現難度：

| 順位 | 方式 | 打字量 | 為什麼排這裏 |
|---|---|---|---|
| 1 | **Passkey（指紋/臉）** | 0 | 生物辨識確認，不需記憶、不需輸入。Android Credential Manager / iOS 原生支援 |
| 2 | **Google 帳號** | 0 | 一次點擊 + 生物辨識；用户已登入的帳號 |
| 3 | **Apple 帳號** | 0 | 同上（iOS 上若提供 Google，**App Store 審核 4.8 強制**也要提供 Apple） |
| 4 | **Email 一次性碼** | 少（可貼上） | 保底方式。必須自動讀取或允許貼上 |
| 5 | Email + 密碼 | 多 | **最後手段**。見下 |

**為什麼密碼排最後：** WCAG 2.2 **SC 3.3.8 Accessible Authentication (Minimum)**
（AA 級）規定：不得要求使用者通過**認知功能測試**才能登入，除非提供了
替代方式或輔助。從記憶裏敲密碼就是認知功能測試。該條明確的合規路徑是
**允許密碼管理器/自動填充與粘貼**。Passkey 與 SSO 直接繞過整個問題。

**硬性要求（不是建議）：**
- ❌ **不得阻止粘貼**到密碼/驗證碼框（SC 3.3.8 明文）。
- ❌ **不得使用圖形驗證碼**。reCAPTCHA 的拼圖/選圖是認知功能測試；
  若必須用風控，用**音頻驗證碼**或**設備端不可見風控**。
- ✅ 輸入框聲明 `autofillHints`，讓密碼管理器能填。

### 4.2 明確**不要**的設計（每一條都寫清理由）

| ❌ 不要 | 理由 |
|---|---|
| 手勢/圖案密碼 | 純空間記憶 + 視覺輔助，全盲用户無法使用 |
| 「記住我」複選框 | 對盲人是無意義的選擇題。應該**默認保持登錄**，安全靠生物辨識把關 |
| 密碼強度彩色進度條 | 顏色變化對全盲用户信息量為零。要改成**文字 + 播報**（「目前強度：中等，建議加長度」） |
| 自動登出 / 表單短逾時 | SC 2.2.1 Timing Adjustable：必須可延長。OTP 倒數要能延長並播報剩餘時間 |
| 只有 placeholder 沒有 label | 視覺與朗讀都會受損；label 必須常駐（Material 的 `labelText`） |
| 驗證碼圖片 | 同上，認知測試 |
| 「確認密碼」欄 | SC 3.3.7 Redundant Entry：同一資訊不要求輸入兩次 |

### 4.3 頁面與語義樹

**一個頁面一件事。** 登錄頁不要同時塞註冊，用兩個獨立頁面（盲人用户在
長表單裏迷路的成本比多一次跳轉高得多）。

```
[登錄頁]
  ├─ 標題  "登入領路通"            Semantics(header: true)  ← 頁面進入時焦點在此
  ├─ 説明  "登入後可以把未識別的障礙物上傳。不登入也能引導。"  （一句，聽完就懂）
  ├─ 主動作區（按 4.1 順位，有幾個就放幾個）
  │    ├─ [用指紋登入]            ← 有 passkey 時才顯示
  │    ├─ [用 Google 帳號登入]
  │    └─ [用 Apple 帳號登入]     ← iOS 上必備
  ├─ 次要  [用 Email 登入]        （展開才顯示 email 欄）
  ├─ 進度/錯誤區                  Semantics(liveRegion: true)
  └─ 次按鈕 "稍後再説"            ← 與上面同級，不是灰字小連結
```

**焦點順序必須等於朗讀順序**，用 `FocusTraversalGroup` +
`OrdinalSortKey` 釘死，不依賴 widget 樹的偶然順序。

**按鈕 label 必須是「動作 + 結果」：**

| ❌ | ✅ |
|---|---|
| 「Google」 | 「用 Google 帳號登入」 |
| 「確定」 | 「確認並登入」 |
| 「提交」 | 「建立帳號」 |
| 「↗」（圖標按鈕） | 「在新視窗開啟服務條款」 |

理由：圖標和品牌色對全盲用户沒有信息量，**label 是唯一的語義載體**。
Material 的 `IconButton` 必須給 `tooltip`（Flutter 會把它變成語義 label）。

**加載態：** 不要只放轉圈。按下後按鈕 label 換成「正在登入，請稍候」，
並在 liveRegion 播報一次。盲人用户按完按鈕後的第一反應是「按到了嗎」，
**必須立刻有聲音反饋**，不能等網絡回來。

**錯誤態：** 全部走 liveRegion，且文案要説「下一步做什麼」：

| 情形 | 播報 |
|---|---|
| 網絡不通 | 「連不上網路。引導功能不受影響，你可以先『稍後再説』。要重試請雙擊『重試』。」 |
| 用户取消 | 「已取消，沒有登入。」（不要報錯誤） |
| 該 email 已用別的 provider 註冊 | 「這個信箱之前用 Google 註冊過。要我用 Google 幫你登入嗎？」 |
| 生物辨識不可用 | 「這台手機沒設定指紋或臉部。改用 Google 帳號登入，或先『稍後再説』。」 |
| 帳號被鎖 | 「帳號暫時被鎖。要聯絡支援請雙擊『客服』，或先『稍後再説』繼續使用引導。」 |

### 4.4 視覺規範（低視力用户與陪護者仍然需要）

全盲用户靠 TalkBack，但**低視力用户**（這是視障人羣裏的大多數）與
**陪護者/志願者**仍然看屏幕。所以視覺不是可以省掉的。

| 項 | 規範 | 依據 |
|---|---|---|
| 主題 | 沿用 M3 深色，seed `#2E7D32`。全頁一個主題，不中途反色 | skill §4.11 |
| 對比度 | 正文 ≥ 7:1（AAA），大字 ≥ 4.5:1 | WCAG 1.4.6 |
| 目標尺寸 | **≥ 56dp**（比 Android 最低 48dp 更大） | 低視力用户需要 |
| 圓角 | 一套：按鈕全圓角（pill），卡片 16dp，輸入框 12dp，寫進常量 | skill §4.4 |
| 焦點態 | TalkBack 綠框之外，再加 **2dp 描邊 + 形狀變化**，不靠顏色單獨表達 | WCAG 1.4.1 |
| 字號 | 支持系統縮放 **到 200% 不截斷**；用 `textScalerOf`，禁止固定高度 | WCAG 1.4.4 |
| 錯誤 | 圖標 + 文字，**不用紅/綠顏色單獨表達** | WCAG 1.4.1 |
| 強調色 | 單一強調色貫穿全頁；錯誤色是語義色，不算第二強調色 | skill §4.2 |

**不要**在登錄頁放品牌大圖、輪播、動效。`MOTION_INTENSITY 2`：
只有 `:active` 的按壓反饋與 200ms 的淡入，且必須 `prefers-reduced-motion` 友好。

### 4.5 註冊流程：把輸入量壓到最小

**最高效的註冊就是沒有註冊。** 用 Google/Apple 首次登入即建號，
只需要用户確認一次「顯示名稱」（可從帳號帶出，可跳過）。

若必須用 email：
1. 郵箱地址 → 用**系統帳號選擇器**（Android Autofill / iOS 從「郵件」App 取），
   而不是讓用户逐字敲。
2. **不要**「輸入兩次郵箱」「輸入兩次密碼」（SC 3.3.7）。
3. 驗證碼：優先 **Android SMS Retriever API**（自動讀取，用户零操作）；
   降級方案是**允許從通知複製粘貼**，絕不要用户背下來再敲。
4. 註冊完成後**立刻播報**「帳號已建立，已登入。要開始引導請雙擊『開始』。」

### 4.6 帳號綁定（Google / Apple / Passkey）

**綁定的語義：一個帳號可以掛多個登錄方式。** 這比「合併兩個帳號」簡單得多，
也更安全。原則：

1. **主鍵用經過驗證的 email。** Google/Apple 都會給（Apple 的
   「隱藏我的郵件」轉發地址也算驗證過的地址，要單獨處理，不要與真實 email 合併）。
2. **首次登入時不要靜默創建第二個帳號。** 若該 email 已存在，必須問：
   > 「這個信箱已經有帳號了。要用 Google 登入原本的帳號嗎？」
   供「是，連結」與「不，取消」兩個同級選擇。
3. **綁定/解綁必須在「設定 → 帳號」裏可達且可播報**，
   且**解綁最後一個登錄方式時禁止**（否則帳號就鎖死了），並提供刪除帳號的出口。
4. **Apple 的「隱藏我的郵件」**會產生一次性轉發地址。若用户先用 Apple 再用 Google
   登入同一郵箱，兩者**不應自動合併**（因為地址不同），要按 1 的流程問。
5. **刪除帳號**必須應用內可用，不需要聯繫客服（App Store 5.1.1(v) 與
   Google Play 都強制）。刪除前播報清楚刪掉什麼、保留什麼。

### 4.7 台詞表（TTS 文案，中文 / 粵語）

登錄頁的**每一句**都要能被聽懂，且不依賴看到任何東西。

| 場景 | 文案 |
|---|---|
| 進入登錄頁 | 「登入頁。登入後可以把未識別的障礙物上傳。不登入也能引導。」 |
| 焦點到 Google 按鈕 | 「用 Google 帳號登入，按鈕。雙擊以登入。」 |
| 等待中 | 「正在登入，請稍候。」 |
| 成功 | 「登入成功。歡迎回來。」 |
| 跳過 | 「好，不登入。開始引導。」 |
| 元素列表讀到底 | 「已經是最後一項。下面還有『稍後再説』。」 |

> 粵語版另做一套（`AppStrings` 已有 `_zh` 分支模式，擴展時不要寫成
> 「普通話文案 + 粵語讀音」的折中，寧可少幾句也要是真粵語）。

## 5. 實現順序與依賴風險

### 5.1 依賴風險（必須先驗證，別急着寫）

`app/pubspec.yaml` 記着一條硬約束：本倉庫**路徑含空格**，任何拉入
`objective_c` 的依賴都會因 build hook 不給子進程路徑加引號而構建失敗，
且它在**所有平台**都跑。

已核實的直接依賴（pub.dev API，2026-10-06）：

| 包 | 版本 | 直接依賴是否含 `objective_c` |
|---|---|---|
| `google_sign_in` | 7.2.0 | 否 |
| `sign_in_with_apple` | 8.2.0 | 否 |
| `firebase_auth` | 6.7.0 | 否 |
| `passkeys` | 2.23.1 | 否 |
| `credential_manager` | 5.1.0 | 否 |
| `shared_preferences` | 2.5.6 | 否（其 `_foundation` 也只依賴 `meta` + 接口包） |

⚠️ **但這不足以下結論。** `objective_c` 是從**構建 hook** 進來的，不在
pub 依賴列表裏（`permission_handler` 當初就是這麼中招的）。**唯一可信的判定
是真的跑一次 `flutter pub get` + 構建。** 所以第 1 步就是這個，
不要先寫 300 行 UI 再發現裝不上。

### 5.2 順序（每步都可獨立驗證）

| 步 | 做什麼 | 怎麼驗證 | 依賴 |
|---|---|---|---|
| 1 | label 本地化（`@string/app_name` + 4 個 `values-*`） | 倉庫測試斷言資源存在 + XML 良構 | 無 |
| 2 | 啓動即播報 + 3 秒取消窗口 | `flutter test`（假 TTS 斷言首條台詞） | 無 |
| 3 | 權限頁（先説再問 + 三個同級選項 + 永久拒絕路徑） | `flutter test` + 真機 TalkBack | 無 |
| 4 | `Quick Settings` 磁貼 | 真機 | 無 |
| 5 | 登錄頁 UI（**純本地 stub，無網絡**） | `flutter test` 斷言語義樹與焦點順序 | 無 |
| 6 | Passkey | 真機（需 Google 帳號 + Credential Manager） | 1 次構建驗證 |
| 7 | Google / Apple 登入 | 真機（需 OAuth client ID + SHA-1 + Apple Developer） | 後端決策 |
| 8 | 帳號綁定/解綁/刪除 | 真機 | 7 |

**5 之前的每一步都不需要網絡也不需要帳號**，可以立刻做。
**7 需要你先定後端**（見下）。
