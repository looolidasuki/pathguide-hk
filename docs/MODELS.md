## 0. 一句話結論

**端上只跑一個模型**：3 類（行人 / 自行車 / 垃圾桶）的 YOLO11n 微調版，
TFLite int8、輸入 416、2.74 MiB，隨 App 打包，**離線**運行。
其餘模型（COCO、YOLO-World、Grounding DINO、SAM 2.1、LocateAnything-3B）
**只在訓練/標註階段在服務器上跑，永遠不下發到手機**。

## 2. 模型清單（`detector.json`）字段與校驗

**為什麼清單必須存在**：TFLite 文件裏**沒有**「這個模型是用哪些 class-id 訓的」
這個元數據。這份信息以前寫死在 `app/lib/vision/model_class_map.dart` 的一個常量裏——
本地開發沒問題，但模型一旦能從服務器下發，**服務端換了類別集而 App 不知道**，
於是每個框的名字都是錯的，**而且不報錯**。

所以清單**跟着模型一起走**，`modelClassIds` 的來源是訓練數據集的 `classes.json`
（那份文件的 `original_id` 就是真實 id），**不是手寫**。

| 字段 | 含義 | 校驗 |
|---|---|---|
| `format` | 清單格式版本 | 必須 `== 1`，不認識就報錯（**不忽略未知字段**） |
| `version` | 模型版本，用於下發比對 | 必填 |
| `file` | 模型文件名 | 必填 |
| `bytes` | 模型字節數 | 必填；與實際文件比對（防「換了模型忘重生成清單」） |
| `sha256` | 模型哈希 | 必須 `^[0-9a-f]{64}$`；App 側據此校驗下載完整性 |
| `inputSize` | 輸入邊長 | 必填 |
| `modelClassCount` | 模型類別數 | 必填 |
| `modelClassIds` | 本地索引 → 項目 id | 長度必須 `== modelClassCount`；id 必須在類別表內；**不得重複** |
| `trainedAt` | 訓練日期 | 由 `version` 前綴推出 |
| `map50` | 訓練/驗證 mAP50 | 可空 |

**空映射表只在一個條件下合法**：`modelClassCount == kNumClasses`（48）。
此時本地索引就是項目 id，不需要映射。其餘情況給空表 → **直接失敗，不猜**。

**故意不寫進清單的**：數據集路徑。清單是要下發到手機上的資產，
裏面出現 `C:\Users\...` 既沒意義又泄露開發機佈局；
追溯信息改為在導出時打到日誌裏（`映射來源數據集：dataset_poc3`）。

### 守這條不變量的是哪些測試

| 測試 | 守什麼 |
|---|---|
| `app/test/model_manifest_test.dart` | 字段解析、8 類拒絕、內置清單與內置模型同步（防漂移） |
| `app/test/model_class_map_test.dart` | 映射逐項正確；長度不符 / 越界 / 重複 → 返回 `null` 而不是猜 |
| `tests/test_published_model.py` | 默認導出源 == 端上那一份；清單與模型自洽；映射落在類別表內 |
| `scripts/check_tflite_decode.py` | 模型佈局 ↔ Kotlin 解碼假設 ↔ 座標換算三者一致 |

## 3. 老師模型（只在訓練/標註階段用，**不下發**）

| 模型 | 用途 | 階段 | 實測表現 |
|---|---|---|---|
| `yolo11n.pt`（COCO 預訓練） | 微調起點 + COCO 預標 | 訓練 / 預標 | COCO 只覆蓋表裏 **3 類**（bicycle 精確、pedestrian ↔ person、table ↔ dining table 語義不等價） |
| `yolov8s-world.pt` | 零樣本開放詞表提案 | stage1（`--teacher yoloworld`，默認） | 9 個核心類**零召回**（`stairs` 0.000）；不能單獨當老師 |
| `IDEA-Research/grounding-dino-tiny` | 寬覆蓋預標 | stage1（`--teacher gdino`）/ 預標 | 當時 48 類的表裏 **46 類非零**（stairs 60%、step 60%、road_excavation 100%、tactile_paving 30%、barrier_fencing 83%）；但 **11.3 s/圖**（⚠️ 這個數是**在 RTX 5070 上測的**，`gd_detect.py` 用 `.to("cuda")`）、約 **66 框/圖**噪聲。2 張 HK 街景實測 **12.8 s/圖**（`.venv-vlm`，50 類提問）、**43/50 類非零** |
| `sam2.1_t.pt` | 掩膜精修（把框修準） | stage2 | 本地權重齊全（74.5 MB），**未接進 stage1 的新路徑** |
| `nvidia/LocateAnything-3B` | VLM 裁剪驗證「這裏面有沒有 <類別>」 | stage2 / stage3 | 需 `transformers 4.57.1` + bf16；在 `.venv-vlm` 裏跑。權重 **7.66 GB 本地齊全**，在**系統緩存** `~/.cache/huggingface/hub`（分片 4959.6 + 2701.8 MB）。⚠️ **它在系統緩存，GDINO 在工作區 `.hf/hub` —— 兩處分居，不要為切換而全局覆蓋 `HF_HUB_CACHE`/`HF_HOME`**（覆蓋會把另一個藏起來，實測因此白查了一輪「網絡不通」）。⚠️ 許可是 NVIDIA License §3.3：**僅限非商用** |

**老師鏈的定位**：老師的作用是**把人工標註量從 33 h 降到 16.8 h**（現 50 類 × 250 框 ≈ 12,500 框），
不是替代人工。**沒有任何老師模型能直接給出可用的 50 類模型**——
GDINO 覆蓋廣但噪聲大，YOLO-World 對結構性障礙（樓梯、路障）零召回，
COCO 只認識 3 類。所以保留**人工抽樣質檢**這一環。

**蒸餾的結論**：用 COCO 模型蒸餾可以拿到「別人訓練後的效果」的**一部分**——
實測恢復老師 94% 的框——但**只能恢復老師認識的那些類**。
老師不認識樓梯，蒸餾也變不出樓梯。所以蒸餾用於**省標註**，不用於**補類別**。

### 4.1 比較模型時必須寫明閾值

產品的播報門檻是 **0.70**（`kMinSpeakScore`），而 ultralytics 默認報告的 P/R
**不在這個閾值上**。只看默認口徑會得出「加入第三方數據後行人精確率從 0.756 崩到
0.469」；而在 0.70 處兩版是 0.980 vs 0.945 —— **差別消失**。

所以本項目約定：**任何模型指標必須寫明取值閾值**，用
`scripts/compare_at_threshold.py` 打出多個閾值下的曲線，而不是隻報一個數。
一個不帶閾值的「精確率」在本項目裏沒有解釋力，因為產品只在一個閾值上運行。

> ⚠️ `export_tflite.py` 的默認權重**曾經指向 `pg_review_v0`（24 類）**。
> 於是一條普通的 `python scripts/export_tflite.py` 會導出一個類別數與
> `configs/classes.json` 對不上的模型，**而且不報錯**。
> 已改為指向 `pg_poc3`，並由 `tests/test_published_model.py` 釘住。

## 5. 換模型的操作清單（照抄，別憑記憶）

換一份端側模型時，以下**五步缺一不可**，少一步就是靜默錯類：

1. **訓練** → `python scripts/train_yolo.py --data data/<數據集>/dataset.yaml --name <run>`
2. **導出**（必須在 `.venv-export` 裏，見 `scripts/export_tflite.py` 頂部説明）
   → `python scripts/export_tflite.py --weights runs/<run>/weights/best.pt --dataset data/<數據集> --deploy int8 --version <日期>.1 --map50 <驗證值>`
   這一步會**同時**寫模型和清單，並把清單打印出來核對。
3. **核對形狀**：導出腳本會打印 tflite 的輸入/輸出張量形狀。類別數與佈局
   （`anchors_first = d1 > d2`）必須與 Kotlin 解碼假設一致，否則先修再往下走。
4. **跑門禁**：
   - `python scripts/check_tflite_decode.py`（佈局 ↔ Kotlin ↔ 座標換算三者一致）
   - `python -m pytest -q`（含 `test_published_model.py`：默認導出源 == 端上那一份）
   - `cd app && flutter analyze && flutter test`（含清單防漂移）
5. **真機驗證** → `scripts/verify_on_device.ps1`（裝包→喚醒→啓動→截圖→抓 HUD）
   HUD 上必須看到 `classes=3`、`映射 [6, 11, 7]`、`invalid=0`。

> **類別 id 只增不改**：`configs/classes.json` 的 1–22 已凍結。
> 新增類別只能**追加**，絕不能重排——重排會讓所有歷史標籤和已發佈模型全部錯位。

## 6. 將來：模型下發（未做）

當前模型是**隨 APK 打包**的。計劃中的下發流程：

```
用户手機拍照 → 上傳「未識別障礙物」圖片 + 新路線
   → 服務器側大模型/VLM 標註 → 人工抽樣質檢
   → 訓練 → 評測門禁 → 打包【模型 + 清單】→ 下發到手機
```

**下發單位是「模型 + 清單」這一個整體**，不是單獨的 `.tflite`。
App 側收到後：校驗 `sha256` → 讀 `modelClassIds` → 用清單裏的映射解本地索引。
`platform_vision.dart` 現在會先加載並校驗清單，**清單與模型不符就拒絕啓動**並顯示原因
（`模型清單有問題` / `模型與清單不符`），而不是猜一個映射繼續跑。

**注意**：「有沒有檢測到框」**不能**用作上傳觸發條件——
實測 143,784 幀裏 2,358 幀（**98%**）都有候選檢測，
所以這個條件會把幾乎所有幀都傳上去。觸發判據尚未確定。
