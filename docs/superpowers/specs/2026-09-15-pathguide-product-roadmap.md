# 领路通（PathGuide HK）产品版演进路线图

**日期：** 2026-09-15
**状态：** 规划（未经资源与商务论证，见 §6 的假设声明）
**前置文档：** `docs/superpowers/specs/2026-09-15-pathguide-thesis-design.md`（毕设版设计）

---

## 1. 本文档的定位与诚实边界

毕设版（16 周、单人、Android 原型）与产品版（12 个月、6–8 人、跨平台产品）之间的差距**不是技术难度的差距，而是资源与合作的差距**。

**必须先说明的三点：**

1. **本文档中的预算、人数、周期均沿用 `企划书.md` 的数字，未经独立论证。** 它们的作用是提供量级感知，不是可执行预算。
2. **真正的阻塞项不是技术，是合作意向。** BLE 信标部署需要商场物业许可，商业室内地图需要采购，用户测试需要机构合作与伦理审批。这些的周期以**月**计，且不完全在你的控制之下。
3. **因此本路线图的主要价值是排序与前置条件识别**，而非承诺。凡标注"前置条件"的项，未满足即不应启动。

---

## 2. 毕设版 → 产品版的差距清单

| 维度 | 毕设版 | 产品版 | 差距性质 |
|---|---|---|---|
| 平台 | Android | iOS + Android | 工程 |
| 区域 | 调景岭（+中环验证） | 全港主要商场 + 所有港铁站 | 数据 + 商务 |
| 室外定位 | GPS + 视觉节点确认 | GPS + PDR 融合 | 工程 |
| 室内定位 | 节点确认式（无连续定位） | BLE + WiFi 指纹 + PDR 多源融合 | **硬件部署 + 商务** |
| 室内地图 | 手绘节点图 | 地政总署 3D 室内地图 API + 商业数据 | 数据接入 + 采购 |
| 场景理解 | YOLO + OCR + 规则 | + 端侧量化 VLM | 模型 + 机型依赖 |
| 语音 | 系统 TTS | 系统 TTS + Azure Neural TTS | 工程 |
| 用户验证 | 3–5 人非正式 | 30 人、6 轮正式测试 | **合作 + 伦理审批** |
| 后端 | 无 | 路线缓存 + 反馈管道 | 工程 |
| 团队 | 1 人 | 6–8 人 | 资源 |

**关键观察：差距清单里，标注为"工程"的项都可以靠时间解决；标注为"商务/合作"的项不能。**

## 3. 演进阶段

阶段按**依赖顺序**排列，不按重要性。每一项的前置条件未满足时启动，都会造成返工。

### P1 · 跨平台化与后端基线

| 项 | 内容 |
|---|---|
| 增量 | 毕设版功能冻结后，迁移至产品级架构；建立最小后端（路线缓存 + 匿名反馈收集） |
| **前置条件** | **毕设版功能冻结**（未冻结就重写 = 重写两次） |
| 周期 | 约 2–3 个月 |
| 人力 | 移动端 ×2、后端 ×1 |

**毕设版对 P1 的贡献：** 采用 Flutter 已使这一迁移大幅简化——这正是选择 Flutter 的主要理由。但**毕设版的 Android 专用原生通道（TFLite/ML Kit）在 iOS 上需要等价实现**，这是 P1 的主要工作量，不是 UI 迁移。

**风险：** iOS 侧 ML Kit 与粤语 TTS 的可用性未经验证。**建议 P1 的第 1 周先做 iOS 端 TFLite + OCR + TTS 的可行性验证**，再决定是否投入完整迁移。

---

### P2 · 地政总署 3D 室内地图接入

| 项 | 内容 |
|---|---|
| 增量 | 接入官方三维室内地图与室内路线 API，覆盖所有港铁站 |
| **前置条件** | 毕设版的站内段已验证可行（证明价值） |
| 数据可得性 | ✅ 已开放，空间数据共享平台免费下载 |
| 周期 | 约 2 个月 |
| 人力 | 地图/后端 ×1、移动端 ×1 |

**依据：** 地政总署已于 2025-10 将三维室内地图扩展至所有港铁站（[政府新闻公报](https://www.info.gov.hk/gia/general/202510/09/P2025100900161.htm)）。这是**免费且合法**的数据源，应优先于任何商业采购。

**毕设版对 P2 的贡献：** 毕设版在调景岭站验证的"站内节点确认"逻辑，可直接复用于官方路网数据之上。

**注意：** 官方数据覆盖港铁站，**不覆盖商场**。商场部分需 P6 的商业数据或自建。

---

### P3 · 端侧量化 VLM

| 项 | 内容 |
|---|---|
| 增量 | 在端侧运行量化 VLM，用于场景描述与开放词汇识别兜底 |
| **前置条件** | **目标机型内存 ≥ 8 GB**（依赖机型迭代，不在你控制内） |
| 候选模型 | Gemma 4（量化版）；Qwen2.5-VL-3B（INT4，中文/粤语场景理解更强） |
| 周期 | 约 2–3 个月 |
| 人力 | CV ×2 |

**为什么排在 P2 之后：** 它解决的是"OCR 与闭集检测都覆盖不到的开放场景"。在 P1–P2 阶段，这类场景的频率尚不清楚，**过早引入会造成资源错配**。

**推理策略（来自 `企划书.md` §6 挑战一，予以保留）：** 动态推理频率——静态场景（直行）每秒 1 次，动态场景（接近路口/障碍密集）每秒 3–5 次。

**必须实测的指标：** 内存峰值、连续 10 分钟机身温度、电量消耗曲线。**任何一项不达标都应回退，而不是靠降低帧率硬撑。**

---

### P4 · BLE Beacon + WiFi 指纹定位

| 项 | 内容 |
|---|---|
| 增量 | 商场内部署 BLE 信标，实现 1–3 米室内定位 |
| **前置条件** | **商场物业合作意向书** —— 这是真正的阻塞项 |
| 参考方案 | 香港失明人协进会"智能逍遥行"：商场墙面安装约 10–15 个信标，误差约 1 米 |
| 成本 | 硬件成本低（信标单价低），**部署与许可成本高** |
| 周期 | 合作谈判 3–6 个月；部署 1 个月/商场 |
| 人力 | 移动端 ×1、现场 ×1 |

**为什么这在毕设阶段不可行：** 不是技术问题，而是**需要物业许可、需要进入非公共区域施工、需要长期维护承诺**。个人毕设无法提供这些。

**替代路径（建议优先）：** 见 P6。

---

### P5 · 视障用户测试

| 项 | 内容 |
|---|---|
| 增量 | 招募 30 位视障人士，进行 6 轮用户测试 |
| **前置条件** | 与香港失明人协进会 / 香港盲人辅导会建立正式合作；**伦理审批** |
| 周期 | **前置沟通与伦理审批 3+ 个月**，测试执行 2–3 个月 |
| 人力 | 产品/无障碍顾问 ×1、研究助理 ×1 |

**这是整个路线图中最需要提前启动的一项。** 伦理审批与用户招募的周期以月计，且无法通过增加人力压缩。

> **对毕设阶段的强烈建议：** 即使只做 **3–5 人非正式访谈**，也应在毕设期间完成。理由：
> 这是论文中唯一能证明"这东西真的有用"的一手证据，也是产品版寻求合作与资助时最有力的材料。
> 非正式访谈不需要伦理审批（以可用性访谈而非临床试验形式进行），成本仅数天。

---

### P6 · 商业室内数据与视觉定位兜底

| 项 | 内容 |
|---|---|
| 增量 | 采购 Mapxus 等商业室内地图数据；以视觉定位作为 BLE 不可用时的兜底 |
| **前置条件** | 预算；商务谈判 |
| 数据现状 | Mapxus CityGeni 覆盖约 150 个本地室内设施 |
| 周期 | 商务谈判 2–4 个月 |
| 人力 | 后端/地图 ×1 |

**视觉定位兜底的技术路径（毕设版已初步实现，可延伸）：**
当 BLE/WiFi 不可用时，用 OCR 读店铺招牌与楼层指示牌，反查预设 POI 数据库确定位置。**毕设版的 logo 分类器 + OCR 双通道正是这条路径的原型。**

**战略判断：** P4（自建信标）与 P6（采购数据）是**替代关系而非互补关系**。
- 若目标是快速覆盖多个商场 → **P6 更划算**；
- 若目标是在少数商场做到最优体验 → P4 更划算。

**建议：优先 P6。** 理由：产品价值在于覆盖面，而自建信标的边际成本（每个商场都要谈判 + 部署 + 维护）无法随规模下降。

## 4. 依赖关系图

```
毕设版（M0–M6）
   │  功能冻结
   ▼
  P1 跨平台 + 后端 ──────────┐
   │                        │
   ├──→ P2 官方室内地图 ─────┤
   │                        │
   ├──→ P3 端侧 VLM          │  （P2 与 P3 可并行）
   │                        │
   └──→ P6 商业室内数据 ─────┴──→ 全港覆盖
              ▲
              │ （替代关系，二选一或先 P6 后 P4）
         P4 BLE 信标
              ▲
              │ 前置：物业合作意向书（周期 3–6 月，应最早启动谈判）

  P5 用户测试 ── 前置：机构合作 + 伦理审批（周期 3+ 月，应最早启动）
```

**两条"应最早启动"的线：** P4 的合作谈判与 P5 的伦理审批。它们的周期由外部决定，且不因技术进度加快而缩短。**如果这两项在毕设答辩后才开始谈，产品版的时间表会整体后移半年。**

## 5. 团队与资源（沿用 `企划书.md`，供量级参考）

**核心团队 6–8 人：**

| 角色 | 人数 | 在路线图中的主要归属 |
|---|---|---|
| 移动端工程师 | 2 | P1、P2、P4 |
| 计算机视觉工程师 | 2 | P3、P6、毕设版模型维护 |
| 后端/地图工程师 | 1 | P1、P2、P6 |
| 语音交互设计师 | 1 | P1 及全程语音体验迭代 |
| 产品经理/无障碍顾问 | 1 | P5、P4 合作谈判 |
| （研究助理） | 1 | P5 用户测试执行 |

**推荐合作机构（沿用 `企划书.md`）：**
- 香港失明人协进会 —— 用户测试、需求调研；
- 香港盲人辅导会 —— 用户招募、场景验证；
- 地政总署测绘处 —— 室内地图数据接入；
- 香港赛马会慈善信托基金 —— 资金支持（该基金已有资助视障导航项目先例）。

**预算（沿用 `企划书.md` 估算，未独立论证）：** 12 个月约港币 300–500 万，人员薪资 60%、云端 GPU 15%、硬件设备 10%、用户测试与运营 15%。

## 6. 假设与未知（必须显式声明）

| # | 假设 | 若假设不成立的影响 |
|---|---|---|
| 1 | 预算与人员规模达到 `企划书.md` 水平 | 路线图整体不可行，退化为"毕设版 + 单商场试点" |
| 2 | 能取得商场物业的 BLE 部署许可 | P4 不可行，须完全依赖 P6 商业数据 |
| 3 | 能取得伦理审批与机构合作 | P5 不可行，产品缺乏用户验证依据 |
| 4 | 目标机型内存 ≥ 8 GB 可普及 | P3 不可行，端侧 VLM 须推迟 |
| 5 | 地政总署数据接口长期稳定开放 | P2 须自建室内路网，成本大幅上升 |
| 6 | Mapxus 等供应商愿意合作且价格可接受 | P6 不可行，商场覆盖须逐一自建 |

**这 6 项中，1 与 6 属于商务，2 与 3 属于合作，4 属于市场，5 属于政策。** 技术团队无法单独消解其中任何一项——这正是"毕设版优先"这一决策的核心理由：**毕设版在 16 周内交付一个不依赖任何上述假设的完整可演示系统，而产品版必须等待外部条件成熟。**

## 7. 从毕设版继承的资产

以下资产在毕设版完成后可直接或低成本迁移到产品版，是毕设版投资的回报：

| 资产 | 迁移方式 |
|---|---|
| 16 类检测模型 + 数据集 | 直接复用；产品版仅需增量加类 |
| logo 分类器流水线 | 直接复用；新增店铺只需补 40–80 张图 |
| 自举标注流水线（v0 + SAM + VLM 复核） | 直接复用，是扩展到全港时**唯一可规模化的数据生产手段** |
| 决策层的纯 Dart 规则引擎 | 直接复用；这是产品版最核心的业务资产 |
| `VisionSource` 抽象与回放测试集 | 直接复用；使产品版能在无真机情况下回归测试 |
| 黄金集与评测方法 | 直接复用；成为产品版的持续质量门禁 |
| Flutter 代码库 | 大部分复用；iOS 原生通道需等价实现（见 P1） |

**结论：毕设版不是产品版的一个缩水版本，而是产品版的第一阶段。** 除 P4（BLE）外，产品版的每一项都以毕设版为起点，而非从零开始。
