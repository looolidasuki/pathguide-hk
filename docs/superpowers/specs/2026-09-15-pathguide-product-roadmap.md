# 領路通（PathGuide HK）產品版演進路線圖

**日期：** 2026-09-15
**狀態：** 規劃（未經資源與商務論證，見 §6 的假設聲明）
**前置文檔：** `docs/superpowers/specs/2026-09-15-pathguide-thesis-design.md`（畢設版設計）

---

## 1. 本文檔的定位與誠實邊界

畢設版（16 周、單人、Android 原型）與產品版（12 個月、6–8 人、跨平台產品）之間的差距**不是技術難度的差距，而是資源與合作的差距**。

**必須先説明的三點：**

1. **本文檔中的預算、人數、週期均沿用 `企劃書.md` 的數字，未經獨立論證。** 它們的作用是提供量級感知，不是可執行預算。
2. **真正的阻塞項不是技術，是合作意向。** BLE 信標部署需要商場物業許可，商業室內地圖需要採購，用户測試需要機構合作與倫理審批。這些的週期以**月**計，且不完全在你的控制之下。
3. **因此本路線圖的主要價值是排序與前置條件識別**，而非承諾。凡標註"前置條件"的項，未滿足即不應啓動。

---

## 2. 畢設版 → 產品版的差距清單

| 維度 | 畢設版 | 產品版 | 差距性質 |
|---|---|---|---|
| 平台 | Android | iOS + Android | 工程 |
| 區域 | 調景嶺（+中環驗證） | 全港主要商場 + 所有港鐵站 | 數據 + 商務 |
| 室外定位 | GPS + 視覺節點確認 | GPS + PDR 融合 | 工程 |
| 室內定位 | 節點確認式（無連續定位） | BLE + WiFi 指紋 + PDR 多源融合 | **硬件部署 + 商務** |
| 室內地圖 | 手繪節點圖 | 地政總署 3D 室內地圖 API + 商業數據 | 數據接入 + 採購 |
| 場景理解 | YOLO + OCR + 規則 | + 端側量化 VLM | 模型 + 機型依賴 |
| 語音 | 系統 TTS | 系統 TTS + Azure Neural TTS | 工程 |
| 用户驗證 | 3–5 人非正式 | 30 人、6 輪正式測試 | **合作 + 倫理審批** |
| 後端 | 無 | 路線緩存 + 反饋管道 | 工程 |
| 團隊 | 1 人 | 6–8 人 | 資源 |

**關鍵觀察：差距清單裏，標註為"工程"的項都可以靠時間解決；標註為"商務/合作"的項不能。**

## 3. 演進階段

階段按**依賴順序**排列，不按重要性。每一項的前置條件未滿足時啓動，都會造成返工。

### P1 · 跨平台化與後端基線

| 項 | 內容 |
|---|---|
| 增量 | 畢設版功能凍結後，遷移至產品級架構；建立最小後端（路線緩存 + 匿名反饋收集） |
| **前置條件** | **畢設版功能凍結**（未凍結就重寫 = 重寫兩次） |
| 週期 | 約 2–3 個月 |
| 人力 | 移動端 ×2、後端 ×1 |

**畢設版對 P1 的貢獻：** 採用 Flutter 已使這一遷移大幅簡化——這正是選擇 Flutter 的主要理由。但**畢設版的 Android 專用原生通道（TFLite/ML Kit）在 iOS 上需要等價實現**，這是 P1 的主要工作量，不是 UI 遷移。

**風險：** iOS 側 ML Kit 與粵語 TTS 的可用性未經驗證。**建議 P1 的第 1 周先做 iOS 端 TFLite + OCR + TTS 的可行性驗證**，再決定是否投入完整遷移。

---

### P2 · 地政總署 3D 室內地圖接入

| 項 | 內容 |
|---|---|
| 增量 | 接入官方三維室內地圖與室內路線 API，覆蓋所有港鐵站 |
| **前置條件** | 畢設版的站內段已驗證可行（證明價值） |
| 數據可得性 | ✅ 已開放，空間數據共享平台免費下載 |
| 週期 | 約 2 個月 |
| 人力 | 地圖/後端 ×1、移動端 ×1 |

**依據：** 地政總署已於 2025-10 將三維室內地圖擴展至所有港鐵站（[政府新聞公報](https://www.info.gov.hk/gia/general/202510/09/P2025100900161.htm)）。這是**免費且合法**的數據源，應優先於任何商業採購。

**畢設版對 P2 的貢獻：** 畢設版在調景嶺站驗證的"站內節點確認"邏輯，可直接複用於官方路網數據之上。

**注意：** 官方數據覆蓋港鐵站，**不覆蓋商場**。商場部分需 P6 的商業數據或自建。

---

### P3 · 端側量化 VLM

| 項 | 內容 |
|---|---|
| 增量 | 在端側運行量化 VLM，用於場景描述與開放詞彙識別兜底 |
| **前置條件** | **目標機型內存 ≥ 8 GB**（依賴機型迭代，不在你控制內） |
| 候選模型 | Gemma 4（量化版）；Qwen2.5-VL-3B（INT4，中文/粵語場景理解更強） |
| 週期 | 約 2–3 個月 |
| 人力 | CV ×2 |

**為什麼排在 P2 之後：** 它解決的是"OCR 與閉集檢測都覆蓋不到的開放場景"。在 P1–P2 階段，這類場景的頻率尚不清楚，**過早引入會造成資源錯配**。

**推理策略（來自 `企劃書.md` §6 挑戰一，予以保留）：** 動態推理頻率——靜態場景（直行）每秒 1 次，動態場景（接近路口/障礙密集）每秒 3–5 次。

**必須實測的指標：** 內存峯值、連續 10 分鐘機身温度、電量消耗曲線。**任何一項不達標都應回退，而不是靠降低幀率硬撐。**

---

### P4 · BLE Beacon + WiFi 指紋定位

| 項 | 內容 |
|---|---|
| 增量 | 商場內部署 BLE 信標，實現 1–3 米室內定位 |
| **前置條件** | **商場物業合作意向書** —— 這是真正的阻塞項 |
| 參考方案 | 香港失明人協進會"智能逍遙行"：商場牆面安裝約 10–15 個信標，誤差約 1 米 |
| 成本 | 硬件成本低（信標單價低），**部署與許可成本高** |
| 週期 | 合作談判 3–6 個月；部署 1 個月/商場 |
| 人力 | 移動端 ×1、現場 ×1 |

**為什麼這在畢設階段不可行：** 不是技術問題，而是**需要物業許可、需要進入非公共區域施工、需要長期維護承諾**。個人畢設無法提供這些。

**替代路徑（建議優先）：** 見 P6。

---

### P5 · 視障用户測試

| 項 | 內容 |
|---|---|
| 增量 | 招募 30 位視障人士，進行 6 輪用户測試 |
| **前置條件** | 與香港失明人協進會 / 香港盲人輔導會建立正式合作；**倫理審批** |
| 週期 | **前置溝通與倫理審批 3+ 個月**，測試執行 2–3 個月 |
| 人力 | 產品/無障礙顧問 ×1、研究助理 ×1 |

**這是整個路線圖中最需要提前啓動的一項。** 倫理審批與用户招募的週期以月計，且無法通過增加人力壓縮。

> **對畢設階段的強烈建議：** 即使只做 **3–5 人非正式訪談**，也應在畢設期間完成。理由：
> 這是論文中唯一能證明"這東西真的有用"的一手證據，也是產品版尋求合作與資助時最有力的材料。
> 非正式訪談不需要倫理審批（以可用性訪談而非臨牀試驗形式進行），成本僅數天。

---

### P6 · 商業室內數據與視覺定位兜底

| 項 | 內容 |
|---|---|
| 增量 | 採購 Mapxus 等商業室內地圖數據；以視覺定位作為 BLE 不可用時的兜底 |
| **前置條件** | 預算；商務談判 |
| 數據現狀 | Mapxus CityGeni 覆蓋約 150 個本地室內設施 |
| 週期 | 商務談判 2–4 個月 |
| 人力 | 後端/地圖 ×1 |

**視覺定位兜底的技術路徑（畢設版已初步實現，可延伸）：**
當 BLE/WiFi 不可用時，用 OCR 讀店鋪招牌與樓層指示牌，反查預設 POI 數據庫確定位置。**畢設版的 logo 分類器 + OCR 雙通道正是這條路徑的原型。**

**戰略判斷：** P4（自建信標）與 P6（採購數據）是**替代關係而非互補關係**。
- 若目標是快速覆蓋多個商場 → **P6 更划算**；
- 若目標是在少數商場做到最優體驗 → P4 更划算。

**建議：優先 P6。** 理由：產品價值在於覆蓋面，而自建信標的邊際成本（每個商場都要談判 + 部署 + 維護）無法隨規模下降。

## 4. 依賴關係圖

```
畢設版（M0–M6）
   │  功能凍結
   ▼
  P1 跨平台 + 後端 ──────────┐
   │                        │
   ├──→ P2 官方室內地圖 ─────┤
   │                        │
   ├──→ P3 端側 VLM          │  （P2 與 P3 可並行）
   │                        │
   └──→ P6 商業室內數據 ─────┴──→ 全港覆蓋
              ▲
              │ （替代關係，二選一或先 P6 後 P4）
         P4 BLE 信標
              ▲
              │ 前置：物業合作意向書（週期 3–6 月，應最早啓動談判）

  P5 用户測試 ── 前置：機構合作 + 倫理審批（週期 3+ 月，應最早啓動）
```

**兩條"應最早啓動"的線：** P4 的合作談判與 P5 的倫理審批。它們的週期由外部決定，且不因技術進度加快而縮短。**如果這兩項在畢設答辯後才開始談，產品版的時間表會整體後移半年。**

## 5. 團隊與資源（沿用 `企劃書.md`，供量級參考）

**核心團隊 6–8 人：**

| 角色 | 人數 | 在路線圖中的主要歸屬 |
|---|---|---|
| 移動端工程師 | 2 | P1、P2、P4 |
| 計算機視覺工程師 | 2 | P3、P6、畢設版模型維護 |
| 後端/地圖工程師 | 1 | P1、P2、P6 |
| 語音交互設計師 | 1 | P1 及全程語音體驗迭代 |
| 產品經理/無障礙顧問 | 1 | P5、P4 合作談判 |
| （研究助理） | 1 | P5 用户測試執行 |

**推薦合作機構（沿用 `企劃書.md`）：**
- 香港失明人協進會 —— 用户測試、需求調研；
- 香港盲人輔導會 —— 用户招募、場景驗證；
- 地政總署測繪處 —— 室內地圖數據接入；
- 香港賽馬會慈善信託基金 —— 資金支持（該基金已有資助視障導航項目先例）。

**預算（沿用 `企劃書.md` 估算，未獨立論證）：** 12 個月約港幣 300–500 萬，人員薪資 60%、雲端 GPU 15%、硬件設備 10%、用户測試與運營 15%。

## 6. 假設與未知（必須顯式聲明）

| # | 假設 | 若假設不成立的影響 |
|---|---|---|
| 1 | 預算與人員規模達到 `企劃書.md` 水平 | 路線圖整體不可行，退化為"畢設版 + 單商場試點" |
| 2 | 能取得商場物業的 BLE 部署許可 | P4 不可行，須完全依賴 P6 商業數據 |
| 3 | 能取得倫理審批與機構合作 | P5 不可行，產品缺乏用户驗證依據 |
| 4 | 目標機型內存 ≥ 8 GB 可普及 | P3 不可行，端側 VLM 須推遲 |
| 5 | 地政總署數據接口長期穩定開放 | P2 須自建室內路網，成本大幅上升 |
| 6 | Mapxus 等供應商願意合作且價格可接受 | P6 不可行，商場覆蓋須逐一自建 |

**這 6 項中，1 與 6 屬於商務，2 與 3 屬於合作，4 屬於市場，5 屬於政策。** 技術團隊無法單獨消解其中任何一項——這正是"畢設版優先"這一決策的核心理由：**畢設版在 16 周內交付一個不依賴任何上述假設的完整可演示系統，而產品版必須等待外部條件成熟。**

## 7. 從畢設版繼承的資產

以下資產在畢設版完成後可直接或低成本遷移到產品版，是畢設版投資的回報：

| 資產 | 遷移方式 |
|---|---|
| 16 類檢測模型 + 數據集 | 直接複用；產品版僅需增量加類 |
| logo 分類器流水線 | 直接複用；新增店鋪只需補 40–80 張圖 |
| 自舉標註流水線（v0 + SAM + VLM 複核） | 直接複用，是擴展到全港時**唯一可規模化的數據生產手段** |
| 決策層的純 Dart 規則引擎 | 直接複用；這是產品版最核心的業務資產 |
| `VisionSource` 抽象與回放測試集 | 直接複用；使產品版能在無真機情況下回歸測試 |
| 黃金集與評測方法 | 直接複用；成為產品版的持續質量門禁 |
| Flutter 代碼庫 | 大部分複用；iOS 原生通道需等價實現（見 P1） |

**結論：畢設版不是產品版的一個縮水版本，而是產品版的第一階段。** 除 P4（BLE）外，產品版的每一項都以畢設版為起點，而非從零開始。
