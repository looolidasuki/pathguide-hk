# 領路通（PathGuide HK）畢設版設計文檔

**日期：** 2026-09-15
**狀態：** 已批准（brainstorming 階段完成）
**範圍：** 畢業設計版本 —— 端側視覺感知 + 節點確認式語音引導原型
**非範圍：** 導航 API 集成、決策狀態機、室內路網、BLE 定位、端側 VLM（見 §10 與產品版路線圖）

---

## 1. 項目定位

一個運行於 Android 手機上的香港視障人士尋路輔助原型。核心命題不是"告訴用户往哪走"，而是**"幫用户確認自己走在正確的路上"**——導航 API 給出宏觀方向，攝像頭視覺模型確認微觀環境，兩者交叉驗證後生成語音引導。

**畢設版聚焦其中風險最高、最需要提前驗證的一環：視覺感知層能否在真機上實時、可靠地認出香港特有的通行設施。**

## 2. 演示區域與路線分工

選定區域：**調景嶺站 → 地面行人路 → 彩明苑天橋系統 → 彩明商場**，範圍控制在 300 × 300 米內。

| | 路線 A（調景嶺） | 路線 B（中環） |
|---|---|---|
| 路徑 | 調景嶺站 → 地面行人路 → 彩明苑天橋 → 彩明商場 | 中環站 A 出口 → 地面街道 → 中環行人天橋 → IFC |
| 官方室內數據 | ✅ 覆蓋（地政總署 2025-10 起擴展至全港鐵站） | ✅ 站內覆蓋，❌ IFC 商場內無覆蓋 |
| 天橋密度 | 中（1 段，緊鄰商場） | 高 |
| 採集難度 | 低（距離短、人流少） | 中（人流密集、隱私敏感） |
| **角色** | **主實驗區**：數據、訓練、指標、Demo 全在此 | **泛化驗證集**：僅採集 + 評測，**不重訓模型** |

**設計依據：** 路線 B 的價值不是"再做一遍"，而是提供**跨區域泛化能力的證據**——"在 A 訓練，在 B 上召回率仍達 X%"。若僅在 A 採集評測，無法排除對單一橋樑的過擬合。B 的增量成本僅為半天採集 + 一次評測。

**待實地核實（阻塞節點圖定稿）：** 彩明商場與調景嶺站之間是"天橋直達"還是"需經地面行人路"。前者只有一個室內外切換點，後者會多出一段室外街景段。**兩種情形都不影響本設計的任何決策**，隻影響節點圖。

**政府數據依據：**
- 地政總署三維室內地圖已擴展至所有港鐵站：[政府新聞公報](https://www.info.gov.hk/gia/general/202510/09/P2025100900161.htm)
- 彩明商場為領展旗下社區商場：[維基百科](https://zh.wikipedia.org/wiki/%E5%BD%A9%E6%98%8E%E5%95%86%E5%A0%B4)

## 3. 系統總體架構

核心工程約束：**決策與感知的業務邏輯必須能脱離真機單測。** 單人 + 16 周 + 需寫論文，若每次調規則都要拿手機出門實測，項目必然延期。

```
┌────────────────── Flutter App (Dart) ──────────────────┐
│  相機 (camera/CameraX) ─→ JPEG 幀                        │
│  GPS + 傳感器 (geolocator/sensors_plus) ─→ Position      │
│  語音輸入 (speech_to_text) ─→ Destination                │
├──────────────────────────────────────────────────────────┤
│        ★ 純 Dart core（不 import package:flutter）        │
│  RouteProvider  ──→ RouteNode[]        （宏觀節點序列）   │
│  NodeMatcher    ──→ NodeMatch           （節點確認/偏離）  │
│  DecisionEngine ──→ Instruction         （規則狀態機）     │
│  AnnounceQueue  ──→ 播報優先級仲裁                        │
├──────────────────────────────────────────────────────────┤
│  TTS 輸出 (flutter_tts, yue-HK)                          │
└──────────────────────────────────────────────────────────┘
              ↕ MethodChannel（僅幀與結構化結果）
┌──────────── Android 原生 (Kotlin) ────────────────────────┐
│  TFLite Interpreter + NNAPI  → 主檢測器 (16 類)           │
│  TFLite Interpreter + NNAPI  → logo 分類器 (11–16 類)     │
│  ML Kit Text Recognition     → 文字識別（招牌/指示牌）     │
└──────────────────────────────────────────────────────────┘
```

### 3.1 為什麼推理走 Kotlin 而不是純 Dart

**不使用 `tflite_flutter` 做推理。** 該社區包的 INT8 與 NNAPI 委派支持不完整，性能拿不到最優；`google_mlkit_text_recognition` 相對偏重。正確分工是：

- **Dart 側**只負責業務邏輯與 UI，通過 MethodChannel 請求"這一幀裏有什麼"；
- **Kotlin 側**用官方 TFLite Interpreter + NNAPI 和 ML Kit 原生庫完成推理，返回 JSON。

這條邊界帶來一個決定性收益：

```
抽象接口（Dart）
  abstract class VisionSource {
    Future<FrameResult> infer(Uint8List jpeg);
  }
  真機實現：PlatformVisionSource   → MethodChannel → Kotlin
  測試實現：ReplayVisionSource     → 讀錄製的 JSON 日誌
```

**M4 階段調規則時，面對的是回放日誌而不是手機**——改一條規則不到一秒即可驗證。

### 3.2 Flutter 的已知代價

- 平台通道額外開發量約 **2–3 天**（幀傳輸格式、異步背壓）；
- 界面中文須打包 Noto Sans CJK 子集，否則真機顯示方塊；
- iOS 側 ML Kit / 粵語 TTS 不做驗證，畢設只交 Android；iOS 列為產品版目標。

### 3.3 分層職責與替換點

| 層 | 職責 | 替換時不影響 |
|---|---|---|
| `RouteProvider` | 產出 `RouteNode[]` | DecisionEngine（**API 可插拔，這是 M0 不做導航卻能開工的前提**） |
| `VisionSource` | 幀 → `Detection[] + OcrResult[]` | 決策層 |
| `NodeMatcher` | 位置 + 檢測 → 節點確認/偏離判定 | UI |
| `DecisionEngine` | 純函數：`(state, perception) → Instruction` | 全部實現細節 |
| `AnnounceQueue` | 播報優先級仲裁與去重 | TTS 引擎 |

## 5. 店鋪識別：兩段式架構（已批准）

### 5.1 核心認識

**圖形 logo 不是通用 OCR 的問題，是閉集分類的問題。** 金色拱門、7-Eleven 橙綠條、屈臣氏字母標——對 OCR 是無字符可讀的噪聲，對專門學過它的分類器卻是**極其穩定、極低維度的模式**。

**已撤回的設計：** "讓用户語音確認是否到達某店"作為兜底方案。該方案把識別責任轉移給一個恰恰無法執行此判斷的用户，等同未實現。識別必須由系統完成。

### 5.2 架構

```
YOLOv8n 主檢測器（16 類）
   └─ 輸出「店鋪門面」框
          ↓ 裁剪該區域 (224×224)
   YOLOv8n-cls 分類器（11–16 類 = 10–15 店鋪 + unknown）
          ↓
   store_id → 粵語店名 → 播報「已到達麥當勞」
```

**為什麼不把 logo 塞進主檢測器：** 加 12 個 logo 會讓類別數從 16 漲到 28，每一類樣本被攤薄，**主檢測器精度全線下降**，辛苦湊出的天橋入口召回率會跟着掉。兩段式的收益：

| 優勢 | 説明 |
|---|---|
| 解耦 | 新增店鋪只需重訓分類器（數分鐘），主檢測器完全不動 |
| 獨立評測 | 分類器準確率單獨成表，論文裏是乾淨的一節 |
| 體積小 | INT8 約 3–4 MB，推理 10–20 ms |
| 複用 | 「店鋪門面」框可掛接任何後續識別器 |

**雙通道冗餘：** 有文字招牌（"麥當勞"）時，OCR 與分類器可交叉確認；純圖形 logo（拱門）時，分類器是唯一通道——而**純圖形恰是分類器最擅長的輸入**。此冗餘呼應項目"雙通道交叉驗證"主線，是論文可展開的一筆。

### 5.3 店鋪選擇原則

**只訓演示路線上真正需要的店，10–15 家**，按功能分為三類：

| 作用 | 數量 | 説明 |
|---|---|---|
| 目標店 | 1–2 | 演示終點（如麥當勞） |
| 定位錨點 | 6–10 | 沿途用於重置當前位置 |
| `unknown` | 1 | 見 §5.4，非目標店鋪樣本 |

每多訓一家店成本約 40–100 張圖 + 1 小時。訓 50 家店收益遞減極快，且全部會變成誤檢來源。

### 5.4 `unknown` 類是生死線

**分類器只會輸出"最像的那一個"**——只訓 12 家店，它看到第 13 家店也會硬説成其中一家。對視障用户，"把茶餐廳説成麥當勞"比"什麼都沒識別到"危險得多。

| 對策 | 參數 |
|---|---|
| `unknown` 類樣本 | 300–500 張非目標店鋪門面 + 其他品牌 logo（就在彩明商場內拍攝） |
| 推理置信度閾值 | 0.75–0.8，低於閾值一律輸出 `unknown` → 播報「呢間唔係目標店鋪」 |
| 單獨評測指標 | **誤報率**（把 known 説成 unknown 之外的方向）——該數字比準確率更重要 |

### 5.5 數據來源（關鍵：禁止只使用官方矢量 logo）

**只下載官網 PNG 訓練是本環節最典型的失敗模式**——模型會完美識別乾淨矢量圖，然後在真實商場裏被反光、透視、部分遮擋全部打敗。

| 來源 | 數量/店 | 用途 |
|---|---|---|
| 官方 logo / Wikipedia | 1–5 張 | 提供"標準形態"先驗 |
| **實地自拍店招** | **40–80 張** | **主力** |
| 網絡圖片 | 0–30 張 | 補充；**須註明來源，注意版權與隱私** |

**實地拍攝覆蓋要求（比數量更重要）：** 3 種距離（遠/中/近）× 3 種角度（正面/左斜/右斜）× 2 種光照（順光/逆光）。

### 5.6 誤檢來源與規則層對策

**麥當勞 logo 在香港隨處可見**——外賣箱、廣告海報、路人手上的紙袋、貨架包裝。模型看到一個拱門就播報"已到達麥當勞"，會造成嚴重誤導。

| 規則 | 作用 | 可單測 |
|---|---|---|
| 空間綁定：logo 框須落在「店鋪門面」框內 | 排除海報/包裝袋/衣物上的 logo | ✅ |
| 時序確認：連續 ≥3 幀識別為同一店 | 排除路過一眼的瞬時誤檢 | ✅ |
| 距離下界：logo 框高 > 畫面高 15% | 排除遠處招牌 | ✅ |
| 運動一致性：logo 在連續幀中快速橫向移動 → 疑似移動物體 | 排除外賣箱 | ✅ |

四條規則均寫入決策層，**每條都是可單測的純函數**，構成論文"系統驗證"章節素材。

### 5.7 成本

| 環節 | 工作量 |
|---|---|
| 實地拍攝 10–15 家店 + 500 張 unknown | 4–5 小時（與天橋採集同次出行完成） |
| 人工篩選與裁剪 | 3–4 小時 |
| 訓練 + 調參 + 評測 | 3–4 小時 |
| **合計** | **約 11–13 小時** |

**執行策略：先做 5 店鋪試點**（含麥當勞 + unknown），跑通全流程後再擴到 15 家，避免一次性投入後才發現拍攝角度不對。**兩條流水線並行，主檢測器訓練進度不受影響。**

## 6. 數據流水線（已批准）

### 6.1 核心修正：不使用 YOLO-World 做零樣本全量預標

**原文檔方案的缺陷：** YOLO-World 對"天橋入口""觸覺引路帶"這類香港特有類別零樣本召回率很低。漏檢後人工補框比從零畫更慢——因為標註者還需判斷"這是漏檢還是本來就沒有"。

**改為自舉（bootstrap）流程：**

```
第 1 步  人工精標 500 張黃金集
           ├─ 200 張凍結為 golden_baseline（論文對照基準，永不參與訓練）
           └─ 300 張覆蓋全部類別，作為自舉種子
第 2 步  訓 v0 模型（300 張種子 + 公開數據）
第 3 步  v0 + SAM 對剩餘 2,000–2,500 張做半自動預標
第 4 步  LocateAnything-3B 裁剪驗證複核（IoU 閾值放寬到 0.5）
第 5 步  爭議樣本分流至 X-AnyLabeling，人工僅 Accept/Reject
第 6 步  數據集質量報告（類別分佈 / 框尺寸 / 長寬比 / 極小框 / 空標籤）
```

### 6.2 三個必須現在就做對的工程決定

**決定一：採集方式必須匹配 Demo 畫面。**

手機"拍照片"存全傳感器畫幅，而 CameraX 預覽流通常是**裁剪過**的（16:9，FOV 不同）。用照片訓練、用預覽流推理會產生分佈偏移，真機精度顯著下降。

> **對策：採集時視頻與照片同時錄製，訓練集以視頻抽幀（每 0.5 s 一幀 + 拉普拉斯模糊過濾）為主，照片僅用於補充稀有類別。**

**決定二：數據集劃分必須按來源分組，防止泄漏。**

同一段視頻抽出的相鄰幀高度相似，若隨機劃分，訓練集與驗證集會包含近乎相同的圖像，**指標虛高 10+ 個百分點**。

> **對策：以"來源文件夾"為分組鍵做 GroupShuffleSplit，且按類別分層（保證稀有類在 val/test 中有代表）。**

**決定三：標籤質量檢查必須先於訓練。**

標註錯誤在訓練時不會報錯，只會讓 mAP 莫名偏低，然後耗費數日懷疑模型。

> **對策：`check_labels.py` 產出類別分佈、框尺寸/長寬比直方圖、越界框、空標籤、極小框（<4 px）報告，作為訓練前置門禁。**

**決定四（實測發現，必須遵守）：標籤必須鏡像圖像的目錄結構。**

Ultralytics 的 `img2label_paths()` 把路徑中的 `\images\` **替換**為 `\labels\`，**保留其餘層級**：

```
data/dataset/images/<source_folder>/<name>.jpg
data/dataset/labels/<source_folder>/<name>.txt     ← 必須鏡像
```

**若把標籤扁平放在 `labels/` 根下，全部標籤都會被判定為"找不到"**，訓練與評測的實例數變成 0，指標全為 0 且不報錯。**這是實測中真實踩到的坑，代價是數輪排查。**

推論（同樣必須遵守）：
- `manifest.csv` 必須記錄**相對 `images/` 的路徑**（含子目錄），不能只記文件名——否則不同來源的同名幀（多機位 `IMG_0001.jpg`）會互相覆蓋標籤，且分組泄漏校驗失效。
- 劃分清單（`train.txt` 等）必須寫**絕對原生路徑**：Ultralytics 從 CWD 解析相對路徑，且 `img2label_paths()` 在 Windows 上用 `os.sep` 匹配反斜槓，正斜槓路徑同樣無法匹配。

## 7. 模型與端側部署

| 項 | 決定 |
|---|---|
| 主檢測器 | YOLOv8n（備選 YOLOv10n / YOLOv8s，若召回率不達標則升級） |
| logo 分類器 | YOLOv8n-cls（MobileNet 級別），輸入 224×224 |
| 訓練 | 100 epochs，Mosaic / HSV / 旋轉；**天橋類樣本加權提升召回率** |
| 損失權重 | `cls=0.7`，`box=7.5` |
| 導出 | ONNX → TFLite INT8，**須用黃金集複測量化後精度，損失 >1.5% 則回退 FP16** |
| 真機目標 | 平均 FPS ≥ 8，單幀延遲 P95 < 150 ms |
| 輸入尺寸 | 640×640（若真機延遲超標，回退 416 或抽幀推理） |

**不部署端側 VLM。** 場景理解由 ML Kit OCR + 規則承擔；VLM（LocateAnything-3B）僅出現在 PC 端標註流水線中。依據：3B 量化模型在畢設硬件上無法達到實時性，且會嚴重消耗內存與電量。

**已核實的外部模型：** [nvidia/LocateAnything-3B](https://huggingface.co/nvidia/LocateAnything-3B) 真實存在，用於標註流水線的裁剪驗證。

## 8. 決策引擎設計

### 8.1 播報優先級

```
障礙物警告 > 路線糾偏 > 節點確認 > 常規引導
```

### 8.2 核心規則（示例）

```dart
// 障礙物：即時警告
if (d.obstacle && d.distanceM < 3.0) {
  return Warn('前方有障礙物，請向左繞行');
}

// 交叉校驗：導航説"該上天橋" + 視覺看到入口 → 確認走對
if (routeCmd == RouteCmd.upFootbridge && d.has(Labels.footbridgeEntrance)) {
  return Guide('前方係天橋入口，請行右邊嘅斜道');
}

// 無障礙繞行：看到樓梯但無替代設施 → 提示尋找
if (routeCmd == RouteCmd.upFootbridge &&
    d.has(Labels.stairs) && !d.has(Labels.ramp) && !d.has(Labels.elevator)) {
  return Correct('前方係樓梯，請揾升降機或者斜道');
}

// 垂直設施不確定：多幀仲裁
if (verticalFacilityUncertain(history, windowSize: 5)) {
  return Caution('前方有向上／向下嘅通道，請小心，我唔確定係樓梯定係扶手電梯');
}
```

### 8.3 時序仲裁原則

**決策層不依賴單幀判斷。** 連續 3–5 幀中只要出現一次高置信度"扶梯"即確認；全部低置信度則播報不確定提示。**純模型做不到的，靠時序 + 規則補上——這是"視覺 + 規則"架構的方法論價值，也是論文的實質貢獻點。**

### 8.4 可測試性要求

每條規則的觸發條件必須寫成可量化的測試用例：輸入一段合成的檢測序列 → 期望輸出特定 `Instruction`。**規則有效性由單測覆蓋，而非"上街試了幾次感覺還行"。**

## 14. 受限執行環境適配（實測）

在受文件沙箱約束的執行環境中（例如 AI 代理會話），有三處必須適配，否則流水線無法運行：

| 衝突 | 現象 | 處理 |
|---|---|---|
| Ultralytics 配置目錄 | `PermissionError: [WinError 5] ...\AppData\Roaming\Ultralytics` | 設 `YOLO_CONFIG_DIR` 指向工作區內 |
| matplotlib 緩存目錄 | 同類權限錯誤 | 設 `MPLCONFIGDIR` 指向工作區內 |
| **命名管道不可用** | `ThreadPool` / DataLoader 多進程拋 `PermissionError: [WinError 5]`（`CreateFile` 命名管道） | ① DataLoader 用 `workers=0`；② `scripts/env_setup.py` 把 Ultralytics 的 `cache_labels` 替換為順序實現 |
| TFLite 導出 | 進程掛起且無輸出 | **無法在此類環境中完成**，須在普通終端執行 `scripts/export_model.py` |

**關於 `cache_labels` 補丁的實現約束（實測得出）：**
- `cache_labels` 定義在 `ultralytics.data.dataset.YOLODataset`（非基類）。
- `verify_image_label(args: tuple) -> list` 接受**單個元組**，返回 **10 元素**（成功與失敗路徑均為 10 元素），失敗時 `result[0]` 為 `None`。
- 緩存字典必須含 `labels / hash / results / msgs / version`，應調用官方 `save_dataset_cache_file`，否則 `get_labels()` 拋 `KeyError('version')`。
- `"im_file"` 必須是 **str**（下游 `load_image()` 會調用 `.endswith(...)`），傳 `Path` 會拋 `AttributeError`。

**重要提示：** 上述適配只是**為了能在受限環境中驗證流水線**。在普通終端中運行時，`workers` 應恢復為 4–8 以獲得正常訓練速度，且不需要 `cache_labels` 補丁（`env_setup.py` 會先探測 `ThreadPool` 是否可用，僅在不可用時才打補丁）。
