# 领路通（PathGuide HK）毕设版设计文档

**日期：** 2026-09-15
**状态：** 已批准（brainstorming 阶段完成）
**范围：** 毕业设计版本 —— 端侧视觉感知 + 节点确认式语音引导原型
**非范围：** 导航 API 集成、决策状态机、室内路网、BLE 定位、端侧 VLM（见 §10 与产品版路线图）

---

## 1. 项目定位

一个运行于 Android 手机上的香港视障人士寻路辅助原型。核心命题不是"告诉用户往哪走"，而是**"帮用户确认自己走在正确的路上"**——导航 API 给出宏观方向，摄像头视觉模型确认微观环境，两者交叉验证后生成语音引导。

**毕设版聚焦其中风险最高、最需要提前验证的一环：视觉感知层能否在真机上实时、可靠地认出香港特有的通行设施。**

---

## 2. 演示区域与路线分工

选定区域：**调景岭站 → 地面行人路 → 彩明苑天桥系统 → 彩明商场**，范围控制在 300 × 300 米内。

| | 路线 A（调景岭） | 路线 B（中环） |
|---|---|---|
| 路径 | 调景岭站 → 地面行人路 → 彩明苑天桥 → 彩明商场 | 中环站 A 出口 → 地面街道 → 中环行人天桥 → IFC |
| 官方室内数据 | ✅ 覆盖（地政总署 2025-10 起扩展至全港铁站） | ✅ 站内覆盖，❌ IFC 商场内无覆盖 |
| 天桥密度 | 中（1 段，紧邻商场） | 高 |
| 采集难度 | 低（距离短、人流少） | 中（人流密集、隐私敏感） |
| **角色** | **主实验区**：数据、训练、指标、Demo 全在此 | **泛化验证集**：仅采集 + 评测，**不重训模型** |

**设计依据：** 路线 B 的价值不是"再做一遍"，而是提供**跨区域泛化能力的证据**——"在 A 训练，在 B 上召回率仍达 X%"。若仅在 A 采集评测，无法排除对单一桥梁的过拟合。B 的增量成本仅为半天采集 + 一次评测。

**待实地核实（阻塞节点图定稿）：** 彩明商场与调景岭站之间是"天桥直达"还是"需经地面行人路"。前者只有一个室内外切换点，后者会多出一段室外街景段。**两种情形都不影响本设计的任何决策**，只影响节点图。

**政府数据依据：**
- 地政总署三维室内地图已扩展至所有港铁站：[政府新闻公报](https://www.info.gov.hk/gia/general/202510/09/P2025100900161.htm)
- 彩明商场为领展旗下社区商场：[维基百科](https://zh.wikipedia.org/wiki/%E5%BD%A9%E6%98%8E%E5%95%86%E5%A0%B4)

## 3. 系统总体架构

核心工程约束：**决策与感知的业务逻辑必须能脱离真机单测。** 单人 + 16 周 + 需写论文，若每次调规则都要拿手机出门实测，项目必然延期。

```
┌────────────────── Flutter App (Dart) ──────────────────┐
│  相机 (camera/CameraX) ─→ JPEG 帧                        │
│  GPS + 传感器 (geolocator/sensors_plus) ─→ Position      │
│  语音输入 (speech_to_text) ─→ Destination                │
├──────────────────────────────────────────────────────────┤
│        ★ 纯 Dart core（不 import package:flutter）        │
│  RouteProvider  ──→ RouteNode[]        （宏观节点序列）   │
│  NodeMatcher    ──→ NodeMatch           （节点确认/偏离）  │
│  DecisionEngine ──→ Instruction         （规则状态机）     │
│  AnnounceQueue  ──→ 播报优先级仲裁                        │
├──────────────────────────────────────────────────────────┤
│  TTS 输出 (flutter_tts, yue-HK)                          │
└──────────────────────────────────────────────────────────┘
              ↕ MethodChannel（仅帧与结构化结果）
┌──────────── Android 原生 (Kotlin) ────────────────────────┐
│  TFLite Interpreter + NNAPI  → 主检测器 (16 类)           │
│  TFLite Interpreter + NNAPI  → logo 分类器 (11–16 类)     │
│  ML Kit Text Recognition     → 文字识别（招牌/指示牌）     │
└──────────────────────────────────────────────────────────┘
```

### 3.1 为什么推理走 Kotlin 而不是纯 Dart

**不使用 `tflite_flutter` 做推理。** 该社区包的 INT8 与 NNAPI 委派支持不完整，性能拿不到最优；`google_mlkit_text_recognition` 相对偏重。正确分工是：

- **Dart 侧**只负责业务逻辑与 UI，通过 MethodChannel 请求"这一帧里有什么"；
- **Kotlin 侧**用官方 TFLite Interpreter + NNAPI 和 ML Kit 原生库完成推理，返回 JSON。

这条边界带来一个决定性收益：

```
抽象接口（Dart）
  abstract class VisionSource {
    Future<FrameResult> infer(Uint8List jpeg);
  }
  真机实现：PlatformVisionSource   → MethodChannel → Kotlin
  测试实现：ReplayVisionSource     → 读录制的 JSON 日志
```

**M4 阶段调规则时，面对的是回放日志而不是手机**——改一条规则不到一秒即可验证。

### 3.2 Flutter 的已知代价

- 平台通道额外开发量约 **2–3 天**（帧传输格式、异步背压）；
- 界面中文须打包 Noto Sans CJK 子集，否则真机显示方块；
- iOS 侧 ML Kit / 粤语 TTS 不做验证，毕设只交 Android；iOS 列为产品版目标。

### 3.3 分层职责与替换点

| 层 | 职责 | 替换时不影响 |
|---|---|---|
| `RouteProvider` | 产出 `RouteNode[]` | DecisionEngine（**API 可插拔，这是 M0 不做导航却能开工的前提**） |
| `VisionSource` | 帧 → `Detection[] + OcrResult[]` | 决策层 |
| `NodeMatcher` | 位置 + 检测 → 节点确认/偏离判定 | UI |
| `DecisionEngine` | 纯函数：`(state, perception) → Instruction` | 全部实现细节 |
| `AnnounceQueue` | 播报优先级仲裁与去重 | TTS 引擎 |

## 4. 类别表（已批准）

### 4.1 主检测器 —— 16 类

| 组 | 类别 | 角色 | 优先级 |
|---|---|---|---|
| **天桥专项 (6)** | 天桥入口 | ★ 论文特色类别 | P0 |
| | 楼梯 | 与扶梯需区分 | P0 |
| | 户外扶梯 | 天桥端 | P0 |
| | 升降机 | 无障碍绕行依赖 | P0 |
| | 坡道 | 无障碍绕行依赖 | P0 |
| | 天桥栏杆 | 边界感知 | P1 |
| **障碍物 (4)** | 行人 | 移动障碍 | P0 |
| | 路边障碍（围栏/立柱/杂物） | 安全底线 | P0 |
| | 台阶 | 安全底线 | P0 |
| | 玻璃门 | 香港商场高风险（无框玻璃） | P0 |
| **导航辅助 (2)** | 盲道 / 触觉引路带 | 香港特有 | P1 |
| | 斑马线 | 过街点 | P1 |
| **室内 (3)** | 店铺门面 | 供 logo 分类器裁剪 | P0 |
| | 商场扶梯 | 室内垂直移动锚点 | P0 |
| | 商场玻璃门 | 出入口确认 | P0 |
| **训练专用 (1)** | `ambiguous_vertical` | **仅用于训练，永不播报** | P0 |

**关于 `ambiguous_vertical`：** 正对扶梯口时，画面里只有"一片阶梯向上/向下延伸"，与楼梯难以区分——而这**恰恰是视障用户最常处的姿态**（他不会侧身看扶梯）。让模型学会说"我不确定"，比让它猜更安全。对视障用户，错误引导的代价远高于"请稍等，让我确认"。

### 4.2 明确合并与删除的决定

| 决定 | 理由 |
|---|---|
| **"上行扶梯/下行扶梯"合并为一类** | 静态图上方向不可靠（换视角即变），且运行时不必要——两个方向都播报"请小心，扶手电梯" |
| 车辆/自行车/红绿灯/斑马线以外交通元素**不标注** | YOLOv8n 的 COCO 预训练权重本就覆盖，可作为「零标注类别」按需直接推理 |
| 施工围栏**不标注** | 香港变化快，标了易过时；用 OCR 读围栏文字更可靠 |
| 触摸地图/楼层指示牌**不做检测类** | 交给 OCR，不是几何物体识别问题 |

### 4.3 类别表规模与精度的取舍（已决策依据）

| 维度 | 16 类（本方案） | 22–28 类（原文档） |
|---|---|---|
| 最少图像量 | 2,500–3,000 张 | 4,500–6,000 张 |
| 标注总投入 | 约 20 小时 | 约 40 小时 |
| 单类平均样本 | ~200 张（充足） | 被摊薄 |
| 预期 mAP@0.5（YOLOv8n） | 0.60–0.70 | 0.45–0.55 |
| P0 类别召回率 | 80–90% 可达标 | 60–75%，**可能不达标** |
| 真机推理延迟 | 差异可忽略（类别数对速度影响很小） | 同左 |

**结论：成本差距全在标注与采集，收益差距在精度。** 毕设硬指标是**按类计算的召回率**（天桥入口 > 70%、障碍物 > 70%），类别越多越难达标。类别表更长不会让模型更全面，只会让每一类都变弱。

**增量扩展路径：** M2 先按 16 类训出达标模型；若 M4 有富余时间，以该模型为起点**迁移学习增量加类**，扩到 20+ 类。风险可控，而非一开始就压在 40 小时标注上。

## 5. 店铺识别：两段式架构（已批准）

### 5.1 核心认识

**图形 logo 不是通用 OCR 的问题，是闭集分类的问题。** 金色拱门、7-Eleven 橙绿条、屈臣氏字母标——对 OCR 是无字符可读的噪声，对专门学过它的分类器却是**极其稳定、极低维度的模式**。

**已撤回的设计：** "让用户语音确认是否到达某店"作为兜底方案。该方案把识别责任转移给一个恰恰无法执行此判断的用户，等同未实现。识别必须由系统完成。

### 5.2 架构

```
YOLOv8n 主检测器（16 类）
   └─ 输出「店铺门面」框
          ↓ 裁剪该区域 (224×224)
   YOLOv8n-cls 分类器（11–16 类 = 10–15 店铺 + unknown）
          ↓
   store_id → 粤语店名 → 播报「已到達麥當勞」
```

**为什么不把 logo 塞进主检测器：** 加 12 个 logo 会让类别数从 16 涨到 28，每一类样本被摊薄，**主检测器精度全线下降**，辛苦凑出的天桥入口召回率会跟着掉。两段式的收益：

| 优势 | 说明 |
|---|---|
| 解耦 | 新增店铺只需重训分类器（数分钟），主检测器完全不动 |
| 独立评测 | 分类器准确率单独成表，论文里是干净的一节 |
| 体积小 | INT8 约 3–4 MB，推理 10–20 ms |
| 复用 | 「店铺门面」框可挂接任何后续识别器 |

**双通道冗余：** 有文字招牌（"麥當勞"）时，OCR 与分类器可交叉确认；纯图形 logo（拱门）时，分类器是唯一通道——而**纯图形恰是分类器最擅长的输入**。此冗余呼应项目"双通道交叉验证"主线，是论文可展开的一笔。

### 5.3 店铺选择原则

**只训演示路线上真正需要的店，10–15 家**，按功能分为三类：

| 作用 | 数量 | 说明 |
|---|---|---|
| 目标店 | 1–2 | 演示终点（如麦当劳） |
| 定位锚点 | 6–10 | 沿途用于重置当前位置 |
| `unknown` | 1 | 见 §5.4，非目标店铺样本 |

每多训一家店成本约 40–100 张图 + 1 小时。训 50 家店收益递减极快，且全部会变成误检来源。

### 5.4 `unknown` 类是生死线

**分类器只会输出"最像的那一个"**——只训 12 家店，它看到第 13 家店也会硬说成其中一家。对视障用户，"把茶餐厅说成麦当劳"比"什么都没识别到"危险得多。

| 对策 | 参数 |
|---|---|
| `unknown` 类样本 | 300–500 张非目标店铺门面 + 其他品牌 logo（就在彩明商场内拍摄） |
| 推理置信度阈值 | 0.75–0.8，低于阈值一律输出 `unknown` → 播报「呢間唔係目標店鋪」 |
| 单独评测指标 | **误报率**（把 known 说成 unknown 之外的方向）——该数字比准确率更重要 |

### 5.5 数据来源（关键：禁止只使用官方矢量 logo）

**只下载官网 PNG 训练是本环节最典型的失败模式**——模型会完美识别干净矢量图，然后在真实商场里被反光、透视、部分遮挡全部打败。

| 来源 | 数量/店 | 用途 |
|---|---|---|
| 官方 logo / Wikipedia | 1–5 张 | 提供"标准形态"先验 |
| **实地自拍店招** | **40–80 张** | **主力** |
| 网络图片 | 0–30 张 | 补充；**须注明来源，注意版权与隐私** |

**实地拍摄覆盖要求（比数量更重要）：** 3 种距离（远/中/近）× 3 种角度（正面/左斜/右斜）× 2 种光照（顺光/逆光）。

### 5.6 误检来源与规则层对策

**麦当劳 logo 在香港随处可见**——外卖箱、广告海报、路人手上的纸袋、货架包装。模型看到一个拱门就播报"已到达麦当劳"，会造成严重误导。

| 规则 | 作用 | 可单测 |
|---|---|---|
| 空间绑定：logo 框须落在「店铺门面」框内 | 排除海报/包装袋/衣物上的 logo | ✅ |
| 时序确认：连续 ≥3 帧识别为同一店 | 排除路过一眼的瞬时误检 | ✅ |
| 距离下界：logo 框高 > 画面高 15% | 排除远处招牌 | ✅ |
| 运动一致性：logo 在连续帧中快速横向移动 → 疑似移动物体 | 排除外卖箱 | ✅ |

四条规则均写入决策层，**每条都是可单测的纯函数**，构成论文"系统验证"章节素材。

### 5.7 成本

| 环节 | 工作量 |
|---|---|
| 实地拍摄 10–15 家店 + 500 张 unknown | 4–5 小时（与天桥采集同次出行完成） |
| 人工筛选与裁剪 | 3–4 小时 |
| 训练 + 调参 + 评测 | 3–4 小时 |
| **合计** | **约 11–13 小时** |

**执行策略：先做 5 店铺试点**（含麦当劳 + unknown），跑通全流程后再扩到 15 家，避免一次性投入后才发现拍摄角度不对。**两条流水线并行，主检测器训练进度不受影响。**

## 6. 数据流水线（已批准）

### 6.1 核心修正：不使用 YOLO-World 做零样本全量预标

**原文档方案的缺陷：** YOLO-World 对"天桥入口""触觉引路带"这类香港特有类别零样本召回率很低。漏检后人工补框比从零画更慢——因为标注者还需判断"这是漏检还是本来就没有"。

**改为自举（bootstrap）流程：**

```
第 1 步  人工精标 500 张黄金集
           ├─ 200 张冻结为 golden_baseline（论文对照基准，永不参与训练）
           └─ 300 张覆盖全部类别，作为自举种子
第 2 步  训 v0 模型（300 张种子 + 公开数据）
第 3 步  v0 + SAM 对剩余 2,000–2,500 张做半自动预标
第 4 步  LocateAnything-3B 裁剪验证复核（IoU 阈值放宽到 0.5）
第 5 步  争议样本分流至 X-AnyLabeling，人工仅 Accept/Reject
第 6 步  数据集质量报告（类别分布 / 框尺寸 / 长宽比 / 极小框 / 空标签）
```

### 6.2 三个必须现在就做对的工程决定

**决定一：采集方式必须匹配 Demo 画面。**

手机"拍照片"存全传感器画幅，而 CameraX 预览流通常是**裁剪过**的（16:9，FOV 不同）。用照片训练、用预览流推理会产生分布偏移，真机精度显著下降。

> **对策：采集时视频与照片同时录制，训练集以视频抽帧（每 0.5 s 一帧 + 拉普拉斯模糊过滤）为主，照片仅用于补充稀有类别。**

**决定二：数据集划分必须按来源分组，防止泄漏。**

同一段视频抽出的相邻帧高度相似，若随机划分，训练集与验证集会包含近乎相同的图像，**指标虚高 10+ 个百分点**。

> **对策：以"来源文件夹"为分组键做 GroupShuffleSplit，且按类别分层（保证稀有类在 val/test 中有代表）。**

**决定三：标签质量检查必须先于训练。**

标注错误在训练时不会报错，只会让 mAP 莫名偏低，然后耗费数日怀疑模型。

> **对策：`check_labels.py` 产出类别分布、框尺寸/长宽比直方图、越界框、空标签、极小框（<4 px）报告，作为训练前置门禁。**

### 6.4 数据量目标

| 类别组 | 目标图像量 |

## 7. 模型与端侧部署

| 项 | 决定 |
|---|---|
| 主检测器 | YOLOv8n（备选 YOLOv10n / YOLOv8s，若召回率不达标则升级） |
| logo 分类器 | YOLOv8n-cls（MobileNet 级别），输入 224×224 |
| 训练 | 100 epochs，Mosaic / HSV / 旋转；**天桥类样本加权提升召回率** |
| 损失权重 | `cls=0.7`，`box=7.5` |
| 导出 | ONNX → TFLite INT8，**须用黄金集复测量化后精度，损失 >1.5% 则回退 FP16** |
| 真机目标 | 平均 FPS ≥ 8，单帧延迟 P95 < 150 ms |
| 输入尺寸 | 640×640（若真机延迟超标，回退 416 或抽帧推理） |

**不部署端侧 VLM。** 场景理解由 ML Kit OCR + 规则承担；VLM（LocateAnything-3B）仅出现在 PC 端标注流水线中。依据：3B 量化模型在毕设硬件上无法达到实时性，且会严重消耗内存与电量。

**已核实的外部模型：** [nvidia/LocateAnything-3B](https://huggingface.co/nvidia/LocateAnything-3B) 真实存在，用于标注流水线的裁剪验证。

## 8. 决策引擎设计

### 8.1 播报优先级

```
障碍物警告 > 路线纠偏 > 节点确认 > 常规引导
```

### 8.2 核心规则（示例）

```dart
// 障碍物：即时警告
if (d.obstacle && d.distanceM < 3.0) {
  return Warn('前方有障礙物，請向左繞行');
}

// 交叉校验：导航说"该上天桥" + 视觉看到入口 → 确认走对
if (routeCmd == RouteCmd.upFootbridge && d.has(Labels.footbridgeEntrance)) {
  return Guide('前方係天橋入口，請行右邊嘅斜道');
}

// 无障碍绕行：看到楼梯但无替代设施 → 提示寻找
if (routeCmd == RouteCmd.upFootbridge &&
    d.has(Labels.stairs) && !d.has(Labels.ramp) && !d.has(Labels.elevator)) {
  return Correct('前方係樓梯，請搵升降機或者斜道');
}

// 垂直设施不确定：多帧仲裁
if (verticalFacilityUncertain(history, windowSize: 5)) {
  return Caution('前方有向上／向下嘅通道，請小心，我唔確定係樓梯定係扶手電梯');
}
```

### 8.3 时序仲裁原则

**决策层不依赖单帧判断。** 连续 3–5 帧中只要出现一次高置信度"扶梯"即确认；全部低置信度则播报不确定提示。**纯模型做不到的，靠时序 + 规则补上——这是"视觉 + 规则"架构的方法论价值，也是论文的实质贡献点。**

### 8.4 可测试性要求

每条规则的触发条件必须写成可量化的测试用例：输入一段合成的检测序列 → 期望输出特定 `Instruction`。**规则有效性由单测覆盖，而非"上街试了几次感觉还行"。**

## 9. 最小可见 Demo（已批准切片）

### 9.1 验收标准

| 项 | 标准 |
|---|---|
| 形态 | Android APK，装入真机，**无需联网** |
| 能看到 | 相机实时画面 + 检测框 + 中文类别标签 + FPS/延迟数字 |
| 能听到 | 命中 P0 类别时粤语播报，2 秒防抖去重 |
| 能演示 | 阈值滑条，现场演示召回/精确率权衡 |
| 能回放 | 支持加载**本地视频文件**跑推理（答辩时不受现场光线/人流影响） |
| **明确不做** | 导航 API、路线规划、决策状态机、语音输入、室内地图 |

### 9.2 为什么这是正确的最小切片

项目最大技术风险是"模型到底能否在手机上实时认出天桥入口与障碍物"。**该风险不解除，后续所有导航逻辑都建在沙子上。** 5 周内拿到此 Demo，即拿到整个毕设的可行性证据。

### 9.3 Demo 文件结构

| 文件 | 职责 |
|---|---|
| `lib/main.dart` | 应用入口 |
| `lib/vision/vision_source.dart` | `VisionSource` 抽象接口 |
| `lib/vision/platform_vision_source.dart` | MethodChannel → Kotlin TFLite + ML Kit |
| `lib/vision/replay_vision_source.dart` | 本地视频回放 |
| `lib/vision/labels.dart` | 16 类中文名 + 播报话术映射 |
| `lib/overlay/box_painter.dart` | CustomPainter 绘制框与标签 |
| `lib/tts/announcer.dart` | 粤语播报 + 2 秒去重防抖 |
| `lib/ui/demo_page.dart` | 相机预览 + 叠加层 + 阈值滑条 + 性能面板 |

**关键实现点：**
- 推理在 `Isolate` 中执行，主线程只画框，否则预览卡顿；
- **抽帧推理**：每 2–3 帧推理一次，观感几乎无差别，但发热与耗电显著下降；
- 相机分辨率设为 640×480 或 1280×720，与训练输入对齐；
- 打包 Noto Sans CJK 子集；确认 `flutter_tts` 的 `yue-HK` 语音包可用。

## 11. 风险登记

| 风险 | 影响 | 缓解 | 触发条件 |
|---|---|---|---|
| 天桥入口样本不足 | 特色类别不达标 | **第 1 周即拍满 800 张**，不等后期 | 第 3 周样本 < 500 张 |
