# 第三方数据的实测收益：**没有**（并且我一度误读了结果）

**日期：** 2026-10-02
**目标：** 用 Roboflow 的 People Detection v1（7261 张）补 `pedestrian` 与
`bicycle` 的训练数据，看能不能在香港验证集上换来可测量的提升。
**结论：**
1. **没有可测量的收益。** 在**播报门槛 0.70**（产品实际运行的那个阈值）处，
   两版模型几乎相同。
2. **我一度得出相反的结论，原因是误读了 mAP 报告口径** —— 值得单独记一节。
3. `bicycle` 在播报门槛处**两版都是 P=0、R=0**（val 仅 2 个实例），
   `bicycle` 的问题不在训练数据量，在**验证数据本身**。
4. 附带查出一个**之前写错的事实**：本机**有 CUDA GPU**，不是「无 GPU」。

---

## 1. 数据规模：本来很可观

| 类别 | 该数据集提供 | 原训练集 | 倍数 |
|---|---:|---:|---|
| pedestrian | 29,857 框 | 2,218 框 | 13.5× |
| bicycle | 2,038 框 | 15 框 | **136×** |

合并后的 `data/dataset_poc4`：**5697 图**（train 5594 / val 103），
pedestrian 32,105 / bicycle 2,053 / bin 88 框。
Roboflow 的 5178 张走 `--add-train-only`，**全在 train**，
val 的 103 张 **100% 是香港实拍**。

## 2. 公平对比：同一个验证集

`runs/pg_poc3` 与 `runs/pg_poc4` 各自的 val 划分不同，直接比各自的 mAP 是**不可比**的
（差异里混了「验证集变了」）。而两者的本地索引顺序一致
（0=pedestrian, 1=bicycle, 2=bin），所以让**两个模型都跑 poc4 的 val**
（`scripts/compare_models.py`、`scripts/compare_at_threshold.py`）。

### 2.1 按 mAP（默认报告口径）

| 类别 | poc3 | poc4 |
|---|---|---|
| pedestrian | P 0.756 / R 0.719 / mAP50 **0.796** | P 0.469 / R 0.893 / mAP50 **0.817** |
| bicycle | P 0.841 / R 0.500 / mAP50 0.496 | P 0.752 / R 0.500 / mAP50 0.507 |
| bin | P 0.688 / R 1.000 / mAP50 0.958 | P 0.690 / R 0.938 / mAP50 0.964 |

看这张表很容易得出「行人精确率从 0.756 崩到 0.469」的结论。
**这个结论是错的**，见下一节。

### 2.2 按**产品实际运行的阈值**（决定性的一张表）

产品运行在 `kMinSpeakScore = 0.70`（`app/lib/tts/announcer.dart`）：
低于它画框但不播报。所以真正的问题是「**在 0.70 处**哪个模型更好」。

| 在 conf=0.70 | poc3 | poc4 |
|---|---|---|
| pedestrian P / R | **0.980** / 0.413 | 0.945 / 0.355 |
| bicycle P / R | 0.000 / 0.000 | 0.000 / 0.000 |
| bin P / R | 0.929 / 0.812 | 1.000 / 0.875 |
| **总体 P** | 0.636 | **0.648** |

各阈值下的总体精确率：

| conf | poc3 | poc4 |
|---|---|---|
| 0.30 | 0.5909 | 0.5792 |
| 0.50 | 0.5909 | 0.6148 |
| 0.60 | 0.6227 | 0.6465 |
| **0.70** | **0.6363** | **0.6484** |
| 0.80 | 0.6429 | 0.6667 |
| 0.90 | 0.6667 | 0.6667 |

**结论：两版在同一工作点上等价（差异在 260 个实例的范围内属噪声）。**
13.5× / 136× 的额外数据，在香港验证集上买不到可测量的提升。

## 3. 为什么我一度读错了 —— 这一节比结论本身重要

第一版对比只看了 `ultralytics` 默认报告的 P/R，于是写出
「行人精确率崩塌 0.756 → 0.469」。而**那个 P/R 不在产品运行的阈值上**。

mAP50 是对所有阈值积分的面积；两版模型的面积接近，但**曲线的取值点不同**。
默认口径取了低阈值端，于是 poc4（高召回、低精度的那一端）看起来"崩了"。
一旦把口径固定到产品真正使用的 0.70，差别就消失了。

**教训（本项目要长期用）：比较任何模型指标时，必须写明是在哪个置信度阈值处取的值。**
一个不带阈值的「精确率」，在本项目里没有解释力，因为产品只在一个阈值上运行。

因此新增 `scripts/compare_at_threshold.py`：按一组阈值取 P/R 并把曲线打出来，
而不是只报一个数。

## 4. `bicycle`：问题不在训练数据量

在 conf=0.70 处，**两版模型对 bicycle 都是 P=0.000、R=0.000** ——
即在这 2 个验证实例上，两个模型都没有任何高于 0.70 的检出，
所以**系统根本不会播报单车**。

而 val 只有 **2 个** bicycle 实例（原数据集就 13 帧/15 框）。
2 个实例既算不出指标，也**不足以证伪**——加了 2038 个框有没有用，
用 2 个实例是测不出来的。

所以 `bicycle` 的下一步**不是继续加训练数据**，而是：
1. **补香港实拍的单车径素材**，把 val 撑到有统计意义（至少几十个实例）；
2. 在此之前，bicycle 的任何指标都**不可引用**。

## 5. 决策

| 项 | 决定 | 理由 |
|---|---|---|
| 是否把 `pg_poc4`（含第三方数据）作为发布模型 | **暂不** | 在香港 val 的工作点处无可测量收益；而它带许可负担（仅限研究用途）、训练时间 ×10、且引入域偏移风险 |
| 第三方数据是否保留 | **保留在 `data/dataset_poc4`** | 作为已记录的证据；若将来扩类或做消融仍可用 |
| 验证集 | **维持香港实拍、不含第三方数据** | 本次对比之所以可信，正因为 val 是干净的（`--add-train-only`）。若当初把 Roboflow 混进 val，这次会得出「大胜」的假结论 |

**这个负面结果本身有价值**：它说明在 3 类 POC 上，「通用域大数据」不是瓶颈的解，
瓶颈是 `bicycle`/`scooter` 这类**香港特定素材的验证数据**。

## 6. 附带更正：本机**有** CUDA GPU

`runs/pg_poc4` 的训练横幅显示 `CUDA:0 (NVIDIA GeForce RTX 5070, 12199MiB)`。
实测（`scripts/probe_cuda.py`，不只读 `is_available()`，还实际做矩阵乘）：

| 环境 | torch | CUDA |
|---|---|---|
| `.venv`（训练） | `2.11.0+cu128` | ✅ |
| `.venv-vlm`（GDINO/VLM） | `2.11.0+cu128` | ✅ |
| `.venv-export`（TFLite 导出） | `2.14.0+cpu` | ❌ |

**RTX 5070，11.9 GiB，sm_120，实测 4.44 TFLOP/s**（同规模矩阵乘：CPU 25 ms vs GPU 3.6 ms）。

原先多处文档写「本机无 GPU、CUDA 不可用」，很可能是**只看了 `.venv-export` 就推广到全机**。
`docs/superpowers/plans/2026-09-28-decision-no-ssl-pretraining.md` 已更正并保留了更正记录。
**那条决策的结论不变**（1e8 图像/数千 GPU-小时 与 14 万帧差 4~5 个数量级），
但受影响的成本估算要改：GDINO 的 **11.3 s/图是在 GPU 上测的**
（`gd_detect.py` 用 `.to("cuda")`），8033 张 ≈ **25 GPU-小时**，不是 CPU-小时。
