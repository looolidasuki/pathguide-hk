# 第三方數據的實測收益：**沒有**（並且我一度誤讀了結果）

**日期：** 2026-10-02
**目標：** 用 Roboflow 的 People Detection v1（7261 張）補 `pedestrian` 與
`bicycle` 的訓練數據，看能不能在香港驗證集上換來可測量的提升。
**結論：**
1. **沒有可測量的收益。** 在**播報門檻 0.70**（產品實際運行的那個閾值）處，
   兩版模型幾乎相同。
2. **我一度得出相反的結論，原因是誤讀了 mAP 報告口徑** —— 值得單獨記一節。
3. `bicycle` 在播報門檻處**兩版都是 P=0、R=0**（val 僅 2 個實例），
   `bicycle` 的問題不在訓練數據量，在**驗證數據本身**。
4. 附帶查出一個**之前寫錯的事實**：本機**有 CUDA GPU**，不是「無 GPU」。

---

## 1. 數據規模：本來很可觀

| 類別 | 該數據集提供 | 原訓練集 | 倍數 |
|---|---:|---:|---|
| pedestrian | 29,857 框 | 2,218 框 | 13.5× |
| bicycle | 2,038 框 | 15 框 | **136×** |

合併後的 `data/dataset_poc4`：**5697 圖**（train 5594 / val 103），
pedestrian 32,105 / bicycle 2,053 / bin 88 框。
Roboflow 的 5178 張走 `--add-train-only`，**全在 train**，
val 的 103 張 **100% 是香港實拍**。

## 2. 公平對比：同一個驗證集

`runs/pg_poc3` 與 `runs/pg_poc4` 各自的 val 劃分不同，直接比各自的 mAP 是**不可比**的
（差異裏混了「驗證集變了」）。而兩者的本地索引順序一致
（0=pedestrian, 1=bicycle, 2=bin），所以讓**兩個模型都跑 poc4 的 val**
（`scripts/compare_models.py`、`scripts/compare_at_threshold.py`）。

### 2.0 這個對比比預想的更嚴格：逐類實例數幾乎完全相同

後來逐個數了一下兩份 val 的實例數：

| val | pedestrian | bicycle | bin | 合計 |
|---|---:|---:|---:|---:|
| `dataset_poc3` | 242 | 2 | 19 | 263 |
| `dataset_poc4` | 242 | **2** | 16 | 260 |

**pedestrian（242）與 bicycle（2）在兩份劃分裏完全相同** ——
因為香港實拍那部分數據沒變，而切分是按幀名排序後的確定性 20% 切。
只有 bin 從 19 變 16（bin 組構成變了：44 張裏 13 張的行人/單車幀與主組重合）。

也就是説，pedestrian 的對比**幾乎是對照實驗**（同數據、同實例），
不是兩組不同數據的間接比較。這讓「第三方數據無收益」的結論更硬。

### 2.1 按 mAP（默認報告口徑）

| 類別 | poc3 | poc4 |
|---|---|---|
| pedestrian | P 0.756 / R 0.719 / mAP50 **0.796** | P 0.469 / R 0.893 / mAP50 **0.817** |
| bicycle | P 0.841 / R 0.500 / mAP50 0.496 | P 0.752 / R 0.500 / mAP50 0.507 |
| bin | P 0.688 / R 1.000 / mAP50 0.958 | P 0.690 / R 0.938 / mAP50 0.964 |

看這張表很容易得出「行人精確率從 0.756 崩到 0.469」的結論。
**這個結論是錯的**，見下一節。

### 2.2 按**產品實際運行的閾值**（決定性的一張表）

產品運行在 `kMinSpeakScore = 0.70`（`app/lib/tts/announcer.dart`）：
低於它畫框但不播報。所以真正的問題是「**在 0.70 處**哪個模型更好」。

| 在 conf=0.70 | poc3 | poc4 |
|---|---|---|
| pedestrian P / R | **0.980** / 0.413 | 0.945 / 0.355 |
| bicycle P / R | 0.000 / 0.000 | 0.000 / 0.000 |
| bin P / R | 0.929 / 0.812 | 1.000 / 0.875 |
| **總體 P** | 0.636 | **0.648** |

各閾值下的總體精確率：

| conf | poc3 | poc4 |
|---|---|---|
| 0.30 | 0.5909 | 0.5792 |
| 0.50 | 0.5909 | 0.6148 |
| 0.60 | 0.6227 | 0.6465 |
| **0.70** | **0.6363** | **0.6484** |
| 0.80 | 0.6429 | 0.6667 |
| 0.90 | 0.6667 | 0.6667 |

**結論：兩版在同一工作點上等價（差異在 260 個實例的範圍內屬噪聲）。**
13.5× / 136× 的額外數據，在香港驗證集上買不到可測量的提升。

## 3. 為什麼我一度讀錯了 —— 這一節比結論本身重要

第一版對比只看了 `ultralytics` 默認報告的 P/R，於是寫出
「行人精確率崩塌 0.756 → 0.469」。而**那個 P/R 不在產品運行的閾值上**。

mAP50 是對所有閾值積分的面積；兩版模型的面積接近，但**曲線的取值點不同**。
默認口徑取了低閾值端，於是 poc4（高召回、低精度的那一端）看起來"崩了"。
一旦把口徑固定到產品真正使用的 0.70，差別就消失了。

**教訓（本項目要長期用）：比較任何模型指標時，必須寫明是在哪個置信度閾值處取的值。**
一個不帶閾值的「精確率」，在本項目裏沒有解釋力，因為產品只在一個閾值上運行。

因此新增 `scripts/compare_at_threshold.py`：按一組閾值取 P/R 並把曲線打出來，
而不是隻報一個數。

## 4. `bicycle`：問題不在訓練數據量

在 conf=0.70 處，**兩版模型對 bicycle 都是 P=0.000、R=0.000** ——
即在這 2 個驗證實例上，兩個模型都沒有任何高於 0.70 的檢出，
所以**系統根本不會播報單車**。

而 val 只有 **2 個** bicycle 實例（原數據集就 13 幀/15 框）。
2 個實例既算不出指標，也**不足以證偽**——加了 2038 個框有沒有用，
用 2 個實例是測不出來的。

所以 `bicycle` 的下一步**不是繼續加訓練數據**，而是：
1. **補香港實拍的單車徑素材**，把 val 撐到有統計意義（至少幾十個實例）；
2. 在此之前，bicycle 的任何指標都**不可引用**。

## 5. 決策

| 項 | 決定 | 理由 |
|---|---|---|
| 是否把 `pg_poc4`（含第三方數據）作為發佈模型 | **暫不** | 在香港 val 的工作點處無可測量收益；而它帶許可負擔（僅限研究用途）、訓練時間 ×10、且引入域偏移風險 |
| 第三方數據是否保留 | **保留在 `data/dataset_poc4`** | 作為已記錄的證據；若將來擴類或做消融仍可用 |
| 驗證集 | **維持香港實拍、不含第三方數據** | 本次對比之所以可信，正因為 val 是乾淨的（`--add-train-only`）。若當初把 Roboflow 混進 val，這次會得出「大勝」的假結論 |

**這個負面結果本身有價值**：它説明在 3 類 POC 上，「通用域大數據」不是瓶頸的解，
瓶頸是 `bicycle`/`scooter` 這類**香港特定素材的驗證數據**。

## 6. 附帶更正：本機**有** CUDA GPU

`runs/pg_poc4` 的訓練橫幅顯示 `CUDA:0 (NVIDIA GeForce RTX 5070, 12199MiB)`。
實測（`scripts/probe_cuda.py`，不只讀 `is_available()`，還實際做矩陣乘）：

| 環境 | torch | CUDA |
|---|---|---|
| `.venv`（訓練） | `2.11.0+cu128` | ✅ |
| `.venv-vlm`（GDINO/VLM） | `2.11.0+cu128` | ✅ |
| `.venv-export`（TFLite 導出） | `2.14.0+cpu` | ❌ |

**RTX 5070，11.9 GiB，sm_120，實測 4.44 TFLOP/s**（同規模矩陣乘：CPU 25 ms vs GPU 3.6 ms）。

原先多處文檔寫「本機無 GPU、CUDA 不可用」，很可能是**只看了 `.venv-export` 就推廣到全機**。
`docs/superpowers/plans/2026-09-28-decision-no-ssl-pretraining.md` 已更正並保留了更正記錄。
**那條決策的結論不變**（1e8 圖像/數千 GPU-小時 與 14 萬幀差 4~5 個數量級），
但受影響的成本估算要改：GDINO 的 **11.3 s/圖是在 GPU 上測的**
（`gd_detect.py` 用 `.to("cuda")`），8033 張 ≈ **25 GPU-小時**，不是 CPU-小時。
