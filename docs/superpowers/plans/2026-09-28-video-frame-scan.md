# 視頻掃描：從「只留有檢測的幀」改成「按類別定額取前 K」

**日期：** 2026-09-28
**範圍：** `scripts/scan_video_frames.py`（方案 A）
**目的：** 把長時間視頻變成一份**可人工複核的候選幀集**，而不是上萬張空街。

---

## 1. 最初的設計是錯的，而且錯得看不出來

原方案（也是我一開始建議的）：高步長掃描 + 開放詞表檢測，**凡有命中的幀就留**。

邏輯上説得通，但沒量過。寫完先量了一下（`scripts/probe_scan_selectivity.py`，
12 張真實街景 `data/probe/streetview`，48 類 164 條 prompt）：

| 門檻 | 保留幀佔比 |
|---|---|
| 0.15 | 100% |
| 0.25 | 100% |
| 0.35 | 100% |
| 0.45 | 100% |
| 0.55 | 100% |

**即使把門檻提到 0.55，一幀都篩不掉。**

原因是開放詞表在真實街景上**什麼都能匹配**：每幀命中 9~16 個類、
90~150 個框（`hand_truck` 平均 18 框/幀、`billboard` 261 框/12 幀）。
「有沒有檢測」在街景裏恆為真，所以它不是一個篩選條件。

更值得警惕的是反向的那一半：**我們唯一有真實模型的類 `bin`，
在這 12 幀裏最高只到 0.18**。零樣本既篩不掉多餘的，也認不出想要的。

> 教訓與本文檔其他記錄同類：**一個「邏輯上説得通」的篩選條件，
> 不量一下就可能恆為真。** 而它的表現是「按規則正常工作」——
> 輸出一份看起來沒問題的萬餘幀清單。

---

## 2. 改成按類別定額取前 K

數據集的真實需求不是「哪些幀有東西」，而是**「每一類各要 250 個實例」**。
所以選幀的正確形式是按類別排序取前 K：

- 每一類按該類在幀上的**最高分**排序，取前 `--per-class` 幀；
- 一幀可被多個類選中，只存一張圖；
- 選完再按 phash 去重，避免同類前 K 全是同一堵牆；
- **某類一幀都沒選上，本身就是結論**，報告裏顯式列出來。

零樣本分數**沒有標定**，所以只用來**排序**，不用來判定真偽。
`class_aliases.json` 裏的 `gdin_threshold` 是 Grounding DINO 的閾值，
**不能**拿來用在這裏（兩者分值分佈不同，混用會得到一個看似合理卻錯的篩選）。

### 兩遍掃描，不落地任何一張落選圖

第一遍解碼 + 推理，**只在內存裏記每幀各類的最高分**（不留框，防內存膨脹），
據此算出每類前 K、得到幀號集合；第二遍只解碼並寫出這些幀號。
解碼比推理便宜兩個數量級，換來的是「絕不寫出一張不會被選中的圖」。

## 3. 端到端驗證（答案已知的合成視頻）

`scripts/make_scan_test_video.py` 造一段 210 幀的視頻，7 段 × 30 幀，
交替使用**純噪聲背景**與**貼上垃圾桶的背景**；`--sample-fps 1` 時每段恰好採一幀。

已知答案：段 2/3/4/6 有垃圾桶（段 3 與段 2 逐像素相同），段 0/1/5 什麼都沒有。

實跑結果（`--per-class 3 --min-score 0.25`）：

| 階段 | 幀數 |
|---|---|
| 解碼總幀 | 210 |
| 採樣 | 7 |
| 有候選的幀 | 4 |
| 按定額選中 | 4 |
| 去重後又丟 | 1 |
| **最終可用** | **3** |

- 三個「空段」**一幀候選都沒產生** → 篩子確實在篩；
- 逐像素相同的那一幀被去重丟掉 → 去重有效；
- 最終 3 張恰是 3 個**不同的**有垃圾桶場景 → 210 幀壓縮到 3 張（70×）。

同時這份輸出也驗證了「零樣本標籤只能當線索」：貼了垃圾桶的那兩幀，
零樣本給的主要是 `billboard:0.79` / `bucket:0.63`（**錯的**），
只有其中一幀正確給出了 `bin:0.83`。報告裏明確寫了這一點，
否則複核的人會以為清單裏的類名是結論。

---

## 4. 侷限（已寫進報告，不在代碼裏藏）

- 零樣本分數未標定 → 只用於排序。
- 街景噪聲極大 → `manifest.csv` 的類名是**線索**，不是結論。
- 「42 個類沒有任何候選」經常出現，**不代表素材裏沒有**，
  而是零樣本對它們的召回可能為零。這些類要靠實拍補，或等有了帶數據的模型再復掃。
- 產物是**候選幀**，不是標註；真正的判定交給人工複核與三段式預標。

## 5. 用法

```powershell
# 把素材放到 data/raw/<路線>/ 下，然後：
python scripts/scan_video_frames.py --per-class 20

# 先估一下會選出多少張（不寫圖）
python scripts/scan_video_frames.py --dry-run

# 指定素材與採樣率
python scripts/scan_video_frames.py --videos D:\footage\tiu_keng_leng --sample-fps 1 --per-class 30
```

產出：`data/frames/selected/<來源>/` 下的候選幀、`manifest.csv`（每幀依據）、
`report.md`（總賬 + 逐類情況 + 沒掃到的類）。

## 6. 首次真實素材試跑：尖沙咀步行 4K ×2（2026-09-28）

素材：`data/raw/myVideo/` 下兩條 20 分鐘、1280×720 @ **59.94 fps** 的香港步行視頻。

```powershell
python scripts/scan_video_frames.py --videos data\raw\myVideo `
    --out data\frames\selected --sample-fps 1 --per-class 20
```

| 階段 | 幀數 |
|---|---|
| 解碼總幀 | 143,784 |
| 採樣（1 fps） | 2,397 |
| 模糊被丟 | 2 |
| **有候選的幀** | **2,358（98%）** |
| 按定額選中 | 454 |
| 去重後又丟 | 9 |
| **最終可用** | **445** |

耗時 **1.7 分鐘**。能這麼快是因為 `grab()` 優化：59.94 fps 下每 120 幀只用 1 幀，
`read()` 會把 119 幀白解碼一遍，而兩步式掃描要解碼兩遍。

**98% 的採樣幀都有候選**——再次印證第 1 節的結論：在真實街景裏
「有沒有檢測」不是篩選條件，**配額才是**（2397 → 445）。

### 6.1 關鍵發現：9 個核心類零樣本**完全沒有召回**

報告顯示 12 個類「零候選」。但**光看掃描報告分不清**是「沒有召回」
還是「只是低於門檻」——這兩者的處理方式完全相反。於是用
`scripts/probe_missing_classes.py`（推理下限壓到 0.01）看了 150 幀：

| 類別 | 150 幀內最高分 | 結論 |
|---|---|---|
| `zebra_crossing` | 0.179 | 低於門檻 |
| `fork_in_road` | 0.133 | 低於門檻 |
| `crowds_of_people_queuing` | 0.083 | 低於門檻 |
| `step` | 0.044 | **無召回** |
| `tree_root_on_the_road` | 0.031 | **無召回** |
| `scaffold` / `road_excavation` / `caution_slippery` / `footbridge_railing` | 0.010~0.020 | **無召回** |
| **`stairs` / `barrier_water` / `barrier_fencing`** | **0.000** | **無召回** |
| （對照）`bin` / `pedestrian` / `hand_truck` | 0.671 / 0.960 / 0.987 | 正常 |

**`stairs` 在 40 分鐘香港街景裏最高分是 0.000。** 樓梯、台階、天橋欄杆
這些**畢設主線上的核心類，靠掃視頻一個都拿不到**。

> 戰略含義：**掃視頻只能解決約 15 個類**。`stairs` / `step` /
> `footbridge_railing` / `barrier_water` 等必須**專門去拍**——
> 錄製時特意走近、正對這些目標，讓整段視頻本身就是候選，
> 再由人工標註。這一條改變了原先「靠掃描攢數據」的計劃。

### 6.2 可疑的類（高觸發率 = 過度觸發）

| 類別 | 候選幀 | 佔採樣幀 | 判斷 |
|---|---|---|---|
| `pedestrian` | 2,090 | 87% | 可信（街道本來就人多） |
| `billboard` | 1,641 | 68% | **可疑**，尖沙咀不可能每兩幀一塊廣告牌 |
| `streetlight` | 1,184 | 49% | 存疑 |
| `hand_truck` | 1,030 | 43% | **高度可疑**，具體物體不該有 43% 的出框率 |

低觸發率 + 分數尚可的類（`tactile_paving` 18、`push_cart` 13、
`footbridge_entrance` 4）反而更可能是真的。**複核時先看這些。**
