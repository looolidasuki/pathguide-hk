# 视频扫描：从「只留有检测的帧」改成「按类别定额取前 K」

**日期：** 2026-09-28
**范围：** `scripts/scan_video_frames.py`（方案 A）
**目的：** 把长时间视频变成一份**可人工复核的候选帧集**，而不是上万张空街。

---

## 1. 最初的设计是错的，而且错得看不出来

原方案（也是我一开始建议的）：高步长扫描 + 开放词表检测，**凡有命中的帧就留**。

逻辑上说得通，但没量过。写完先量了一下（`scripts/probe_scan_selectivity.py`，
12 张真实街景 `data/probe/streetview`，48 类 164 条 prompt）：

| 门槛 | 保留帧占比 |
|---|---|
| 0.15 | 100% |
| 0.25 | 100% |
| 0.35 | 100% |
| 0.45 | 100% |
| 0.55 | 100% |

**即使把门槛提到 0.55，一帧都筛不掉。**

原因是开放词表在真实街景上**什么都能匹配**：每帧命中 9~16 个类、
90~150 个框（`hand_truck` 平均 18 框/帧、`billboard` 261 框/12 帧）。
「有没有检测」在街景里恒为真，所以它不是一个筛选条件。

更值得警惕的是反向的那一半：**我们唯一有真实模型的类 `bin`，
在这 12 帧里最高只到 0.18**。零样本既筛不掉多余的，也认不出想要的。

> 教训与本文档其他记录同类：**一个「逻辑上说得通」的筛选条件，
> 不量一下就可能恒为真。** 而它的表现是「按规则正常工作」——
> 输出一份看起来没问题的万余帧清单。

---

## 2. 改成按类别定额取前 K

数据集的真实需求不是「哪些帧有东西」，而是**「每一类各要 250 个实例」**。
所以选帧的正确形式是按类别排序取前 K：

- 每一类按该类在帧上的**最高分**排序，取前 `--per-class` 帧；
- 一帧可被多个类选中，只存一张图；
- 选完再按 phash 去重，避免同类前 K 全是同一堵墙；
- **某类一帧都没选上，本身就是结论**，报告里显式列出来。

零样本分数**没有标定**，所以只用来**排序**，不用来判定真伪。
`class_aliases.json` 里的 `gdin_threshold` 是 Grounding DINO 的阈值，
**不能**拿来用在这里（两者分值分布不同，混用会得到一个看似合理却错的筛选）。

### 两遍扫描，不落地任何一张落选图

第一遍解码 + 推理，**只在内存里记每帧各类的最高分**（不留框，防内存膨胀），
据此算出每类前 K、得到帧号集合；第二遍只解码并写出这些帧号。
解码比推理便宜两个数量级，换来的是「绝不写出一张不会被选中的图」。

## 3. 端到端验证（答案已知的合成视频）

`scripts/make_scan_test_video.py` 造一段 210 帧的视频，7 段 × 30 帧，
交替使用**纯噪声背景**与**贴上垃圾桶的背景**；`--sample-fps 1` 时每段恰好采一帧。

已知答案：段 2/3/4/6 有垃圾桶（段 3 与段 2 逐像素相同），段 0/1/5 什么都没有。

实跑结果（`--per-class 3 --min-score 0.25`）：

| 阶段 | 帧数 |
|---|---|
| 解码总帧 | 210 |
| 采样 | 7 |
| 有候选的帧 | 4 |
| 按定额选中 | 4 |
| 去重后又丢 | 1 |
| **最终可用** | **3** |

- 三个「空段」**一帧候选都没产生** → 筛子确实在筛；
- 逐像素相同的那一帧被去重丢掉 → 去重有效；
- 最终 3 张恰是 3 个**不同的**有垃圾桶场景 → 210 帧压缩到 3 张（70×）。

同时这份输出也验证了「零样本标签只能当线索」：贴了垃圾桶的那两帧，
零样本给的主要是 `billboard:0.79` / `bucket:0.63`（**错的**），
只有其中一帧正确给出了 `bin:0.83`。报告里明确写了这一点，
否则复核的人会以为清单里的类名是结论。

## 4. 局限（已写进报告，不在代码里藏）

- 零样本分数未标定 → 只用于排序。
- 街景噪声极大 → `manifest.csv` 的类名是**线索**，不是结论。
- 「42 个类没有任何候选」经常出现，**不代表素材里没有**，
  而是零样本对它们的召回可能为零。这些类要靠实拍补，或等有了带数据的模型再复扫。
- 产物是**候选帧**，不是标注；真正的判定交给人工复核与三段式预标。

## 5. 用法

```powershell
# 把素材放到 data/raw/<路线>/ 下，然后：
python scripts/scan_video_frames.py --per-class 20

# 先估一下会选出多少张（不写图）
python scripts/scan_video_frames.py --dry-run

# 指定素材与采样率
python scripts/scan_video_frames.py --videos D:\footage\tiu_keng_leng --sample-fps 1 --per-class 30
```

产出：`data/frames/selected/<来源>/` 下的候选帧、`manifest.csv`（每帧依据）、
`report.md`（总账 + 逐类情况 + 没扫到的类）。

## 6. 首次真实素材试跑：尖沙咀步行 4K ×2（2026-09-28）

素材：`data/raw/myVideo/` 下两条 20 分钟、1280×720 @ **59.94 fps** 的香港步行视频。

```powershell
python scripts/scan_video_frames.py --videos data\raw\myVideo `
    --out data\frames\selected --sample-fps 1 --per-class 20
```

| 阶段 | 帧数 |
|---|---|
| 解码总帧 | 143,784 |
| 采样（1 fps） | 2,397 |
| 模糊被丢 | 2 |
| **有候选的帧** | **2,358（98%）** |
| 按定额选中 | 454 |
| 去重后又丢 | 9 |
| **最终可用** | **445** |

耗时 **1.7 分钟**。能这么快是因为 `grab()` 优化：59.94 fps 下每 120 帧只用 1 帧，
`read()` 会把 119 帧白解码一遍，而两步式扫描要解码两遍。

**98% 的采样帧都有候选**——再次印证第 1 节的结论：在真实街景里
「有没有检测」不是筛选条件，**配额才是**（2397 → 445）。

### 6.1 关键发现：9 个核心类零样本**完全没有召回**

报告显示 12 个类「零候选」。但**光看扫描报告分不清**是「没有召回」
还是「只是低于门槛」——这两者的处理方式完全相反。于是用
`scripts/probe_missing_classes.py`（推理下限压到 0.01）看了 150 帧：

| 类别 | 150 帧内最高分 | 结论 |
|---|---|---|
| `zebra_crossing` | 0.179 | 低于门槛 |
| `fork_in_road` | 0.133 | 低于门槛 |
| `crowds_of_people_queuing` | 0.083 | 低于门槛 |
| `step` | 0.044 | **无召回** |
| `tree_root_on_the_road` | 0.031 | **无召回** |
| `scaffold` / `road_excavation` / `caution_slippery` / `footbridge_railing` | 0.010~0.020 | **无召回** |
| **`stairs` / `barrier_water` / `barrier_fencing`** | **0.000** | **无召回** |
| （对照）`bin` / `pedestrian` / `hand_truck` | 0.671 / 0.960 / 0.987 | 正常 |

**`stairs` 在 40 分钟香港街景里最高分是 0.000。** 楼梯、台阶、天桥栏杆
这些**毕设主线上的核心类，靠扫视频一个都拿不到**。

> 战略含义：**扫视频只能解决约 15 个类**。`stairs` / `step` /
> `footbridge_railing` / `barrier_water` 等必须**专门去拍**——
> 录制时特意走近、正对这些目标，让整段视频本身就是候选，
> 再由人工标注。这一条改变了原先「靠扫描攒数据」的计划。

### 6.2 可疑的类（高触发率 = 过度触发）

| 类别 | 候选帧 | 占采样帧 | 判断 |
|---|---|---|---|
| `pedestrian` | 2,090 | 87% | 可信（街道本来就人多） |
| `billboard` | 1,641 | 68% | **可疑**，尖沙咀不可能每两帧一块广告牌 |
| `streetlight` | 1,184 | 49% | 存疑 |
| `hand_truck` | 1,030 | 43% | **高度可疑**，具体物体不该有 43% 的出框率 |

低触发率 + 分数尚可的类（`tactile_paving` 18、`push_cart` 13、
`footbridge_entrance` 4）反而更可能是真的。**复核时先看这些。**
