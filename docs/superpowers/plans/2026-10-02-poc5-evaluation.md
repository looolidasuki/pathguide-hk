# pg_poc5 评估：新类不误报（好），但行人工作点没变好（关键）

**日期：** 2026-10-02
**训练：** `data/dataset_poc5`（10,456 图 / 18 类 / 40,992 框），60 轮，**147 分钟**，
最佳 mAP50 **0.9268**（第 31 轮）。
**对比对象：** `runs/pg_poc3`（当前端上模型，3 类）。
**对比数据：** `data/dataset_poc5` 的 val —— 103 张**香港实拍**，与 poc3 的 val
在前三类上实例数相同（pedestrian 242 / bicycle 2；bin 16 vs 19）。

---

## 1. 一句话结论

**poc5 的高 mAP50 没有转化成工作点上的收益。** 在同等精确率下，行人的召回
poc5 **不比 poc3 好**（高精度区间更差）；真正的收获是 `bin` 明显变好、
`bicycle` 首次能被检出、以及 **15 个新类不产生误报**。

## 2. 决定性的一张表：按 mAP 会得出相反的结论

| 口径 | poc3 | poc5 | 看起来 |
|---|---:|---:|---|
| 总体 mAP50（默认阈值） | 0.744 | **0.927** | poc5 大胜 |
| pedestrian mAP50 | 0.796 | **0.816** | poc5 略好 |
| bicycle mAP50 | 0.496 | **0.995** | poc5 大胜 |
| bin mAP50 | 0.958 | **0.969** | 持平 |

若停在这里，结论会是「poc5 全面提升」。**但这是错的** ——
mAP50 是对所有阈值积分的面积，而产品只在**一个**阈值上运行（播报门槛 0.70）。

## 3. 在播报门槛 0.70 处

| 类 | poc3 P / R | poc5 P / R |
|---|---|---|
| pedestrian | 0.980 / **0.413** | 0.974 / **0.314** |
| bicycle | 0.000 / 0.000 | 0.000 / 0.000 |
| bin | 0.929 / 0.812 | **1.000 / 0.938** |
| 总体 | 0.636 | 0.658 |

**pedestrian 的召回从 0.413 掉到 0.314** —— 在播报门槛上，poc5 反而说得更少。

## 4. 原因：置信度分布整体下移，不是能力退化

按阈值看 pedestrian：

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.30 | 0.929 / 0.593 | 0.835 / **0.669** |
| 0.40 | 0.929 / 0.593 | 0.893 / **0.624** |
| 0.50 | 0.929 / 0.593 | 0.940 / 0.516 |
| 0.60 | 0.935 / 0.533 | 0.934 / 0.409 |
| 0.65 | 0.975 / 0.479 | 0.955 / 0.351 |
| 0.70 | 0.980 / 0.413 | 0.974 / 0.314 |

poc5 在**低阈值**处召回更高（0.669 vs 0.593），在**高阈值**处更低。
这说明它学到的**更多**，但**置信度整体被压低** —— 典型的域偏移导致的标定偏移
（第三方数据是近景实物照，与街景不同分布）。

### 4.1 因此「固定在 0.70 比较」是不公平的

0.70 是在 poc3 上调出来的（见 `app/lib/tts/announcer.dart` 的 `kMinSpeakScore`）。
拿它去量 poc5，测的是**标定差异**，不是能力差异。
本项目精度优先（误报代价不对称），所以公平的做法是让两者各自取到
**同等精确率**的工作点再比召回：

| 目标精度 | poc3 | poc5 | 判定 |
|---|---|---|---|
| P ≥ 0.90 | R=**0.593** @0.40 | R=0.554 @0.45 | poc3 略好 |
| P ≥ 0.93 | R=0.533 @0.60 | R=0.516 @0.50 | 持平 |
| P ≥ 0.95 | R=**0.479** @0.65 | R=0.351 @0.65 | **poc3 明显更好** |
| P ≥ 0.97 | R=**0.479** @0.65 | R=0.314 @0.70 | **poc3 明显更好** |

**结论：同等精确率下 poc3 的行人召回不差于 poc5，高精度区间更好。**
多出来的 30,000 个第三方行人框没有换来行人这一项的提升。

## 5. 真正的收获

### 5.1 `bin` 明确变好

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.50 | 0.844 / 0.875 | **1.000 / 0.938** |
| 0.70 | 0.929 / 0.812 | **1.000 / 0.938** |
| 0.90 | 1.000 / 0.438 | 1.000 / **0.562** |

几乎每个阈值上都更好。

### 5.2 `bicycle` 首次能被检出（但仍不会播报）

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.30 | 0.000 / 0.000 | **1.000 / 0.500** |
| ≥0.50 | 0.000 / 0.000 | 0.000 / 0.000 |

poc5 在 0.30 处检出 1 个（召回 0.500，且精确率 1.000 = 没错报），
**但置信度不到 0.50**，所以**在播报门槛处仍然是 0/0 —— 用户依然听不到单车提醒**。

bicycle 的 mAP50 0.995 完全是低阈值那一段撑起来的。
**val 只有 2 个实例，所以这不能作为「bicycle 好了」的依据**，
只能说「从完全检不出，变成检得出但不够自信」。

### 5.3 ★ 15 个新类**零误报**（这是最有价值的一条）

val 的 103 张香港街拍里，这 15 个类**一个实例都没有**。
跑预测统计「检出了 val 里不存在的类」的次数：

| conf ≥ | 误报次数 |
|---|---|
| 0.30 | **0** |
| 0.70 | **0** |

**在播报门槛处误报过的图：0 / 103（0.0%）。**

含义：poc5 在香港街景上**不会乱报** `obstacle` / `escalator` / `door` 等新类 ——
它们在自己的域外保持**沉默**，而不是胡说。
对视障用户来说，沉默远比错报安全（错报会让人对着空无一物做动作）。
**所以加入这 15 个类不会让系统变危险。**

> 反过来说：它们也**可能根本不会在香港街景上触发** ——
> 因为训练图是近景实物照。这一点从 val 上看不出来（val 里没有它们的实例），
> 需要香港实拍素材才能验证。

## 6. 一个测量盲区（必须记住）

ultralytics 的 `ap_per_class` 只对 **GT 里出现过的类** 计算 AP；
预测到其它类的框**直接被丢掉，不计入任何指标**。

而 poc5 的 val 里那 15 个新类**一个实例都没有** —— 于是
**poc5 把它们误检多少次，val 指标里完全看不见**。
「总体 P 0.658」这个数字**不包含**新类的误报。

这就是为什么必须单独跑 §5.3 那个探测：**指标看不见的地方要靠专门的探测补上**。
本项目已经反复出现同一模式（98% 帧都有检出所以「有无检出」不能当筛子、
bicycle 只有 2 个实例所以它的 mAP 不可引用）——
**每次都要问「这个数字看不见什么」**。

## 7. 建议

| 项 | 建议 | 理由 |
|---|---|---|
| 是否把 poc5 作为端上模型 | **暂不** | 工作点上行人召回没有变好（高精度区间更差），而端上只有一个模型、268 ms 已到 CPU 上限 |
| poc5 的定位 | **作为 50 类路线的基线继续用** | 它是唯一能识别那 15 个类的模型，且已验证不误报；poc3 只能做 3 类 |
| 端上阈值 | 若最终采用 poc5，**必须重新标定** `kMinSpeakScore` | 0.70 是给 poc3 调的，对 poc5 偏严（0.65 处 poc5 的 P=0.955/R=0.351，而 0.50 处 P=0.940/R=0.516） |
| 下一步最该做的 | **在 poc5 基础上只用香港数据做第二阶段微调** | 域偏移是 §4 的根因。第二阶段可以既保住 15 个新类、又把行人工作点拉回来 |
| 不要做的事 | 不要再加第三方训练数据 | 两次实验（people-detection 13×/136×、everyday 18 类）都**没有**在同等精确率下改善行人 |

## 8. 工具侧的修复（顺带）

对比脚本里发现一个**靠巧合工作**的写法并修掉：
`r.names` 是 data.yaml 的类别数（poc5 = 18），而 `r.box.p` 只覆盖 val 里有实例的类
（poc5 = 3），用 names 的下标索引 box.p 会错位/越界。
旧模型 3 类时两个长度恰好相等，**错误被埋了很久**，换到 18 类才暴露。

已抽成 `scripts/yolo_metrics.py` 的纯函数 + 8 条单测，
其中一条专门守「长度不一致必须报错，不能默默错位」。
`compare_at_threshold.py` 与 `val_published_model.py` 都已改用它，
重构后 `pg_poc3_val.json` 的数字与原实现**逐项一致**（确认行为未变）。

另新增 `--grid`：要按「同等精确率」公平对比，就必须在目标精度附近加密阈值网格。
