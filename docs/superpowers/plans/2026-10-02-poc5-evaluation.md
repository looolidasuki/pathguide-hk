# pg_poc5 評估：新類不誤報（好），但行人工作點沒變好（關鍵）

**日期：** 2026-10-02
**訓練：** `data/dataset_poc5`（10,456 圖 / 18 類 / 40,992 框），60 輪，**147 分鐘**，
最佳 mAP50 **0.9268**（第 31 輪）。
**對比對象：** `runs/pg_poc3`（當前端上模型，3 類）。
**對比數據：** `data/dataset_poc5` 的 val —— 103 張**香港實拍**，與 poc3 的 val
在前三類上實例數相同（pedestrian 242 / bicycle 2；bin 16 vs 19）。

---

## 1. 一句話結論

**poc5 的高 mAP50 沒有轉化成工作點上的收益。** 在同等精確率下，行人的召回
poc5 **不比 poc3 好**（高精度區間更差）；真正的收穫是 `bin` 明顯變好、
`bicycle` 首次能被檢出、以及 **15 個新類不產生誤報**。

## 2. 決定性的一張表：按 mAP 會得出相反的結論

| 口徑 | poc3 | poc5 | 看起來 |
|---|---:|---:|---|
| 總體 mAP50（默認閾值） | 0.744 | **0.927** | poc5 大勝 |
| pedestrian mAP50 | 0.796 | **0.816** | poc5 略好 |
| bicycle mAP50 | 0.496 | **0.995** | poc5 大勝 |
| bin mAP50 | 0.958 | **0.969** | 持平 |

若停在這裏，結論會是「poc5 全面提升」。**但這是錯的** ——
mAP50 是對所有閾值積分的面積，而產品只在**一個**閾值上運行（播報門檻 0.70）。

## 3. 在播報門檻 0.70 處

| 類 | poc3 P / R | poc5 P / R |
|---|---|---|
| pedestrian | 0.980 / **0.413** | 0.974 / **0.314** |
| bicycle | 0.000 / 0.000 | 0.000 / 0.000 |
| bin | 0.929 / 0.812 | **1.000 / 0.938** |
| 總體 | 0.636 | 0.658 |

**pedestrian 的召回從 0.413 掉到 0.314** —— 在播報門檻上，poc5 反而説得更少。

## 4. 原因：置信度分佈整體下移，不是能力退化

按閾值看 pedestrian：

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.30 | 0.929 / 0.593 | 0.835 / **0.669** |
| 0.40 | 0.929 / 0.593 | 0.893 / **0.624** |
| 0.50 | 0.929 / 0.593 | 0.940 / 0.516 |
| 0.60 | 0.935 / 0.533 | 0.934 / 0.409 |
| 0.65 | 0.975 / 0.479 | 0.955 / 0.351 |
| 0.70 | 0.980 / 0.413 | 0.974 / 0.314 |

poc5 在**低閾值**處召回更高（0.669 vs 0.593），在**高閾值**處更低。
這説明它學到的**更多**，但**置信度整體被壓低** —— 典型的域偏移導致的標定偏移
（第三方數據是近景實物照，與街景不同分佈）。

### 4.1 因此「固定在 0.70 比較」是不公平的

0.70 是在 poc3 上調出來的（見 `app/lib/tts/announcer.dart` 的 `kMinSpeakScore`）。
拿它去量 poc5，測的是**標定差異**，不是能力差異。
本項目精度優先（誤報代價不對稱），所以公平的做法是讓兩者各自取到
**同等精確率**的工作點再比召回：

| 目標精度 | poc3 | poc5 | 判定 |
|---|---|---|---|
| P ≥ 0.90 | R=**0.593** @0.40 | R=0.554 @0.45 | poc3 略好 |
| P ≥ 0.93 | R=0.533 @0.60 | R=0.516 @0.50 | 持平 |
| P ≥ 0.95 | R=**0.479** @0.65 | R=0.351 @0.65 | **poc3 明顯更好** |
| P ≥ 0.97 | R=**0.479** @0.65 | R=0.314 @0.70 | **poc3 明顯更好** |

**結論：同等精確率下 poc3 的行人召回不差於 poc5，高精度區間更好。**
多出來的 30,000 個第三方行人框沒有換來行人這一項的提升。

## 5. 真正的收穫

### 5.1 `bin` 明確變好

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.50 | 0.844 / 0.875 | **1.000 / 0.938** |
| 0.70 | 0.929 / 0.812 | **1.000 / 0.938** |
| 0.90 | 1.000 / 0.438 | 1.000 / **0.562** |

幾乎每個閾值上都更好。

### 5.2 `bicycle` 首次能被檢出（但仍不會播報）

| conf | poc3 P / R | poc5 P / R |
|---|---|---|
| 0.30 | 0.000 / 0.000 | **1.000 / 0.500** |
| ≥0.50 | 0.000 / 0.000 | 0.000 / 0.000 |

poc5 在 0.30 處檢出 1 個（召回 0.500，且精確率 1.000 = 沒錯報），
**但置信度不到 0.50**，所以**在播報門檻處仍然是 0/0 —— 用户依然聽不到單車提醒**。

bicycle 的 mAP50 0.995 完全是低閾值那一段撐起來的。
**val 只有 2 個實例，所以這不能作為「bicycle 好了」的依據**，
只能説「從完全檢不出，變成檢得出但不夠自信」。

### 5.3 ★ 15 個新類**零誤報**（這是最有價值的一條）

val 的 103 張香港街拍裏，這 15 個類**一個實例都沒有**。
跑預測統計「檢出了 val 裏不存在的類」的次數：

| conf ≥ | 誤報次數 |
|---|---|
| 0.30 | **0** |
| 0.70 | **0** |

**在播報門檻處誤報過的圖：0 / 103（0.0%）。**

含義：poc5 在香港街景上**不會亂報** `obstacle` / `escalator` / `door` 等新類 ——
它們在自己的域外保持**沉默**，而不是胡説。
對視障用户來説，沉默遠比錯報安全（錯報會讓人對着空無一物做動作）。
**所以加入這 15 個類不會讓系統變危險。**

> 反過來説：它們也**可能根本不會在香港街景上觸發** ——
> 因為訓練圖是近景實物照。這一點從 val 上看不出來（val 裏沒有它們的實例），
> 需要香港實拍素材才能驗證。

## 6. 一個測量盲區（必須記住）

ultralytics 的 `ap_per_class` 只對 **GT 裏出現過的類** 計算 AP；
預測到其它類的框**直接被丟掉，不計入任何指標**。

而 poc5 的 val 裏那 15 個新類**一個實例都沒有** —— 於是
**poc5 把它們誤檢多少次，val 指標裏完全看不見**。
「總體 P 0.658」這個數字**不包含**新類的誤報。

這就是為什麼必須單獨跑 §5.3 那個探測：**指標看不見的地方要靠專門的探測補上**。
本項目已經反覆出現同一模式（98% 幀都有檢出所以「有無檢出」不能當篩子、
bicycle 只有 2 個實例所以它的 mAP 不可引用）——
**每次都要問「這個數字看不見什麼」**。

## 7. 建議

| 項 | 建議 | 理由 |
|---|---|---|
| 是否把 poc5 作為端上模型 | **暫不** | 工作點上行人召回沒有變好（高精度區間更差），而端上只有一個模型、268 ms 已到 CPU 上限 |
| poc5 的定位 | **作為 50 類路線的基線繼續用** | 它是唯一能識別那 15 個類的模型，且已驗證不誤報；poc3 只能做 3 類 |
| 端上閾值 | 若最終採用 poc5，**必須重新標定** `kMinSpeakScore` | 0.70 是給 poc3 調的，對 poc5 偏嚴（0.65 處 poc5 的 P=0.955/R=0.351，而 0.50 處 P=0.940/R=0.516） |
| 下一步最該做的 | **在 poc5 基礎上只用香港數據做第二階段微調** | 域偏移是 §4 的根因。第二階段可以既保住 15 個新類、又把行人工作點拉回來 |
| 不要做的事 | 不要再加第三方訓練數據 | 兩次實驗（people-detection 13×/136×、everyday 18 類）都**沒有**在同等精確率下改善行人 |

## 8. 工具側的修復（順帶）

對比腳本里發現一個**靠巧合工作**的寫法並修掉：
`r.names` 是 data.yaml 的類別數（poc5 = 18），而 `r.box.p` 只覆蓋 val 裏有實例的類
（poc5 = 3），用 names 的下標索引 box.p 會錯位/越界。
舊模型 3 類時兩個長度恰好相等，**錯誤被埋了很久**，換到 18 類才暴露。

已抽成 `scripts/yolo_metrics.py` 的純函數 + 8 條單測，
其中一條專門守「長度不一致必須報錯，不能默默錯位」。
`compare_at_threshold.py` 與 `val_published_model.py` 都已改用它，
重構後 `pg_poc3_val.json` 的數字與原實現**逐項一致**（確認行為未變）。

另新增 `--grid`：要按「同等精確率」公平對比，就必須在目標精度附近加密閾值網格。
