# 真機「框全錯」的六處靜默缺陷 · 解碼鏈路覆盤

**日期：** 2026-09-23
**範圍：** Android 原生 `YoloDetector`（`app/android/.../VisionPlugin.kt`）的取幀→預處理→解碼鏈路，
以及 Dart 側的座標映射
**症狀（全部不崩潰、不報錯）：**

1. 「HUD 顯示十幾個檢測框，屏幕上一個框都畫不出來」；
2. 「沒有垃圾桶也一直顯示垃圾桶」；
3. 「分數 1.0 幾」，以及診斷裏出現 `score=-386`（模型最後一層是 sigmoid，分數不可能越界）；
4. 「無效檢測還在增長」。

同一個模型、同一批圖片在電腦上完全正常——這是本項目反覆出現的一類失敗模式：
**兩端假設不一致，且沒有任何一端會報錯。**

第一輪修掉了 3 處（佈局、座標換算、pad 偏移）後，複查整條鏈路又找出 3 處。
**六處互相獨立，任何一處單獨存在都足以讓結果不可用。**

---

## 1. 定位方法：把電腦當成真機的鏡子

此前的排查方式是「改真機代碼 → 裝到手機上看 → 回來猜」，一來一回十幾分鍾，
而且改動與症狀之間沒有隔離。這一輪換成：

> **在電腦上把原生 `decode()` 的每一步照抄一遍，用帶人工標註的真實圖片驗證，
> 並把 Kotlin 源碼裏的假設讀出來一起對照。**

產出 `scripts/check_tflite_decode.py`。它同時做三件事：

- 打印模型的真實張量形狀與通道取值；
- 把「佈局 × 座標換算 × 是否減 pad」的各種組合都算一遍，與人工標註比 IoU；
- **讀 Kotlin 源碼**，斷言裏面那幾行與實測/與 numpy 參照一致：
  佈局推導的運算符、座標三步換算、逆旋轉的四個分支、色度取樣下標、`PAD` 填充值。

最後一條是關鍵：光有「電腦對」不能防止真機繼續錯，必須讓兩者的假設**被同一個
腳本同時檢查**。其中「逆旋轉的四個分支」的參照公式不是抄來的，而是腳本用
`np.rot90(R, k=-(rot/90))` 逐點驗證過的——腳本先證明自己的參照是對的，再去核對源碼。

## 2. 六處缺陷

### 2.1 輸出張量的內存佈局讀反了（一行寫反）

```kotlin
val d1 = outShape[1]   // 5
val d2 = outShape[2]   // 8400
transposed = d1 < d2   // ← 寫反了，應為 d1 > d2
```

- **事實：** 本模型輸出是 `[1, 5, 8400]`，即**通道優先**（通道是慢變下標）。
  「錨點優先」當且僅當 anchors 落在第 1 維，也就是 `d1 > d2`。
- **舊寫法：** `d1 < d2` 判成「錨點優先」，於是用 `a * stride + c` 去讀一個
  通道優先的緩衝——**讀到的全是別的通道的數值，框座標被當成了分數**。
- **後果：** 過閾值的框從 20 個漲到 **2629 個**（NMS 後剩十幾個，正好對應
  「HUD 十幾個框」）；分數取到座標值，於是出現 1.0 幾與 `-386`。
- **為什麼看不見：** 本模型的座標已被歸一化到 `[0,1]`，讀錯佈局取到的仍是
  `[0,1]` 內的合法數值，**分數範圍檢查照樣通過**。兩個佈局下的分數範圍分別是
  `[0.0001,0.9355]` 與 `[0.0001,0.9932]`——單看這個判不出對錯。

### 2.2 座標是歸一化的，被當成像素用了

- **事實：** TFLite 導出的 `cx/cy/w/h` 是**歸一化到 letterbox 輸入（640×640）**
  的比例值，不是像素。實測四個座標通道範圍 `[0.0023, 1.0038]`，
  `mean(cx)≈0.498`（正是 320/640）。
- **舊寫法：** `(cx - w/2) / scale / srcW`——漏了 `* inputSize`，
  於是 0.5 被當成 0.5 像素。
- **後果：** 所有框被壓成 0 大小，**屏幕上一個框都畫不出來**（而 HUD 仍在計數）。
- **注意：** 這與 ONNX 的像素座標約定不同，模型裏沒有任何元數據能看出來。

### 2.3 letterbox 的 pad 偏移沒減

- **事實：** 模型座標在**加過灰邊**的空間裏，必須減掉 `padX/padY`。
  豎屏取幀時 `padX = 140`（720×1280 → 縮放到 360×640 後左右各留 140 像素）。
- **舊寫法：** 完全沒減。
- **後果：** 框整體平移，平移量恰好等於灰邊寬度（佔 22%）。

### 2.4 逆旋轉的 90° 與 270° 分支公式錯（每個像素都取錯）

```kotlin
val (sx, sy) = when (rotationDegrees) {
    90 -> Pair(outH - 1 - uy, frameWidth - 1 - ux)   // ← 兩個分量都錯
    270 -> Pair(uy, ux)                              // ← 純轉置 = 鏡像，缺一次翻轉
}
```

- **事實：** Android 的 `rotationDegrees` 是「把原始幀**順時針**轉這麼多度才正立」。
  順時針 90° 的正向映射是 `destX = SRC_H-1-srcY`、`destY = srcX`（第二項是 `srcX`，
  **不是** `SRC_W-1-srcX`，後者會多一次鏡像）。反解即
  `srcX = destY`、`srcY = SRC_H-1-destX`。
- **核對結果（numpy 逐點，raw 1280×720、rotation=90）：**
  舊寫法 **9216 個採樣點 100% 取錯源像素**，正確寫法 0 個錯。
- **後果特別隱蔽：** `sy` 會算到 `[560,1279]`，而原始幀只有 720 行，
  被 `coerceIn` 夾到 719 —— 於是正立圖裏約 **78% 的區域全都取原始幀的最後一行**，
  模型看到的基本上是一條糊掉的橫線。
  而輸入診斷（min/max/越界計數）看不出任何異常，因為讀到的仍是合法 Y 值。

### 2.5 色度（UV）下標按原始平面步長算，但數組是緊湊副本

```kotlin
val uvIndex = (cy / 2) * uvRowStride + (cx / 2) * uvPixelStride   // ← 用了原始步長
```

- **事實：** `copyPlane` 返回的是**緊湊數組** `out[y * width + x]`，
  UV 的 width 就是 `(frameWidth + 1) / 2`、pixelStride 已展開為 1。
- **舊寫法：** 用的是**原始平面**的 `rowStride/pixelStride`。真機常見的 NV21 佈局是
  `rowStride ≈ frameWidth`、`pixelStride = 2`，於是下標被放大近 2 倍。
- **後果：** 上半幅畫面取到**錯誤的色度**，下半幅直接越界、被 `in u.indices`
  兜成 128（中性色 = 灰度）。表現與「喂灰度圖」完全相同——而本項目實測
  灰度輸入會把最高分從 0.62~0.82 壓到 0.04~0.55（閾值 0.30 下一個框都不出）。
- **注意：** Dart 那一側的 `detect` 路徑本來就傳 `cw / 1`（正確），
  只有相機路徑傳的是原始步長——同一個函數被兩個調用方用兩套約定調用。

### 2.6 Dart 側又轉了一次（重複旋轉）

- **事實：** 原生在採樣時已經把畫面逐像素轉正，檢測框就誕生在**正立座標系**裏，
  而 `VisionSource.frameSize` 報的也正是正立尺寸。
- **舊寫法：** UI 既用正立尺寸構造 `DisplayFit`，又把 `rotationDegrees` 傳給
  `mapDetectionsToScreen` 再轉 90°，兩處疊加。
- **後果：** 框相對畫面整體偏 90°，畫得出來、位置全錯。
- **修法：** 直接**刪掉 `mapDetectionsToScreen` 的 `rotationDegrees` 參數**，
  而不是「傳 0」——讓這個錯誤在類型上就寫不出來，並配契約測試釘住。
  `rotateNormalized` 保留（將來 iOS 若返回原始幀座標就用得上）。

## 3. 證據：與人工標註的 IoU

`data/dataset/images/trashbin/` 抽 8 張帶人工標註的圖，逐組合對照
（`scripts/check_tflite_decode.py --images 8`）：

| 解碼組合 | 平均最佳 IoU | 過閾值框數（NMS 前，均值） |
|---|---|---|
| **正確**（通道優先 + 乘邊長 + 減 pad） | **0.915** | 20 |
| 錯佈局（佈局讀反，座標換算對） | 0.509 | **2629** |
| 漏減 pad | 0.499 | 20 |
| 漏乘邊長 | 0.000 | 20 |
| **真機舊行為**（佈局讀反 + 舊座標換算） | **0.000** | 2629 |

單張最好的例子：`bin (1).jpg` 正確解碼 0.964，舊行為 0.000。

2.2 單獨就足以讓 IoU 歸零，2.1 單獨就足以讓框數爆掉。
2.4 / 2.5 發生在**取幀階段**，比解碼更靠前：它們不改變「解碼對不對」，
而是直接讓模型看到一張錯的圖——所以它們的症狀是「解碼全對但分數極低」，
與上面兩條的「框數/位置錯」完全不同，必須分開驗證。

## 4. 修復

`VisionPlugin.kt`：

1. `transposed = d1 > d2`（並寫清「為什麼必須是 `>`」）；
2. 座標換算改為三步：`* inputSize` → `- padX/padY` → `/ newW/newH`。
   第 3 步用 `newW/newH` 而不是 `scale`——`newW` 就是 `(srcW * scale).toInt()`，
   與真正貼進畫布的那塊像素嚴格一致，避免整數截斷帶來的半像素偏差；
3. 逆旋轉 90/270 分支改為 numpy 驗證過的形式，並刪掉了那段**本身就是錯**的
   文檔註釋（它寫着 `destY = SRC_W-1-srcX`，多一次鏡像——錯的公式註釋是這次
   寫錯的源頭）；
4. 色度下標改為按緊湊副本寬度 `uvWidth` 計算；`detectYuv` 的參數由
   `uvRowStride/uvPixelStride` 改成 `uvWidth`，兩個調用方從此只有一套約定；
5. `decodeStats` 末尾追加 `geo=源尺寸->縮放後尺寸 pad=x,y`，
   `frameFormat` 同時報 `uvPlane=` 原始步長與 `uvCopy=` 緊湊寬度——
   把座標換算與色度取樣的**全部輸入**擺在 HUD 上，畫偏/變灰時第一眼看這裏。

Dart：

6. `mapDetectionsToScreen` 刪掉 `rotationDegrees` 參數；`VisionSource.frameSize`
   的註釋寫明「它同時是檢測框的座標系，UI 不得再旋轉」；
   `test/vision_source_contract_test.dart` 增加「來源已把畫面轉正，映射時不得再旋轉一次」
   的契約測試（用一個偏離中心的框，重複旋轉會讓它跑掉半幅畫面）。

## 6. 順帶記錄的性能事實（不是缺陷）

豎屏取幀下 `720×1280 → letterbox 到 360×640`：方形模型輸入與 9:16 畫幅不匹配，
**寬度方向只用了 640 中的 360**，等於把畫面降採樣 2 倍。垃圾桶這類大目標不受影響
（離線 0.915 IoU），但離得遠的小目標會吃虧。若後續要提小目標召回，
可考慮按豎屏畫幅重新導出/訓練，而不是繼續用方形 640。

## 7. 上真機前先算出「應該看到什麼」

修完之後，用**設備實際使用的那套幾何**（豎屏取幀 720×1280 → `360×640`、
`pad=(140,0)`、`scale=0.5`）在電腦上覆算了一遍：把帶人工標註的照片按 90% 視口
貼進豎屏場景，再走完整的 letterbox → 推理 → 解碼：

| 項目 | 預測值 |
|---|---|
| 最高分範圍 | **0.898 ~ 0.983** |
| 平均最佳 IoU | **0.927** |
| 命中（IoU ≥ 0.5） | **7/7** |

**這就是上真機時的對照基準**：如果真機上分數落在 0.9 上下、框落在垃圾桶上，
説明整條鏈路通了；如果分數很低，問題在取幀/顏色（第 2.4、2.5 條那一類），
而不是解碼；如果框位置整體偏移，看 HUD 的 `geo=` 那一行。

把「預期值」先算出來再上真機，是為了讓真機驗證變成**確認**而不是**試探**——
後者每來一輪都要重裝、重啓、目視判斷，代價高且結論模糊。

## 9. 真機實測（2026-09-27，Redmi 2609FRA74T / Snapdragon 685 / Android 16）

裝包、授權、啓動全部由 `scripts/verify_on_device.ps1` 自動完成；
`demo_page.dart` 的 `_logHud()` 每秒把 HUD 狀態打一行到 logcat，
於是**不需要人看屏幕**就能判斷鏈路是否打通（81 行日誌，`artifacts/device/`）。

### 修好了的證據

| 觀察項 | 真機值 | 説明 |
|---|---|---|
| `transposed` | `false` | 佈局推導修正生效（舊碼這裏必為 `true`） |
| `invalid` | **0** | 不再有分數越界（舊碼是「無效檢測還在增長」） |
| `analyzed` | 0 → 29 持續增長 | 相機分析迴路在跑 |
| `nativeDet` / `det` | 最多 8，81 幀裏 70 幀非零 | **框真的到了 UI**（舊碼是「有數字、畫不出來」） |
| `maxScore` | 最高 **0.982** | 落在離線預測的 0.898~0.983 區間內 |
| `geo` | `480x640->480x640 pad=80,0` | 實測原始幀是 640×480（豎屏取幀 480×640），pad 偏移生效 |
| 崩潰 | 無 | — |

這一步最有價值的地方：**預測值與實測值吻合**。
第 7 節先用設備幾何離線算出「應該看到 0.9 上下的分數、框落在目標上」，
真機跑出來落在同一區間——説明整條鏈路（取幀→轉正→色度→預處理→解碼→映射）
現在是一致的，不是碰巧湊出來的。

### 新發現的**未解決**問題：幀率不可用

| 指標 | 實測 |
|---|---|
| 單幀推理耗時 | 中位 **1182 ms**，最大 **5048 ms** |
| 幀率 | **約 0.7 ~ 1 FPS** |

已排除的原因：

- **不是 delegate 沒掛上**：`tflite` 日誌顯示 XNNPACK 已生效
  （`Replacing 343 out of 345 node(s) with delegate`）。
- **不是省電模式**：`low_power=0`。
- 但**大核被限頻**：cpu4~7 在負載下穩定在 **1.79 GHz**，而 `cpuinfo_max_freq`
  是 **2.61 GHz**（約 68%）——屬於 ROM/温控限制。
- 本機 SoC 為 **Snapdragon 685**（4×A73 + 4×A53），本身是入門級。
- 當前依賴的 `com.google.ai.edge.litert:litert:2.2.0` 的 `classes.jar`
  **只有 17 個類，不含 NnApiDelegate / GpuDelegate**，所以 NNAPI/GPU 完全沒用上。

結論：**純 CPU float32、640×640 的 yolo11n 在這台機器上就是 ~1 秒**。
要讓 demo 可用必須減算力，方向有四條（可疊加）：

| 方案 | 預期倍數 | 代價 |
|---|---|---|
| 加 NNAPI 或 GPU delegate | 2~5× | 需加依賴 + 做好回退（`litert` 本體不含 delegate 類） |
| 輸入邊長 640 → **416**（= 訓練時用的尺寸） | 0.42×（≈500 ms） | 重新導出；**不改代碼**，且與訓練分辨率對齊 |
| int8 量化 | 2~3×，體積 1/4 | 需重新導出 + 改 Kotlin 張量處理（現碼 `require` 輸入元素為 4 字節 float32） |
| 416 + int8 組合 | 預期 100~200 ms（5~10 FPS） | 上述兩項之和 |

這是**尚待決定**的取捨：後兩條會改變模型交付物本身（分辨率/量化），
屬於畢設裏可見的精度-速度權衡，不該由我單方面定。

## 10. 播報門檻：低分只畫框，不開口（2026-09-27 追加）

真機跑通後暴露的下一個問題是**誤報會被念出來**：播報器原本只按
「類別可播報 + 兩級冷卻」過濾，**沒有任何分數門檻**，於是 0.3 分左右的假框
也會説給用户聽。

### 為什麼播報門檻必須高於顯示門檻

代價不對稱：

- **顯示**：屏幕上多一個框，代價接近零；
- **播報**：誤報會讓視障用户**對空無一物做出動作**，在馬路牙子、樓梯口前
  這是安全問題。

而漏報的代價會被**幀的重複**攤薄：真實目標會在連續多幀被檢出，某一幀分數不夠
沒念，冷卻過後還有機會；誤報只要**一幀**就夠被念出去。所以這個門檻按**精度**定，
而不是按 precision/recall 的折中點。

### 門檻值由數據定，不靠感覺

新增 `scripts/pick_speak_threshold.py`：在 44 張帶人工標註的實拍圖上跑全鏈路，
把檢出按分數與標註配對（IoU ≥ 0.5），掃出精度/召回曲線：

| 門檻 | 説出條數 | 誤報 | 精度 | 召回 |
|---|---|---|---|---|
| 0.30（= 顯示默認值） | 92 | 8 | 0.913 | 0.689 |
| 0.50 | 86 | 5 | 0.942 | 0.664 |
| **0.70（選定）** | **78** | **3** | **0.962** | **0.615** |
| 0.90 | 62 | 0 | 1.000 | 0.508 |

取 0.70：誤報 8 → 3（**減少 62%**），每幀召回只掉 0.07，且會被多幀重播補回。
常量定義在 `app/lib/tts/announcer.dart` 的 `kMinSpeakScore`，
**換模型後必須重跑該腳本再改這個值**。

### 實現要點

- 門檻判定放在 `_rejectReason` 的**最前面**，且**不受 `force` 影響**：
  `force` 的語義是「別被冷卻擋住」（時機問題），分數門檻管的是「這是不是真的」
  （正確性問題）。讓 force 繞過它等於留了個「逢低分也照念」的後門。
- 低分候選被跳過時**繼續看下一個候選**，所以低分的 P0 不會把高分目標一起擋掉。
- 界面把兩個閾值分開寫清：滑條改名為「顯示閾值」，面板上另起一行
  「播報門檻 ≥ 0.70（低分只畫框）」。不寫清楚，用户會以為「滑條拉低了怎麼還不念」
  是壞了。
- 單測 5 條覆蓋：低分不播但有記錄、邊界 `>=`、`force` 繞不過、
  跳過低分後高分仍能播、門檻可注入。

真機確認（HUD 狀態行）：`speakMin=0.70` 已生效。

### 順帶修掉的一個自己造的毛病

「本幀無檢出」時 `bestAnchorScore` 仍是 `-Float.MAX_VALUE`，
按 `%f` 打出來是
`best=-340282346638528860000000000000000000000.000@anchor-1`——
既讀不懂又把 HUD 那一欄撐爆。**「沒有檢出」是正常狀態，不該長得像異常**，
已改成 `best=none（無錨點過閾值）`，真機確認顯示正常。

## 11. 幀率優化：640 float32 → 416 int8（2026-09-27）

### 實測結果（同一台機器、同一段場景）

| 配置 | 推理耗時 | 幀率 | 離線 IoU | 模型體積 |
|---|---|---|---|---|
| 640 float32（原） | 776 ~ 1180 ms | 1.1 ~ 1.3 | 0.915 | 10.5 MB |
| 416 float32 | **324 ms** | 3.0 | 0.963 | 10.5 MB |
| **416 int8（現部署）** | **268 ms** | **3.7** | **0.966** | **2.87 MB** |

合計 **3.4×**（1.2 → 3.7 FPS）。

幾條值得記下的結論：

- **輸入邊長是主因，且與面積成正比。** 預測 0.42×（(416/640)²），
  實測 324/776 = 0.42 —— 完全吻合。以後估耗時直接用面積比即可。
- **416 的離線精度反而更高**（0.963 vs 0.915）：416 正是訓練時用的分辨率，
  640 是導出時放大的，等於讓模型處理它沒見過的尺度。
- **int8 只快 1.2×，遠低於預期的 2~3×。** 原因：Ultralytics 導出的 int8 模型
  **保留 float32 輸入/輸出**（量化/反量化在計算圖內部），
  XNNPACK 的 int8 收益被邊緣算子吃掉一部分。
  但換來兩件實在的好處：**零代碼改動**（Kotlin 的 float32 通路原樣可用，
  不用處理量化參數），以及**體積 1/3.7**。
- **`topAll` 這一項讓「沒有檢出」不再有歧義。** 新增後實測 `topAll=0.028`：
  模型在 3549 個錨點上的最高分只有 0.028，遠低於閾值 —— 説明鏡頭前**確實沒有**垃圾桶，
  而不是閾值太高。兩者此前的顯示完全一樣。順帶這也證明了修復後的鏈路
  **不再產生假框**（修之前同一場景會產生上千個）。

### 方案「加 NNAPI / GPU delegate」的可行性結論（有證據，不是推測）

查了 Google Maven 的權威索引，並直接 `javap` 了本地 Gradle 緩存裏的 AAR：

1. `litert:2.2.0` 的 `Interpreter$Options` **只有**
   `setNumThreads / setCancellable / setRuntime / setUseXNNPACK` ——
   **沒有 `addDelegate`，也沒有 `setUseNNAPI`**。
   所以在當前這套 API 上**根本掛不上任何 delegate**。
2. 但 `litert-api:2.2.0` 裏有新 API：
   `com.google.ai.edge.litert.CompiledModel`（含 `GpuOptions` / `QualcommOptions` /
   `Accelerator` / `NpuAcceleratorProvider`），而 `litert:2.2.0` 的 AAR
   **已自帶 `libLiteRtClGlAccelerator.so`**（OpenCL GPU 加速器）。
   → **GPU 加速不需要新增依賴**，但要把 `YoloDetector` 從 `Interpreter`
   遷到 `CompiledModel`。
3. `litert-gpu` 最新只到 **1.4.2**（我們用的是 `litert` 2.2.0），
   走舊的 GPU delegate 會版本錯配 —— 不走。

**CPU 側已接近該機上限**：416 float32 下有效算力約 11 GFLOPS，
與 4×A73@1.79GHz（被 ROM 限頻，滿頻 2.61GHz）的實測吞吐同量級。
繼續提速只有兩條路：**減少算力**（更小輸入 / 更小模型）或
**換計算單元**（GPU via `CompiledModel`、或 NPU）。

### 順帶修掉：導出腳本里的佈局標籤也是反的

`export_tflite.py` 的 `explain_output_shape()` 寫着 `transposed = d1 < d2`，
並把 `[1, 5, 3549]` 報成「`[1, anchors, 4+nc]`（轉置）」——**恰好説反**。
Kotlin 裏那句 `transposed = d1 < d2` 就是照着這條信息寫的
（見第 2.1 節）。**一處錯的名字會生產出另一處錯的代碼**，
現在兩處都由 `check_tflite_decode.py` 同時核對，運算符必須都是 `>`。
