# 真机「框全错」的六处静默缺陷 · 解码链路复盘

**日期：** 2026-09-23
**范围：** Android 原生 `YoloDetector`（`app/android/.../VisionPlugin.kt`）的取帧→预处理→解码链路，
以及 Dart 侧的坐标映射
**症状（全部不崩溃、不报错）：**

1. 「HUD 显示十几个检测框，屏幕上一个框都画不出来」；
2. 「没有垃圾桶也一直显示垃圾桶」；
3. 「分数 1.0 几」，以及诊断里出现 `score=-386`（模型最后一层是 sigmoid，分数不可能越界）；
4. 「无效检测还在增长」。

同一个模型、同一批图片在电脑上完全正常——这是本项目反复出现的一类失败模式：
**两端假设不一致，且没有任何一端会报错。**

第一轮修掉了 3 处（布局、坐标换算、pad 偏移）后，复查整条链路又找出 3 处。
**六处互相独立，任何一处单独存在都足以让结果不可用。**

---

## 1. 定位方法：把电脑当成真机的镜子

此前的排查方式是「改真机代码 → 装到手机上看 → 回来猜」，一来一回十几分钟，
而且改动与症状之间没有隔离。这一轮换成：

> **在电脑上把原生 `decode()` 的每一步照抄一遍，用带人工标注的真实图片验证，
> 并把 Kotlin 源码里的假设读出来一起对照。**

产出 `scripts/check_tflite_decode.py`。它同时做三件事：

- 打印模型的真实张量形状与通道取值；
- 把「布局 × 坐标换算 × 是否减 pad」的各种组合都算一遍，与人工标注比 IoU；
- **读 Kotlin 源码**，断言里面那几行与实测/与 numpy 参照一致：
  布局推导的运算符、坐标三步换算、逆旋转的四个分支、色度取样下标、`PAD` 填充值。

最后一条是关键：光有「电脑对」不能防止真机继续错，必须让两者的假设**被同一个
脚本同时检查**。其中「逆旋转的四个分支」的参照公式不是抄来的，而是脚本用
`np.rot90(R, k=-(rot/90))` 逐点验证过的——脚本先证明自己的参照是对的，再去核对源码。

## 2. 六处缺陷

### 2.1 输出张量的内存布局读反了（一行写反）

```kotlin
val d1 = outShape[1]   // 5
val d2 = outShape[2]   // 8400
transposed = d1 < d2   // ← 写反了，应为 d1 > d2
```

- **事实：** 本模型输出是 `[1, 5, 8400]`，即**通道优先**（通道是慢变下标）。
  「锚点优先」当且仅当 anchors 落在第 1 维，也就是 `d1 > d2`。
- **旧写法：** `d1 < d2` 判成「锚点优先」，于是用 `a * stride + c` 去读一个
  通道优先的缓冲——**读到的全是别的通道的数值，框坐标被当成了分数**。
- **后果：** 过阈值的框从 20 个涨到 **2629 个**（NMS 后剩十几个，正好对应
  「HUD 十几个框」）；分数取到坐标值，于是出现 1.0 几与 `-386`。
- **为什么看不见：** 本模型的坐标已被归一化到 `[0,1]`，读错布局取到的仍是
  `[0,1]` 内的合法数值，**分数范围检查照样通过**。两个布局下的分数范围分别是
  `[0.0001,0.9355]` 与 `[0.0001,0.9932]`——单看这个判不出对错。

### 2.2 坐标是归一化的，被当成像素用了

- **事实：** TFLite 导出的 `cx/cy/w/h` 是**归一化到 letterbox 输入（640×640）**
  的比例值，不是像素。实测四个坐标通道范围 `[0.0023, 1.0038]`，
  `mean(cx)≈0.498`（正是 320/640）。
- **旧写法：** `(cx - w/2) / scale / srcW`——漏了 `* inputSize`，
  于是 0.5 被当成 0.5 像素。
- **后果：** 所有框被压成 0 大小，**屏幕上一个框都画不出来**（而 HUD 仍在计数）。
- **注意：** 这与 ONNX 的像素坐标约定不同，模型里没有任何元数据能看出来。

### 2.3 letterbox 的 pad 偏移没减

- **事实：** 模型坐标在**加过灰边**的空间里，必须减掉 `padX/padY`。
  竖屏取帧时 `padX = 140`（720×1280 → 缩放到 360×640 后左右各留 140 像素）。
- **旧写法：** 完全没减。
- **后果：** 框整体平移，平移量恰好等于灰边宽度（占 22%）。

### 2.4 逆旋转的 90° 与 270° 分支公式错（每个像素都取错）

```kotlin
val (sx, sy) = when (rotationDegrees) {
    90 -> Pair(outH - 1 - uy, frameWidth - 1 - ux)   // ← 两个分量都错
    270 -> Pair(uy, ux)                              // ← 纯转置 = 镜像，缺一次翻转
}
```

- **事实：** Android 的 `rotationDegrees` 是「把原始帧**顺时针**转这么多度才正立」。
  顺时针 90° 的正向映射是 `destX = SRC_H-1-srcY`、`destY = srcX`（第二项是 `srcX`，
  **不是** `SRC_W-1-srcX`，后者会多一次镜像）。反解即
  `srcX = destY`、`srcY = SRC_H-1-destX`。
- **核对结果（numpy 逐点，raw 1280×720、rotation=90）：**
  旧写法 **9216 个采样点 100% 取错源像素**，正确写法 0 个错。
- **后果特别隐蔽：** `sy` 会算到 `[560,1279]`，而原始帧只有 720 行，
  被 `coerceIn` 夹到 719 —— 于是正立图里约 **78% 的区域全都取原始帧的最后一行**，
  模型看到的基本上是一条糊掉的横线。
  而输入诊断（min/max/越界计数）看不出任何异常，因为读到的仍是合法 Y 值。

### 2.5 色度（UV）下标按原始平面步长算，但数组是紧凑副本

```kotlin
val uvIndex = (cy / 2) * uvRowStride + (cx / 2) * uvPixelStride   // ← 用了原始步长
```

- **事实：** `copyPlane` 返回的是**紧凑数组** `out[y * width + x]`，
  UV 的 width 就是 `(frameWidth + 1) / 2`、pixelStride 已展开为 1。
- **旧写法：** 用的是**原始平面**的 `rowStride/pixelStride`。真机常见的 NV21 布局是
  `rowStride ≈ frameWidth`、`pixelStride = 2`，于是下标被放大近 2 倍。
- **后果：** 上半幅画面取到**错误的色度**，下半幅直接越界、被 `in u.indices`
  兜成 128（中性色 = 灰度）。表现与「喂灰度图」完全相同——而本项目实测
  灰度输入会把最高分从 0.62~0.82 压到 0.04~0.55（阈值 0.30 下一个框都不出）。
- **注意：** Dart 那一侧的 `detect` 路径本来就传 `cw / 1`（正确），
  只有相机路径传的是原始步长——同一个函数被两个调用方用两套约定调用。

### 2.6 Dart 侧又转了一次（重复旋转）

- **事实：** 原生在采样时已经把画面逐像素转正，检测框就诞生在**正立坐标系**里，
  而 `VisionSource.frameSize` 报的也正是正立尺寸。
- **旧写法：** UI 既用正立尺寸构造 `DisplayFit`，又把 `rotationDegrees` 传给
  `mapDetectionsToScreen` 再转 90°，两处叠加。
- **后果：** 框相对画面整体偏 90°，画得出来、位置全错。
- **修法：** 直接**删掉 `mapDetectionsToScreen` 的 `rotationDegrees` 参数**，
  而不是「传 0」——让这个错误在类型上就写不出来，并配契约测试钉住。
  `rotateNormalized` 保留（将来 iOS 若返回原始帧坐标就用得上）。

## 3. 证据：与人工标注的 IoU

`data/dataset/images/trashbin/` 抽 8 张带人工标注的图，逐组合对照
（`scripts/check_tflite_decode.py --images 8`）：

| 解码组合 | 平均最佳 IoU | 过阈值框数（NMS 前，均值） |
|---|---|---|
| **正确**（通道优先 + 乘边长 + 减 pad） | **0.915** | 20 |
| 错布局（布局读反，坐标换算对） | 0.509 | **2629** |
| 漏减 pad | 0.499 | 20 |
| 漏乘边长 | 0.000 | 20 |
| **真机旧行为**（布局读反 + 旧坐标换算） | **0.000** | 2629 |

单张最好的例子：`bin (1).jpg` 正确解码 0.964，旧行为 0.000。

2.2 单独就足以让 IoU 归零，2.1 单独就足以让框数爆掉。
2.4 / 2.5 发生在**取帧阶段**，比解码更靠前：它们不改变「解码对不对」，
而是直接让模型看到一张错的图——所以它们的症状是「解码全对但分数极低」，
与上面两条的「框数/位置错」完全不同，必须分开验证。

## 4. 修复

`VisionPlugin.kt`：

1. `transposed = d1 > d2`（并写清「为什么必须是 `>`」）；
2. 坐标换算改为三步：`* inputSize` → `- padX/padY` → `/ newW/newH`。
   第 3 步用 `newW/newH` 而不是 `scale`——`newW` 就是 `(srcW * scale).toInt()`，
   与真正贴进画布的那块像素严格一致，避免整数截断带来的半像素偏差；
3. 逆旋转 90/270 分支改为 numpy 验证过的形式，并删掉了那段**本身就是错**的
   文档注释（它写着 `destY = SRC_W-1-srcX`，多一次镜像——错的公式注释是这次
   写错的源头）；
4. 色度下标改为按紧凑副本宽度 `uvWidth` 计算；`detectYuv` 的参数由
   `uvRowStride/uvPixelStride` 改成 `uvWidth`，两个调用方从此只有一套约定；
5. `decodeStats` 末尾追加 `geo=源尺寸->缩放后尺寸 pad=x,y`，
   `frameFormat` 同时报 `uvPlane=` 原始步长与 `uvCopy=` 紧凑宽度——
   把坐标换算与色度取样的**全部输入**摆在 HUD 上，画偏/变灰时第一眼看这里。

Dart：

6. `mapDetectionsToScreen` 删掉 `rotationDegrees` 参数；`VisionSource.frameSize`
   的注释写明「它同时是检测框的坐标系，UI 不得再旋转」；
   `test/vision_source_contract_test.dart` 增加「来源已把画面转正，映射时不得再旋转一次」
   的契约测试（用一个偏离中心的框，重复旋转会让它跑掉半幅画面）。

## 6. 顺带记录的性能事实（不是缺陷）

竖屏取帧下 `720×1280 → letterbox 到 360×640`：方形模型输入与 9:16 画幅不匹配，
**宽度方向只用了 640 中的 360**，等于把画面降采样 2 倍。垃圾桶这类大目标不受影响
（离线 0.915 IoU），但离得远的小目标会吃亏。若后续要提小目标召回，
可考虑按竖屏画幅重新导出/训练，而不是继续用方形 640。

## 7. 上真机前先算出「应该看到什么」

修完之后，用**设备实际使用的那套几何**（竖屏取帧 720×1280 → `360×640`、
`pad=(140,0)`、`scale=0.5`）在电脑上复算了一遍：把带人工标注的照片按 90% 视口
贴进竖屏场景，再走完整的 letterbox → 推理 → 解码：

| 项目 | 预测值 |
|---|---|
| 最高分范围 | **0.898 ~ 0.983** |
| 平均最佳 IoU | **0.927** |
| 命中（IoU ≥ 0.5） | **7/7** |

**这就是上真机时的对照基准**：如果真机上分数落在 0.9 上下、框落在垃圾桶上，
说明整条链路通了；如果分数很低，问题在取帧/颜色（第 2.4、2.5 条那一类），
而不是解码；如果框位置整体偏移，看 HUD 的 `geo=` 那一行。

把「预期值」先算出来再上真机，是为了让真机验证变成**确认**而不是**试探**——
后者每来一轮都要重装、重启、目视判断，代价高且结论模糊。

## 9. 真机实测（2026-09-27，Redmi 2609FRA74T / Snapdragon 685 / Android 16）

装包、授权、启动全部由 `scripts/verify_on_device.ps1` 自动完成；
`demo_page.dart` 的 `_logHud()` 每秒把 HUD 状态打一行到 logcat，
于是**不需要人看屏幕**就能判断链路是否打通（81 行日志，`artifacts/device/`）。

### 修好了的证据

| 观察项 | 真机值 | 说明 |
|---|---|---|
| `transposed` | `false` | 布局推导修正生效（旧码这里必为 `true`） |
| `invalid` | **0** | 不再有分数越界（旧码是「无效检测还在增长」） |
| `analyzed` | 0 → 29 持续增长 | 相机分析回路在跑 |
| `nativeDet` / `det` | 最多 8，81 帧里 70 帧非零 | **框真的到了 UI**（旧码是「有数字、画不出来」） |
| `maxScore` | 最高 **0.982** | 落在离线预测的 0.898~0.983 区间内 |
| `geo` | `480x640->480x640 pad=80,0` | 实测原始帧是 640×480（竖屏取帧 480×640），pad 偏移生效 |
| 崩溃 | 无 | — |

这一步最有价值的地方：**预测值与实测值吻合**。
第 7 节先用设备几何离线算出「应该看到 0.9 上下的分数、框落在目标上」，
真机跑出来落在同一区间——说明整条链路（取帧→转正→色度→预处理→解码→映射）
现在是一致的，不是碰巧凑出来的。

### 新发现的**未解决**问题：帧率不可用

| 指标 | 实测 |
|---|---|
| 单帧推理耗时 | 中位 **1182 ms**，最大 **5048 ms** |
| 帧率 | **约 0.7 ~ 1 FPS** |

已排除的原因：

- **不是 delegate 没挂上**：`tflite` 日志显示 XNNPACK 已生效
  （`Replacing 343 out of 345 node(s) with delegate`）。
- **不是省电模式**：`low_power=0`。
- 但**大核被限频**：cpu4~7 在负载下稳定在 **1.79 GHz**，而 `cpuinfo_max_freq`
  是 **2.61 GHz**（约 68%）——属于 ROM/温控限制。
- 本机 SoC 为 **Snapdragon 685**（4×A73 + 4×A53），本身是入门级。
- 当前依赖的 `com.google.ai.edge.litert:litert:2.2.0` 的 `classes.jar`
  **只有 17 个类，不含 NnApiDelegate / GpuDelegate**，所以 NNAPI/GPU 完全没用上。

结论：**纯 CPU float32、640×640 的 yolo11n 在这台机器上就是 ~1 秒**。
要让 demo 可用必须减算力，方向有四条（可叠加）：

| 方案 | 预期倍数 | 代价 |
|---|---|---|
| 加 NNAPI 或 GPU delegate | 2~5× | 需加依赖 + 做好回退（`litert` 本体不含 delegate 类） |
| 输入边长 640 → **416**（= 训练时用的尺寸） | 0.42×（≈500 ms） | 重新导出；**不改代码**，且与训练分辨率对齐 |
| int8 量化 | 2~3×，体积 1/4 | 需重新导出 + 改 Kotlin 张量处理（现码 `require` 输入元素为 4 字节 float32） |
| 416 + int8 组合 | 预期 100~200 ms（5~10 FPS） | 上述两项之和 |

这是**尚待决定**的取舍：后两条会改变模型交付物本身（分辨率/量化），
属于毕设里可见的精度-速度权衡，不该由我单方面定。

## 10. 播报门槛：低分只画框，不开口（2026-09-27 追加）

真机跑通后暴露的下一个问题是**误报会被念出来**：播报器原本只按
「类别可播报 + 两级冷却」过滤，**没有任何分数门槛**，于是 0.3 分左右的假框
也会说给用户听。

### 为什么播报门槛必须高于显示门槛

代价不对称：

- **显示**：屏幕上多一个框，代价接近零；
- **播报**：误报会让视障用户**对空无一物做出动作**，在马路牙子、楼梯口前
  这是安全问题。

而漏报的代价会被**帧的重复**摊薄：真实目标会在连续多帧被检出，某一帧分数不够
没念，冷却过后还有机会；误报只要**一帧**就够被念出去。所以这个门槛按**精度**定，
而不是按 precision/recall 的折中点。

### 门槛值由数据定，不靠感觉

新增 `scripts/pick_speak_threshold.py`：在 44 张带人工标注的实拍图上跑全链路，
把检出按分数与标注配对（IoU ≥ 0.5），扫出精度/召回曲线：

| 门槛 | 说出条数 | 误报 | 精度 | 召回 |
|---|---|---|---|---|
| 0.30（= 显示默认值） | 92 | 8 | 0.913 | 0.689 |
| 0.50 | 86 | 5 | 0.942 | 0.664 |
| **0.70（选定）** | **78** | **3** | **0.962** | **0.615** |
| 0.90 | 62 | 0 | 1.000 | 0.508 |

取 0.70：误报 8 → 3（**减少 62%**），每帧召回只掉 0.07，且会被多帧重播补回。
常量定义在 `app/lib/tts/announcer.dart` 的 `kMinSpeakScore`，
**换模型后必须重跑该脚本再改这个值**。

### 实现要点

- 门槛判定放在 `_rejectReason` 的**最前面**，且**不受 `force` 影响**：
  `force` 的语义是「别被冷却挡住」（时机问题），分数门槛管的是「这是不是真的」
  （正确性问题）。让 force 绕过它等于留了个「逢低分也照念」的后门。
- 低分候选被跳过时**继续看下一个候选**，所以低分的 P0 不会把高分目标一起挡掉。
- 界面把两个阈值分开写清：滑条改名为「显示阈值」，面板上另起一行
  「播报门槛 ≥ 0.70（低分只画框）」。不写清楚，用户会以为「滑条拉低了怎么还不念」
  是坏了。
- 单测 5 条覆盖：低分不播但有记录、边界 `>=`、`force` 绕不过、
  跳过低分后高分仍能播、门槛可注入。

真机确认（HUD 状态行）：`speakMin=0.70` 已生效。

## 11. 帧率优化：640 float32 → 416 int8（2026-09-27）

### 实测结果（同一台机器、同一段场景）

| 配置 | 推理耗时 | 帧率 | 离线 IoU | 模型体积 |
|---|---|---|---|---|
| 640 float32（原） | 776 ~ 1180 ms | 1.1 ~ 1.3 | 0.915 | 10.5 MB |
| 416 float32 | **324 ms** | 3.0 | 0.963 | 10.5 MB |
| **416 int8（现部署）** | **268 ms** | **3.7** | **0.966** | **2.87 MB** |

合计 **3.4×**（1.2 → 3.7 FPS）。

几条值得记下的结论：

- **输入边长是主因，且与面积成正比。** 预测 0.42×（(416/640)²），
  实测 324/776 = 0.42 —— 完全吻合。以后估耗时直接用面积比即可。
- **416 的离线精度反而更高**（0.963 vs 0.915）：416 正是训练时用的分辨率，
  640 是导出时放大的，等于让模型处理它没见过的尺度。
- **int8 只快 1.2×，远低于预期的 2~3×。** 原因：Ultralytics 导出的 int8 模型
  **保留 float32 输入/输出**（量化/反量化在计算图内部），
  XNNPACK 的 int8 收益被边缘算子吃掉一部分。
  但换来两件实在的好处：**零代码改动**（Kotlin 的 float32 通路原样可用，
  不用处理量化参数），以及**体积 1/3.7**。
- **`topAll` 这一项让「没有检出」不再有歧义。** 新增后实测 `topAll=0.028`：
  模型在 3549 个锚点上的最高分只有 0.028，远低于阈值 —— 说明镜头前**确实没有**垃圾桶，
  而不是阈值太高。两者此前的显示完全一样。顺带这也证明了修复后的链路
  **不再产生假框**（修之前同一场景会产生上千个）。

### 方案「加 NNAPI / GPU delegate」的可行性结论（有证据，不是推测）

查了 Google Maven 的权威索引，并直接 `javap` 了本地 Gradle 缓存里的 AAR：

1. `litert:2.2.0` 的 `Interpreter$Options` **只有**
   `setNumThreads / setCancellable / setRuntime / setUseXNNPACK` ——
   **没有 `addDelegate`，也没有 `setUseNNAPI`**。
   所以在当前这套 API 上**根本挂不上任何 delegate**。
2. 但 `litert-api:2.2.0` 里有新 API：
   `com.google.ai.edge.litert.CompiledModel`（含 `GpuOptions` / `QualcommOptions` /
   `Accelerator` / `NpuAcceleratorProvider`），而 `litert:2.2.0` 的 AAR
   **已自带 `libLiteRtClGlAccelerator.so`**（OpenCL GPU 加速器）。
   → **GPU 加速不需要新增依赖**，但要把 `YoloDetector` 从 `Interpreter`
   迁到 `CompiledModel`。
3. `litert-gpu` 最新只到 **1.4.2**（我们用的是 `litert` 2.2.0），
   走旧的 GPU delegate 会版本错配 —— 不走。

**CPU 侧已接近该机上限**：416 float32 下有效算力约 11 GFLOPS，
与 4×A73@1.79GHz（被 ROM 限频，满频 2.61GHz）的实测吞吐同量级。
继续提速只有两条路：**减少算力**（更小输入 / 更小模型）或
**换计算单元**（GPU via `CompiledModel`、或 NPU）。

### 顺带修掉：导出脚本里的布局标签也是反的

`export_tflite.py` 的 `explain_output_shape()` 写着 `transposed = d1 < d2`，
并把 `[1, 5, 3549]` 报成「`[1, anchors, 4+nc]`（转置）」——**恰好说反**。
Kotlin 里那句 `transposed = d1 < d2` 就是照着这条信息写的
（见第 2.1 节）。**一处错的名字会生产出另一处错的代码**，
现在两处都由 `check_tflite_decode.py` 同时核对，运算符必须都是 `>`。
