## 1. 這一輪暴露的真實缺陷：複核結果根本沒進數據集

**現象：** 人工在 X-AnyLabeling 裏改完框，`data/dataset/labels/` 裏仍是三階段
預標註的產物。

**根因：** GUI 保存只寫回**同名 `.json`**。X-AnyLabeling 0.4.43 的 PyPI 版能導出
YOLO、不能導入 YOLO，它的原生標籤格式就是同名 JSON。於是人工的修改停留在
`data/xtest/` 裏，訓練完全看不到。

**為什麼危險：** 和已經踩過的「標籤未鏡像目錄結構」是同一類錯誤——**不報錯**。
訓練照跑，指標照出，只是人工複核的收益為零。若不做這次核對，會直接得出
「人工複核沒用」的錯誤結論。

**修復：** 新增 `scripts/xlabel_io.py`，把「JSON → 數據集」變成**顯式的一步**，
並在轉寫前做質檢。

## 5. 無法迴避的方法論限制：劃分是同源的

44 張照片來自**同一次實地拍攝，只有一個 `source_folder`**。
分組防泄漏劃分（`assign_folds`）對單來源無從下手——它會把 44 張全部丟進 train，
val/test 為空，訓練直接跑不起來。

**處理（`scripts/single_source.py`）：** 退到**等間隔取樣**劃分
（train 36 / val 4 / test 4），並在 `split.json` 裏寫入機器可讀的標記：

```json
"single_source": true,
"single_source_note": "單來源等間隔取樣：同源劃分無法防泄漏，指標偏樂觀，僅用於跑通鏈路"
```

**這不是防泄漏方案，是誠實的退路。** 同一地點連拍的相鄰幀幾乎相同，
無論怎麼切都有泄漏，因此：

- 本輪產出的指標**只能用來確認鏈路連通和相對變化**，
  **不能作為論文裏的最終性能證據**；
- 論文中的性能數字必須來自多來源劃分（≥ 3 個獨立採集點位）；
- 單來源下討論「人工複核帶來多少 mAP 提升」也會被高估，
  因為 train 與 val 高度相似，模型容易記住具體場景。

**下一步的真實數據採集必須按「一個採集點位 = 一個文件夾」組織，且每類 ≥ 3 個點位。**

## 6. 對照實驗：人工複核到底買到了什麼

**設計：** 只換標籤，其餘全部相同——同一批 44 張圖、同一 `seed=42`、同一劃分
（單來源等間隔取樣是確定性的，兩份數據的 train/val/test 完全一致）、同樣
100 epochs / imgsz 416 / batch 8 / yolo11n。

| 配置 | 訓練標籤 | 權重 |
|---|---|---|
| 對照（A） | 複核前預標 86 框 | `runs/pg_ablation_prereview/weights/best.pt` |
| 實驗（B） | 複核後 122 框 | `runs/pg_review_v0/weights/best.pt` |

**test 折（4 張 × 未參與訓練的圖）：**

| 指標 | A 複核前 | B 複核後 | 變化 |
|---|---|---|---|
| 可評測實例數 | 4 | 6 | **+2** |
| mAP@0.5 | 0.502 | **0.788** | **+0.285** |
| mAP@0.5:0.95 | 0.402 | **0.556** | **+0.154** |
| macro Recall | 0.500 | **0.750** | **+0.250** |
| macro Precision | 0.946 | 0.567 | −0.379 |

**怎麼讀這組數字（關鍵，別讀錯）：**

1. **實例數 4 → 6 才是核心。** 複核前這 4 張圖的預標只給出 4 個框，實際有 6 個
   目標——**A 模型有 2 個目標從未被標註過，因此無論訓練多久都不可能召回它們**，
   它的召回率上限被標籤鎖死在 ~0.67。B 排除了這個上限。這就解釋了
   macro Recall 0.50 → 0.75。
2. **Precision 下降不是退化。** A 的高精度（0.946）是**漏標換來的**：它只對
   最容易的 2 個目標有把握，剩下 2 個直接不報。用「只答會的題」換來的精度
   在導盲場景是**最壞的結果**——漏檢直接等於危險，而誤檢只是多播報一次。
   本項目的優先級因此明確為**召回 > 精度**。
3. 一個重要細節：test 折裏 `bin (35)` 的預標為 **0 框**，人工補了 1 個。
   這正是「零框圖像」問題的直接體現。

**誠實聲明：** 4 張 test 圖、6 個實例，**這不是一個可信的性能評測**；
且單來源劃分存在泄漏（見 §5），絕對數值偏高。它**唯一**能支持兩個結論：

- 人工複核**修掉了標籤層面的召回上限**（這是結構性的，不依賴樣本量大小）；
- 「複核前 86 框 / 複核後 122 框」這個差異在驗證指標上可觀測。

**這組數字不能寫進論文的性能章節**，只能作為「複核流程有效」的支撐證據。
論文的性能結論必須來自 ≥ 3 個獨立採集點位的多來源劃分。

## 7. 可複用的操作規程（→ Task 10 的 300 張種子集）

```powershell
# 1. 預標（三階段）後轉成 X-AnyLabeling JSON，人工在 GUI 裏複核
python scripts\to_xanylabeling.py --images data/dataset/images/<src> `
    --labels data/dataset/labels/<src> --out data/xtest/<src>

# 2. 複核完先質檢，看有沒有壞框/未知類，再決定是否回寫
python scripts/xlabel_io.py check --json-dir data/xtest/<src> `
    --report data/xtest/check_report.md --csv data/xtest/boxes.csv

# 3. 質檢通過後回寫數據集（會覆蓋預標結果；必要時先備份）
python scripts/xlabel_io.py emit --json-dir data/xtest/<src> `
    --labels-out data/dataset/labels/<src>

# 4. manifest → 劃分 → 門禁 → 訓練
python scripts/make_manifest.py
python scripts/split_dataset.py --seed 42
python scripts/check_labels.py
python scripts/run_pipeline.py --skip-generate --epochs 100
```

**回寫前務必備份**：本次已把複核前的 44 個預標標籤存到
`data/auto/trashbin_pre_review_labels_20260922/`，用於對比與回滾。

## 9. 本輪同時修掉的一個報告缺陷

`run_pipeline.py` 的報告生成把數據集**硬編碼**為「合成數據」，
並且導出命令硬編碼指向 `runs/pg_pipeline/weights/best.pt`。

後果：用真人複核數據跑完，報告第一行仍寫着「合成數據，不可用於交付模型」，
而導出章節指向一個**已經過期的舊權重**。這類錯誤不會讓任何東西報錯，
只會讓人拿着錯誤的權重去導出、或誤以為數據還是合成數據。

**修復：** 數據來源改為 `--data-source` 參數（默認按 `--skip-generate` 推斷），
導出命令改用本次實際產出的權重路徑；單來源劃分會在報告頂部加顯式的
「指標可信度警告」。
