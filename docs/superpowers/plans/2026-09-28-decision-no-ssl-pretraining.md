# 决策记录：不引入自监督预训练 / 骨干替换

**日期：** 2026-09-28
**状态：** **已否决**（用户决定取消，不再投入）
**议题：** 是否为本项目引入「ImageNet 式有监督预训练 → SSL（DINOv2/MAE）预训练 → 接检测头
监督微调」这套流程。

---

## 结论

**不引入。** 三条理由，按决定性排序：

### 1. 「传统预训练」已经是现状，不是待添加项

本项目训练配置（`runs/pg_single_bin/args.yaml`）：

```
model: yolo11n.pt      pretrained: true
epochs: 100   imgsz: 416   freeze: null
```

即：已经在从大规模有监督预训练权重微调，全网络 + 检测头一起训。
所谓「预训练阶段」早已到位。

### 2. 自训 SSL 预训练在本项目**不可能**，换骨干在**设备侧不可能**

| 层级 | 判定 | 依据 |
|---|---|---|
| 自训 SSL（MAE/DINOv2 式） | ✗ | 本机 `torch 2.14.0+cpu`、`CUDA 不可用`、纯 CPU 28 核。自训需 1e8 量级图像 + 数千 GPU 小时，与我们可用的约 14 万帧差 **4~5 个数量级** |
| 换 SSL 骨干（设备侧） | ✗ | 现役 yolo11n：2.6M 参数、416 输入、真机 **268 ms**。DINOv2 ViT-S/14 为 22M 参数 + 518² 输入，ViT 在移动 CPU 上更慢；且所依赖的 `com.google.ai.edge.litert:litert:2.2.0` **不含任何 delegate 类**（`javap` 实测，`Interpreter$Options` 只有 `setNumThreads/setCancellable/setRuntime/setUseXNNPACK`），连提速手段都没有 |
| 换 SSL 骨干（离线侧） | ✓ 可行 | 但见第 3 条：用处有限，且我们已有等价手段 |
| 微调策略消融（freeze vs 全网络） | ✓ 可行 | 100 轮仅 **1.9 分钟** |

### 3. 必要性低：瓶颈是**标签覆盖**，不是**特征质量**

用本项目自己的数据说话：

- 训练 100 轮累计 **1.9 分钟**（1.1 秒/轮）→ **算力不是瓶颈**，数据才是。
- **有数据的类**已经很好：`bin` 真机分数 0.98、离线 IoU 0.966。
- **没数据的类**彻底不行：零样本最高分 `stairs` **0.000**、`step` 0.044、
  `footbridge_railing` 0.010、`barrier_water` 0.000
  （`scripts/probe_missing_classes.py`，150 帧）。
- 48 类里目前只有 1 类有可用数据。

**换更强的骨干不会给 `stairs` 产生一个标签。** SSL 改善的是泛化能力，
而本项目的失败模式是「模型没见过这个类」——这是数据问题，
不是骨干问题。在有数据的类上，现有骨干已经被证明够用。

（附注：现有 mAP50 0.982 来自单源切分，偏乐观，不能作为毕设性能证据。）

## 若将来重新考虑，正确的落点在哪

SSL 特征在本项目里**唯一站得住的位置是离线标注流程**，不是 App 的骨干：

- 用 DINOv2 嵌入做聚类 → 挑「彼此最不相似的帧」优先人工复核（比 phash 更强）；
- 用同一批嵌入找「不属于任何已知类的簇」→ 真正的类别发现，
  正好补上现有 `out_of_taxonomy_candidates` 只有文本概念、没有视觉概念的缺口。

这一条本次不做，但记录在此，避免下次讨论时从头再来。
