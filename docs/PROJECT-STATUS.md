## 0. 一句话

为视障人士做的**手机端离线视觉导航助手**：用手机摄像头识别香港街头的设施与障碍物，
用**粤语语音**播报，演示路线为 **调景岭站 → 彩明苑天桥 → 彩明商场**。

## 1. 项目框架

```
┌─ 设备端（Flutter + Android 原生）──────────────────────────────┐
│  相机 CameraX ──▶ 原生预处理 ──▶ LiteRT 推理 ──▶ 解码 ──▶ 类别映射 │
│                        （Kotlin，零拷贝）        │                │
│                                                  ▼                │
│  预览 AndroidView ◀── 画框叠加层 ◀── VisionFrame（EventChannel）   │
│                                    │                              │
│                                    ▼                              │
│                             播报决策（冷却+分数门槛）──▶ 粤语 TTS    │
└───────────────────────────────────────────────────────────────────┘
        ▲ 模型清单（模型 + 类别映射 + 版本）        │ 上传
        │                                          ▼
┌─ 云端闭环（后期）─────────────────────────────────────────────────┐
│  手机上传「未识别障碍物 + 新路线」 → 大模型/VLM 自动标注            │
│  → 人工抽样质检 → 训练 → 评测门禁 → 打包模型清单 → 下发            │
└───────────────────────────────────────────────────────────────────┘
        ▲
┌─ 数据与训练（本地流水线，也是云端的原型）───────────────────────┐
│  视频扫描选帧 → 老师模型预标 → SAM 精修 → VLM 验证 → 人工质检      │
│  → 数据集合并/切分 → 训练 → TFLite 导出 → 一致性门禁               │
└───────────────────────────────────────────────────────────────────┘
```

**类别表：50 类**（`configs/classes.json`，版本 4，已冻结索引）。
v4 为**纯追加**：id 48 `obstacle`（泛化兜底类，用于「前面有東西擋路」这类无法具体归类的结论）与 id 49 `escalator`（通用扶梯，按「先辨识出来再分」）；既有 0-47 的 id 与名称一字未改。
**当前模型：3 类**（pedestrian / bicycle / bin），通过 `modelClassIds`
映射到 50 类表 —— 模型可以有 N 类，表里有 50 类，**加类不需要改架构**。

## 4. 完整预期产出

### 4.1 毕设交付物

1. **可运行的 App**（Android，真机）：离线实时检测 + 画框 + 粤语播报，覆盖演示路线。
2. **50 类类别表**与配套的标注/训练/评测流水线（可复现）。
3. **数据集**与数据采集规程（含自动预标 + 人工质检的操作手册）。
4. **一版端侧模型**（TFLite int8，附模型清单）。
5. **评测报告**：逐类 P/R/mAP + 真机延迟与帧率 + 失败案例分析。
6. **论文素材**：六处静默缺陷的复盘、蒸馏可行性、零样本召回边界、标注成本分析。

### 4.2 已确认要做的后续能力（**不砍范围**）

类别范围**只增不减**：v3 的 48 类全部保留，v4 又追加了 2 类。数据缺口靠下面的闭环补：

> 手机拍照 → 把**未识别的障碍物图片**与**新路线**上传到服务器
> → 用**大模型 / VLM 自动标注** → 训练出一个新模型 → 下发到本地

这条闭环的各项前置条件：

| 前置 | 状态 |
|---|---|
| 云端标注用什么模型 | 已验证方向：接地/VLM 模型（GDINO 覆盖 46/48），**不能用开放词表检测器**（9 类零召回） |
| 自动标注后如何保证质量 | 三段式：老师预标 → SAM 精修 → VLM 验证 → **人工只抽样质检 5~10%** |
| 模型怎么下发 | ✅ **已定并已实现**：**模型清单**（模型 + `modelClassIds` + 版本 + 输入尺寸 + sha256），随模型一起走 |
| 「未识别障碍物」怎么判 | 未定。实测 **98% 的街景帧都有检出**，所以不能用「有没有检出」当条件 |
| 服务器算力 | GDINO ≈ **11.3 s/图**。⚠️ 这个数字**是在 RTX 5070 上实测的，不是 CPU**（`gd_detect.py` 用 `.to("cuda")`）。8033 张 ≈ **25 GPU-小时**（单环节）——即**云端标注必须有 GPU**，CPU 只会更慢 |

## 5. 难点排序（从难到易）

排序依据：**不确定性 × 影响面 × 是否卡住别人**。不按工作量排。

| # | 难点 | 难在哪 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **50 类的数据获取** | 12,000 个框；9 类零召回；部分类香港特有、公开集没有；云端闭环未建 | 唯一**卡住所有后续**的东西：模型、导航、演示都等它。且失败模式是「看起来在推进、实际没有」 |
| 2 | **云端闭环的评测可靠性** | 用老师标数据又用老师评测 → 指标虚高；没有人工核过的小样本就拿不到真实数字 | 闭环一旦跑起来会**持续自我确认**，比没闭环更危险 |
| 3 | **导航决策与视觉融合** | 时序仲裁、转向指令、方位推断（检测层不知道用户朝向）、误报代价不对称 | 学术上最重的一块，且与「安全」直接相关；目前完全没有 |
| 4 | **可用性评估（真实视障用户）** | 伦理审批、招募、实验设计、不可逆的体验风险 | 毕设说服力的关键，但外部依赖多、周期长，必须早排期 |
| 5 | **设备端性能天花板** | 268 ms/帧已是该机 CPU 上限；`litert:2.2.0` **不含任何 delegate 类**（实测），GPU/NNAPI 都挂不上 | 决定了能跑多少类、多大输入；短期内无法突破，只能接受并据此设计 |
| 6 | **iOS 端原生实现** | AVFoundation + Core ML，完全另写一套；需要 MacBook | 工作量明确但环境不具备；接口已留好（`VisionSource` 抽象），风险可控 |
| 7 | **类别索引契约** | 错位不报错，只是每帧名字全错 | 影响面极大但**已有四处防线**（模型清单随模型走 / Dart 断言 / 导出交叉校验 / 原生拒绝加载），所以排后面 |
| 8 | **「未识别障碍物」的判据** | 98% 帧都有检出，无法用「有无检出」筛；设备端没有算力跑嵌入模型 | 闭环的入口条件，难但可绕（用户手动标记 + 稀疏采样） |
| 9 | **标注成本与误标控制** | 48 项下拉选错不会报错；单类批次可解 | 有明确解法（单类批次 + 抽样质检），故排后 |
| 10 | **端侧数值一致性** | 布局/归一化/pad/旋转/色度五处曾同时错 | **已解决并有门禁**，不再构成风险 |

## 6. 下一步（按优先级）

**① 把 GDINO 接进 stage1，并接上 SAM 精修 + VLM 验证**
现在 `stage1_propose.py` 用的是 YOLO-World，对 9 个核心类零召回，等于全丢。
换 GDINO（46/48 有覆盖）+ 按类门槛压噪声，在本地把「老师预标 → 验证 → 抽样质检」
整条跑通一版 —— 这就是云端那一环的原型，**不需要先搭云服务器**。

**② 补 `scooter`（唯一零检出的类）与 `bicycle` 的**验证**侧数据**
`bicycle` 的训练侧已被 Roboflow 的 2038 框补上，但**val 仍是 2 实例**，
所以它的 mAP 依然不可引用。要修的是**香港实拍的单车径素材**（可以拍，也可以从
`data/raw/external/bicycle` 那 60 张里经老师预标挑出可用的）。
`scooter` 目前仍零检出；`data/raw/external/scooter` 有 60 张整图素材待预标。

**③ 把 Roboflow 那份第三方数据换成来源可追溯的**
当前用的是 14 项目拼盘，无法排除其中一个未声明许可的上游，
只能按"仅限研究用途"使用并全文署名（见 `docs/THIRD-PARTY-DATA.md`）。
若要写进可公开的成果，建议换成**单一来源、许可证明确**的数据集
（COCO 2017 的 bicycle 标注为 CC BY 4.0，或声明 CC BY 4.0 的单个 Roboflow 项目）。
替换的成本很低：`fetch_roboflow.py` 换一个 `--project` 即可。

**④ 人工核验的抽样集（约 30 帧）**
现在所有精度数字都是「对老师标注的保真度」。没有人工核过的小样本，
就拿不到真实准确率，而云端闭环会**持续自我确认**（用老师标、又用老师评）。
**这是比扩类更优先的事**——先有可信的尺子，再谈量。

**⑤ 导航决策引擎**
在数据与模型之后，但设计要先定（它决定需要哪些类、什么样的时序信息）。

## 7. 已确立的关键决策（避免反复讨论）

| 决策 | 理由 | 记录 |
|---|---|---|
| 不引入 SSL / 骨干替换 | **算力规模差 4~5 个数量级**（自训需 1e8 量级图像 + 数千 GPU-小时，我们只有约 14 万帧）；瓶颈是标签不是特征。⚠️ 该决策文档里「本机无 GPU、CUDA 不可用」的说法**是错的**，已更正；但结论不变——一块 12 GB 消费级卡改变不了 4~5 个数量级的差距 | `2026-09-28-decision-no-ssl-pretraining.md` |
| **不砍类别范围（只增不减）** | 用户决定；靠云端闭环补数据 | 对话 2026-09-30 |
| **v4 追加两个泛化类**（`obstacle` 48 / `escalator` 49） | 用户决定「泛化成障碍物」与「电梯先辨识再分」。Roboflow everyday-object-finder 的 `barrier`(2156) 与 `escalator`(1980) 语义比本表既有类都宽，硬映到具体类会教出错语义。代价：兜底类天生容易标注漂移，故在 classes.json 与 class_aliases.json 里都写了边界 | 对话 2026-10-02 |
| 类别表 id 1–22 冻结，只允许追加 | id 是 YOLO 标签契约，改了就静默错位 | `configs/classes.json` 的 history |
| 门（door）推拉用 tag 不用类 | 拆类会让同一扇门在不同帧被标成不同类，且方向常被遮挡 | 同上 |
| 播报门槛（0.70）严于显示门槛（0.30） | 误报让视障用户对空无一物做出动作，代价不对称 | `announcer.dart` |
| 运行时只有一个模型 | 双模型会把 268 ms 翻倍；且两套索引契约 = 两处静默错位风险 | 本文件 §2 |
| **第三方数据只进训练集，绝不进验证集** | 它自带逐图随机划分，相邻视频帧会跨 train/val；混进 val 会让验证指标既不代表性、又有泄漏 —— 而数字照样会打印出来。**本次对比之所以可信，正因为 val 是干净的**；若当初混进去，会得出「第三方数据大胜」的假结论 | `build_multiclass_dataset.py --add-train-only` |
| **比较模型指标必须写明置信度阈值** | 产品的播报门槛是 0.70，而 ultralytics 默认报告的 P/R **不在这个阈值上**。只看默认口径会得出「行人精确率从 0.756 崩到 0.469」，而在 0.70 处差别消失（0.980 vs 0.945）。一个不带阈值的「精确率」在本项目里没有解释力 | `compare_at_threshold.py`、`2026-10-02-third-party-data-yield.md` |
| **第三方数据集的标签绝不入库** | `.gitignore` 的 `!data/dataset/labels/**` 是全目录放行，会把别人的标注一起提交 | `tests/test_gitignore_third_party.py` |
| **类别映射跟着模型走，不写死在代码里** | 写死在 Dart 里时，服务端换类别集 App 不知道，会静默标错每个框；清单是唯一能携带它的载体 | `docs/MODELS.md` §2 |
| 清单与模型不符时**拒绝启动**，不猜映射 | 猜错就是每帧名字全错且不报错；宁可显示「模型与清单不符」 | `platform_vision.dart` |
