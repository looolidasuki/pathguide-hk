## 0. 一句话

为视障人士做的**手机端离线视觉导航助手**：用手机摄像头识别香港街头的设施与障碍物，
用**粤语语音**播报，演示路线为 **调景岭站 → 彩明苑天桥 → 彩明商场**。

## 1. 项目框架

```
┌─ 设备端（Flutter + Android 原生）──────────────────────────────┐
│  相机 CameraX ──▶ 原生预处理 ──▶ LiteRT 推理 ──▶ 解码 ──▶ 类别映射 │
│                        （Kotlin，零拷贝）        │                │
│                                                  ▼                │
│  预览 AndroidView ◀── 画框叠加层 ◀── VisionFrame（EventChannel）   │
│                                    │                              │
│                                    ▼                              │
│                             播报决策（冷却+分数门槛）──▶ 粤语 TTS    │
└───────────────────────────────────────────────────────────────────┘
        ▲ 模型清单（模型 + 类别映射 + 版本）        │ 上传
        │                                          ▼
┌─ 云端闭环（后期）─────────────────────────────────────────────────┐
│  手机上传「未识别障碍物 + 新路线」 → 大模型/VLM 自动标注            │
│  → 人工抽样质检 → 训练 → 评测门禁 → 打包模型清单 → 下发            │
└───────────────────────────────────────────────────────────────────┘
        ▲
┌─ 数据与训练（本地流水线，也是云端的原型）───────────────────────┐
│  视频扫描选帧 → 老师模型预标 → SAM 精修 → VLM 验证 → 人工质检      │
│  → 数据集合并/切分 → 训练 → TFLite 导出 → 一致性门禁               │
└───────────────────────────────────────────────────────────────────┘
```

**类别表：48 类**（`configs/classes.json`，版本 3，已冻结索引）。
**当前模型：3 类**（pedestrian / bicycle / bin），通过 `modelClassIds`
映射到 48 类表 —— 模型可以有 N 类，表里有 48 类，**加类不需要改架构**。

## 3. 进度与实测证据

### ✅ 已完成（有数字支撑）

| 项 | 实测结果 |
|---|---|
| 端侧推理性能 | 640f32 **776 ms** → 416f32 **324 ms** → **416int8 268 ms**（Snapdragon 685，CPU，无 NNAPI/GPU delegate 可用） |
| 真机帧率 | **3.6 ~ 3.9 FPS**（416 int8） |
| 多类链路 | 真机 `classes=3`、`映射 [6, 11, 7]`、`det=1 paint=1`、`invalid=0` |
| 类别表 | 48 类，索引冻结；Dart/文本/标注工具配置全部由同一源生成 |
| 数据集 | bin 44 图/122 框（人工复核）· pedestrian 488 帧/2218 框（COCO 自动）· bicycle 13 帧/15 框 |
| 逐类指标 | **bin mAP50 0.948 / 召回 1.000** · pedestrian 0.790 · bicycle 无统计意义（val 仅 2 实例） |
| 蒸馏可行性 | COCO person → 我们的模型：**老师框回收 94%**（零人工标签） |
| 视频扫描 | 143,784 帧 → 采样 2,397 → 候选 2,358 → 按类定额选中 **445 张**，1.7 分钟 |
| 标注路径规划 | 48 类 × 250 实例 = 12,000 框；从零手工 ≈ **33 h**，按老师可用性分流后 ≈ **16.8 h** |
| 零样本召回 | YOLO-World 对 9 个核心类**零召回**（`stairs` 最高分 0.000）→ 换成 GDINO：**48 类里 46 类非零**（`stairs` 出图率 60%、`tactile_paving` 30%、`road_excavation` 100%），只有 `scooter` 零检出 |
| 门禁 | `pytest` **248** · `flutter test` **64** · `flutter analyze` 0 问题 · Kotlin 编译检查通过 · 模型↔源码一致性检查通过 |

### ⚠️ 进行中

- **48 类的数据采集**：目前只有 3 类有可用数据；`bicycle` 靠这两条片子起不来（598 帧仅 13 帧带单车）。

## 4. 完整预期产出

### 4.1 毕设交付物

1. **可运行的 App**（Android，真机）：离线实时检测 + 画框 + 粤语播报，覆盖演示路线。
2. **48 类类别表**与配套的标注/训练/评测流水线（可复现）。
3. **数据集**与数据采集规程（含自动预标 + 人工质检的操作手册）。
4. **一版端侧模型**（TFLite int8，附模型清单）。
5. **评测报告**：逐类 P/R/mAP + 真机延迟与帧率 + 失败案例分析。
6. **论文素材**：六处静默缺陷的复盘、蒸馏可行性、零样本召回边界、标注成本分析。

### 4.2 已确认要做的后续能力（**不砍范围**）

按你 2026-09-30 的决定，48 类**全部保留**，数据缺口靠下面的闭环补：

> 手机拍照 → 把**未识别的障碍物图片**与**新路线**上传到服务器
> → 用**大模型 / VLM 自动标注** → 训练出一个新模型 → 下发到本地

这条闭环的各项前置条件：

| 前置 | 状态 |
|---|---|
| 云端标注用什么模型 | 已验证方向：接地/VLM 模型（GDINO 覆盖 46/48），**不能用开放词表检测器**（9 类零召回） |
| 自动标注后如何保证质量 | 三段式：老师预标 → SAM 精修 → VLM 验证 → **人工只抽样质检 5~10%** |
| 模型怎么下发 | **模型清单**（模型 + `modelClassIds` + 版本 + 输入尺寸）——未做，且不做会静默错类 |
| 「未识别障碍物」怎么判 | 未定。实测 **98% 的街景帧都有检出**，所以不能用「有没有检出」当条件 |
| 服务器算力 | GDINO ≈ **11.3 s/图**（CPU）。8,033 张 → ≈25 CPU-小时（单环节），需要 GPU 或分夜跑 |

## 5. 难点排序（从难到易）

排序依据：**不确定性 × 影响面 × 是否卡住别人**。不按工作量排。

| # | 难点 | 难在哪 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **48 类的数据获取** | 12,000 个框；9 类零召回；部分类香港特有、公开集没有；云端闭环未建 | 唯一**卡住所有后续**的东西：模型、导航、演示都等它。且失败模式是「看起来在推进、实际没有」 |
| 2 | **云端闭环的评测可靠性** | 用老师标数据又用老师评测 → 指标虚高；没有人工核过的小样本就拿不到真实数字 | 闭环一旦跑起来会**持续自我确认**，比没闭环更危险 |
| 3 | **导航决策与视觉融合** | 时序仲裁、转向指令、方位推断（检测层不知道用户朝向）、误报代价不对称 | 学术上最重的一块，且与「安全」直接相关；目前完全没有 |
| 4 | **可用性评估（真实视障用户）** | 伦理审批、招募、实验设计、不可逆的体验风险 | 毕设说服力的关键，但外部依赖多、周期长，必须早排期 |
| 5 | **设备端性能天花板** | 268 ms/帧已是该机 CPU 上限；`litert:2.2.0` **不含任何 delegate 类**（实测），GPU/NNAPI 都挂不上 | 决定了能跑多少类、多大输入；短期内无法突破，只能接受并据此设计 |
| 6 | **iOS 端原生实现** | AVFoundation + Core ML，完全另写一套；需要 MacBook | 工作量明确但环境不具备；接口已留好（`VisionSource` 抽象），风险可控 |
| 7 | **类别索引契约** | 错位不报错，只是每帧名字全错 | 影响面极大但**已有三处防线**（Dart 断言 / 导出交叉校验 / 原生拒绝加载），所以排后面 |
| 8 | **「未识别障碍物」的判据** | 98% 帧都有检出，无法用「有无检出」筛；设备端没有算力跑嵌入模型 | 闭环的入口条件，难但可绕（用户手动标记 + 稀疏采样） |
| 9 | **标注成本与误标控制** | 48 项下拉选错不会报错；单类批次可解 | 有明确解法（单类批次 + 抽样质检），故排后 |
| 10 | **端侧数值一致性** | 布局/归一化/pad/旋转/色度五处曾同时错 | **已解决并有门禁**，不再构成风险 |

## 6. 下一步（按优先级）

**① 模型清单与下发（立刻做，半天内可验证）**
模型下发必须带 `modelClassIds`，否则服务端换类别集时 App 会把每个框标成别的类
**且不报错**。这是**唯一一处"不补就会静默出错"**的地方，也是云端闭环的前置。

**② 把 GDINO 接进 stage1，并接上 SAM 精修 + VLM 验证**
现在 `stage1_propose.py` 用的是 YOLO-World，对 9 个核心类零召回，等于全丢。
换 GDINO（46/48 有覆盖）+ 按类门槛压噪声，在本地把「老师预标 → 验证 → 抽样质检」
整条跑通一版 —— 这就是云端那一环的原型，**不需要先搭云服务器**。

**③ 补 `scooter`（唯一零检出的类）与 `bicycle`（数据死角）**
走公开数据集（Roboflow 等）或专项实拍。

**④ 导航决策引擎**
在数据与模型之后，但设计要先定（它决定需要哪些类、什么样的时序信息）。

## 7. 已确立的关键决策（避免反复讨论）

| 决策 | 理由 | 记录 |
|---|---|---|
| 不引入 SSL / 骨干替换 | 本机无 GPU、自训差 4~5 个数量级；瓶颈是标签不是特征 | `2026-09-28-decision-no-ssl-pretraining.md` |
| **不砍类别范围（48 类全留）** | 用户决定；靠云端闭环补数据 | 对话 2026-09-30 |
| 类别表 id 1–22 冻结，只允许追加 | id 是 YOLO 标签契约，改了就静默错位 | `configs/classes.json` 的 history |
| 门（door）推拉用 tag 不用类 | 拆类会让同一扇门在不同帧被标成不同类，且方向常被遮挡 | 同上 |
| 播报门槛（0.70）严于显示门槛（0.30） | 误报让视障用户对空无一物做出动作，代价不对称 | `announcer.dart` |
| 运行时只有一个模型 | 双模型会把 268 ms 翻倍；且两套索引契约 = 两处静默错位风险 | 本文件 §2 |
