## 0. 一句話

為視障人士做的**手機端離線視覺導航助手**：用手機攝像頭識別香港街頭的設施與障礙物，
用**粵語語音**播報，演示路線為 **調景嶺站 → 彩明苑天橋 → 彩明商場**。

## 1. 項目框架

```
┌─ 設備端（Flutter + Android 原生）──────────────────────────────┐
│  相機 CameraX ──▶ 原生預處理 ──▶ LiteRT 推理 ──▶ 解碼 ──▶ 類別映射 │
│                        （Kotlin，零拷貝）        │                │
│                                                  ▼                │
│  預覽 AndroidView ◀── 畫框疊加層 ◀── VisionFrame（EventChannel）   │
│                                    │                              │
│                                    ▼                              │
│                             播報決策（冷卻+分數門檻）──▶ 粵語 TTS    │
└───────────────────────────────────────────────────────────────────┘
        ▲ 模型清單（模型 + 類別映射 + 版本）        │ 上傳
        │                                          ▼
┌─ 雲端閉環（後期）─────────────────────────────────────────────────┐
│  手機上傳「未識別障礙物 + 新路線」 → 大模型/VLM 自動標註            │
│  → 人工抽樣質檢 → 訓練 → 評測門禁 → 打包模型清單 → 下發            │
└───────────────────────────────────────────────────────────────────┘
        ▲
┌─ 數據與訓練（本地流水線，也是雲端的原型）───────────────────────┐
│  視頻掃描選幀 → 老師模型預標 → SAM 精修 → VLM 驗證 → 人工質檢      │
│  → 數據集合並/切分 → 訓練 → TFLite 導出 → 一致性門禁               │
└───────────────────────────────────────────────────────────────────┘
```

**類別表：50 類**（`configs/classes.json`，版本 4，已凍結索引）。
v4 為**純追加**：id 48 `obstacle`（泛化兜底類，用於「前面有東西擋路」這類無法具體歸類的結論）與 id 49 `escalator`（通用扶梯，按「先辨識出來再分」）；既有 0-47 的 id 與名稱一字未改。
**當前模型：3 類**（pedestrian / bicycle / bin），通過 `modelClassIds`
映射到 50 類表 —— 模型可以有 N 類，表裏有 50 類，**加類不需要改架構**。

### ⚠️ 進行中

- **50 類的數據採集**：目前只有 3 類有可用數據；`bicycle` 靠這兩條片子起不來（598 幀僅 13 幀帶單車）。
- **GDINO 當老師的質量**：覆蓋夠但**噪聲極大**（實測 ≈66 框/幀，`crowds_of_people_queuing` 8 個/圖），
  必須接 SAM 精修 + VLM 驗證 + 按類門檻才能當標籤用。
- **GDINO 已接進 stage1**（`--teacher gdino`，與原 YOLO-World 路徑共用同一條合併/寫出代碼）。
  2 張 HK 街景實測：150 框原始 → 145 框，**43/50 類非零**；輸出通過字段級契約檢查
  （`class_id`/`conf`/`bbox` 歸一化在 [0,1]/`source` 可打開）。
  ⚠️ 這只是**草稿**，未經複核；離「能當標籤用」還差第 2、3 段。
- **三段式已在本地跑通（第 1、2 段實測數字齊全）**：
  `--teacher gdino` 出草稿 → `stage2_verify.py`（LocateAnything-3B + SAM）
  → `stage3_arbitrate.py`。40 張 HK 天橋幀的實測：

  | 環節 | 數字 |
  |---|---|
  | 第 1 段（GDINO 出框） | 3414 框 → 合併後 **3086 框**（77 框/圖），**49/50 類非零** |
  | 第 2 段（VLM + SAM） | 3086 入 → 採納 2958；VLM 只**驗證了 320**（**拒絕 128，拒絕率 40%**） |
  | 第 3 段（仲裁） | 2958 → **採納 921、需複核 1820（62%）**、丟棄 34 |

  ⚠️ **兩個必須先解決的問題**（都是這次實測才暴露的）：

  1. **複核負擔 62%**：複核 1820 個框很可能比從零畫 921 個更慢，
     與「讓標註變快」的初衷相反。
     **成因已查清，且不是我原先猜的通用類**：撞車主力是
     `fence`(140)、`barrier_water`(120)、`cycle_path`(110)、
     `footbridge_entrance`(68) —— 這些**區域型**類別會被 GDINO 給出近乎滿屏的框，
     因而彼此 IoU≈1.0 地重疊（另有 119 個被標為「框面積異常大」）。
     通用類 `obstacle`(48) 只排第 6（79 次），**不是主因**。
  2. **「VLM 已驗證」名不副實**：`--max-boxes-per-image` 默認 30，而 GDINO 約 77 框/圖，
     超出的框**不丟棄、原樣保留且未經驗證**。複核查下來 **1755/1820 的 `vlm_verdict` 是空的**。
     已讓 stage2 彙總行顯式報出「未經驗證 N 個（佔採納 X%）」，超過一半還會warn。

## 4. 完整預期產出

### 4.1 畢設交付物

1. **可運行的 App**（Android，真機）：離線實時檢測 + 畫框 + 粵語播報，覆蓋演示路線。
2. **50 類類別表**與配套的標註/訓練/評測流水線（可復現）。
3. **數據集**與數據採集規程（含自動預標 + 人工質檢的操作手冊）。
4. **一版端側模型**（TFLite int8，附模型清單）。
5. **評測報告**：逐類 P/R/mAP + 真機延遲與幀率 + 失敗案例分析。
6. **論文素材**：六處靜默缺陷的覆盤、蒸餾可行性、零樣本召回邊界、標註成本分析。

### 4.2 已確認要做的後續能力（**不砍範圍**）

類別範圍**只增不減**：v3 的 48 類全部保留，v4 又追加了 2 類。數據缺口靠下面的閉環補：

> 手機拍照 → 把**未識別的障礙物圖片**與**新路線**上傳到服務器
> → 用**大模型 / VLM 自動標註** → 訓練出一個新模型 → 下發到本地

這條閉環的各項前置條件：

| 前置 | 狀態 |
|---|---|
| 雲端標註用什麼模型 | 已驗證方向：接地/VLM 模型（GDINO 覆蓋 46/48），**不能用開放詞表檢測器**（9 類零召回） |
| 自動標註後如何保證質量 | 三段式：老師預標 → SAM 精修 → VLM 驗證 → **人工只抽樣質檢 5~10%** |
| 模型怎麼下發 | ✅ **已定並已實現**：**模型清單**（模型 + `modelClassIds` + 版本 + 輸入尺寸 + sha256），隨模型一起走 |
| 「未識別障礙物」怎麼判 | 未定。實測 **98% 的街景幀都有檢出**，所以不能用「有沒有檢出」當條件 |
| 服務器算力 | GDINO ≈ **11.3 s/圖**。⚠️ 這個數字**是在 RTX 5070 上實測的，不是 CPU**（`gd_detect.py` 用 `.to("cuda")`）。8033 張 ≈ **25 GPU-小時**（單環節）——即**雲端標註必須有 GPU**，CPU 只會更慢 |

## 5. 難點排序（從難到易）

排序依據：**不確定性 × 影響面 × 是否卡住別人**。不按工作量排。

| # | 難點 | 難在哪 | 為什麼排這個位置 |
|---|---|---|---|
| 1 | **50 類的數據獲取** | 12,000 個框；9 類零召回；部分類香港特有、公開集沒有；雲端閉環未建 | 唯一**卡住所有後續**的東西：模型、導航、演示都等它。且失敗模式是「看起來在推進、實際沒有」 |
| 2 | **雲端閉環的評測可靠性** | 用老師標數據又用老師評測 → 指標虛高；沒有人工核過的小樣本就拿不到真實數字 | 閉環一旦跑起來會**持續自我確認**，比沒閉環更危險 |
| 3 | **導航決策與視覺融合** | 時序仲裁、轉向指令、方位推斷（檢測層不知道用户朝向）、誤報代價不對稱 | 學術上最重的一塊，且與「安全」直接相關；目前完全沒有 |
| 4 | **可用性評估（真實視障用户）** | 倫理審批、招募、實驗設計、不可逆的體驗風險 | 畢設説服力的關鍵，但外部依賴多、週期長，必須早排期 |
| 5 | **設備端性能天花板** | 268 ms/幀已是該機 CPU 上限；`litert:2.2.0` **不含任何 delegate 類**（實測），GPU/NNAPI 都掛不上 | 決定了能跑多少類、多大輸入；短期內無法突破，只能接受並據此設計 |

## 7. 已確立的關鍵決策（避免反覆討論）

| 決策 | 理由 | 記錄 |
|---|---|---|
| 不引入 SSL / 骨幹替換 | **算力規模差 4~5 個數量級**（自訓需 1e8 量級圖像 + 數千 GPU-小時，我們只有約 14 萬幀）；瓶頸是標籤不是特徵。⚠️ 該決策文檔裏「本機無 GPU、CUDA 不可用」的説法**是錯的**，已更正；但結論不變——一塊 12 GB 消費級卡改變不了 4~5 個數量級的差距 | `2026-09-28-decision-no-ssl-pretraining.md` |
| **不砍類別範圍（只增不減）** | 用户決定；靠雲端閉環補數據 | 對話 2026-09-30 |
| **v4 追加兩個泛化類**（`obstacle` 48 / `escalator` 49） | 用户決定「泛化成障礙物」與「電梯先辨識再分」。Roboflow everyday-object-finder 的 `barrier`(2156) 與 `escalator`(1980) 語義比本表既有類都寬，硬映到具體類會教出錯語義。代價：兜底類天生容易標註漂移，故在 classes.json 與 class_aliases.json 裏都寫了邊界 | 對話 2026-10-02 |
| 類別表 id 1–22 凍結，只允許追加 | id 是 YOLO 標籤契約，改了就靜默錯位 | `configs/classes.json` 的 history |
| 門（door）推拉用 tag 不用類 | 拆類會讓同一扇門在不同幀被標成不同類，且方向常被遮擋 | 同上 |
| 播報門檻（0.70）嚴於顯示門檻（0.30） | 誤報讓視障用户對空無一物做出動作，代價不對稱 | `announcer.dart` |
| 運行時只有一個模型 | 雙模型會把 268 ms 翻倍；且兩套索引契約 = 兩處靜默錯位風險 | 本文件 §2 |
| **第三方數據只進訓練集，絕不進驗證集** | 它自帶逐圖隨機劃分，相鄰視頻幀會跨 train/val；混進 val 會讓驗證指標既不代表性、又有泄漏 —— 而數字照樣會打印出來。**本次對比之所以可信，正因為 val 是乾淨的**；若當初混進去，會得出「第三方數據大勝」的假結論 | `build_multiclass_dataset.py --add-train-only` |
| **比較模型指標必須寫明置信度閾值** | 產品的播報門檻是 0.70，而 ultralytics 默認報告的 P/R **不在這個閾值上**。只看默認口徑會得出「行人精確率從 0.756 崩到 0.469」，而在 0.70 處差別消失（0.980 vs 0.945）。一個不帶閾值的「精確率」在本項目裏沒有解釋力 | `compare_at_threshold.py`、`2026-10-02-third-party-data-yield.md` |
| **第三方數據集的標籤絕不入庫** | `.gitignore` 的 `!data/dataset/labels/**` 是全目錄放行，會把別人的標註一起提交 | `tests/test_gitignore_third_party.py` |
| **類別映射跟着模型走，不寫死在代碼裏** | 寫死在 Dart 裏時，服務端換類別集 App 不知道，會靜默標錯每個框；清單是唯一能攜帶它的載體 | `docs/MODELS.md` §2 |
| 清單與模型不符時**拒絕啓動**，不猜映射 | 猜錯就是每幀名字全錯且不報錯；寧可顯示「模型與清單不符」 | `platform_vision.dart` |
